The resolution note amends D1 where they differ. Executable schema, transition tables, and Verifier-owned tests become the contract; an appendix is generated from those artifacts. Tests must therefore pin the accepted resolutions, not preserve a known draft-3 contradiction. The Builder may not edit acceptance tests or their expected-result fixtures to obtain a pass; the Builder files an objection, which the Verifier assesses against these sources. Sean retains integration and approval authority for the manual first build. [RN §§2–5; E E20; F §5.1.]

M1 implements the store, one-shot transitions, git journal, scheduler, `stage` and `alpha_authorize` gates, the decisions/API subset below, ledger, records, and recovery. Plan/baseline inputs can be installed as explicitly identified test fixtures; this does not require a complete interactive spec/architecture workflow. The one-shot work kinds exercised here are `stage_build`, `fix`, `verification`, `review`, `check_correction`, `replan`, and `assessment`, including engine registration of plan outputs. Other kinds are not dispatchable until their owning lane is enabled. [RN §4; D1 §§7.8, 19.3; Review B10/B17.]

The enabled human-decision subset is `blocker`, `out_of_band_change`, `stop_confirm`, `abandon_confirm`, `policy_widening`, `finding_disposition`, `severity_lower`, `finding_applicability_exclusion`, `check_correction_tightening`, `check_correction_loosening`, and `check_correction_unclassifiable`. The last review's manifests are tested per enabled kind. Other decision kinds have no executable effect in M1. Baseline approval fixtures are clearly test setup, not a public route that silently grants approval. [D1 §§10.1, 19.3; RN §2 R4, §3 B12; E E19.]

An Alpha authorization may produce an **issued authorization record** for a configured test target; it cannot execute deployment or claim Alpha Deployed. No live environment observation job, session, export/publication, management workflow, or real provider is required for M1. Guards against reaching those effects are required. [RN §4; D1 §§9.6, 19.3.]

## 2. Test method and fixtures

Resource markings in the matrix:

| Mark | Required resource |
|---|---|
| **S** | Real SQLite database, using the engine's configured driver, constraints, transactions, WAL and durability settings; not a mocked store. |
| **G** | Real git repositories and linked worktrees in disposable directories; actual git commands, refs, objects, indexes and files. |
| **A** | Scripted adapter with deterministic role outputs, usage, liveness, cancellation and failure controls. No model binary, provider credentials, paid calls, deployment or publication. |
| **P** | Real engine/child processes for restart, kill, timeout or locking tests. Scripted children have known test-owned identities and cannot be treated as D2 containment qualification. |
| **H** | Real loopback HTTP/SSE requests to the engine. |
| **B** | A real browser loading a minimal served test shell; Chromium-family and Firefox versions recorded. The full UI package is not a prerequisite. |
| **V** | A filesystem/SQLite durability fault harness that can distinguish synced from unsynced state. Killing a process alone is not this lane. |
| **—** | Pure contract/checker fixture; no S/G/A resource required. |

Each row is one named acceptance test. Where a row specifies a finite case set, the test has separately reported named cases with isolated fixtures; one passing case cannot stand for the others. The executable suite expands those cases without silently skipping a missing lane. In particular, the four journal-probe rows each require all five outcomes. [D1 §18; RN §3.]

The scripted adapter substitutes only the external role/backend behavior and the execution-boundary service. It can report running, terminated or unknown and emit delayed callbacks. Tests prove the engine refuses to snapshot/end/reuse on unknown termination; they do not prove that a production cgroup or container boundary is sound. Every real backend remains refused until D2 qualifies it. Check observations and protected-diff classifications used as test inputs are distinguished from role claims; scripted input does not qualify D3's real runner or semantic classifier. Unknown classification takes the human route. [RN §2 R3, §4; D1 §§15.1, 17(8)/(11)/(12); Review B08.]

Use deterministic barriers at intent commit, effect application, receipt commit, probe confirmation and finalizer commit. A crash test observes durable state by reopening SQLite and inspecting real git, then resumes through the public API where available. It asserts identities, file/ref contents, effect/launch counts, evidence and disposition, not just a state label. SQL constraint tests and fault injection may use a narrow test harness; no production endpoint exposes arbitrary state writes. [D1 §§6.2–6.3, 7.10, 16; RN §3 B05/B11/B17.]

Normal git fixtures use an integration ref not checked out anywhere and detached engine workspaces. The worktree-inventory tests enforce R5 before any ref movement. They do not require the deferred checkout-updating protocol. Manual integration of Surety's own implementation by Sean is separate from exercising the kernel's git mechanism in temporary repositories. [RN §2 R5, §4; E E20.]

Transition-case generation reads the Verifier-reviewed contract table, not the implementation's output. Expected outcomes and forbidden effects are independently pinned by this matrix and fixtures. Generating an appendix or enumerating transitions cannot turn an illegal edge into an accepted one by itself. [RN §3; Review B10/B17/N02.]

## 5. Execution order and acceptance boundary

The Verifier writes the relevant executable rows before the Builder implements that slice. Recommended order is store/identity (M02–M08), work and interruption (M09–M18), git/journal (M19–M34), records/accounting (M59–M67), gates and decisions (M35–M58), then API/load/contract checks (M68–M74) and the full M01 journey. An intentionally failing acceptance test is useful before implementation; a skip, missing harness, or fake substitute for an S/G/P/B/V requirement is not a pass. [RN §§3–4; F §5.1; E E8.]

Acceptance requires every M-row and its named cases to pass at the declared operating limits, with exit status as the machine judgment and retained diagnostics for failures. Tests of pure schema constraints use actual SQLite; git recovery uses actual git effects. A test about recovery must include its successful continuation as well as its refusal branch, so an engine that refuses everything cannot satisfy the suite. D2/D3 and F01–F08 remain explicitly unqualified or disabled, not silently counted as completed M1 work. [D1 §18; RN §4.]

The acceptance report records test/contract revisions, engine revision, OS/runtime/SQLite/git/browser versions, qualified load limits and separate SIGKILL/power-loss results. The finite matrix is the current stopping boundary: further expansion requires a concrete new finding, classified under RN §5. No extra model benchmark, real deployment or prolonged testing campaign is implied by M1 acceptance. [RN §5; E E20; F §5.8.]

An accepted executable contract supersedes its corresponding defective Appendix A detail, and the appendix is then generated from it. This plan is the inventory and ownership record for that conversion; completion of the conversion is demonstrated by the Verifier-owned executable tests, not by calling the matrix itself executable. [RN §§3, 5; E E20.]
