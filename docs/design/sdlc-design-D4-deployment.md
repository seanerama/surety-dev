## 1. The journey

What M4 must prove first, end to end, before any part is polished (E40). Each step names what it records; the sections that follow say why each is safe.

1. **The owner configures an environment** `alpha` for the project: adapter `local_service`, one target `app`, and configuration version 1 (what of the revision is deployed, the start command, the service's settings, its secret references, the identity method). The engine records an immutable `environment_configs` row and its `config_identity` (§3.2). `environment.configured`.
2. **The adapter is qualified on the host**, once per engine build, adapter version, host qualification and profile (`surety qualify-adapter local_service`, §2.6). `adapter.qualified`.
3. **A candidate is nominated and its workspace checks pass** (M3): its stage gates are satisfied.
4. **The operator asks for the deployment:** `surety deploy c-12 --env alpha` (Q3, decided, E95). In one request the engine seals the candidate's artifact from the object store (§3.1), reads the current configuration identity and the environment's target set, records the authorization `proposed` with those engine-derived values (J3) and evaluates `alpha_authorize`, which also requires that the completion's obligations can be met (J4). Satisfied: the authorization is `issued` and a `deploy` work item is created; the same request repeated while that deployment is pending returns them and creates nothing (J3). Not satisfied: the request is refused with the gate's reasons and nothing is deployed.
5. **The Release Operator, which is engine code (§8), intends the deploy:** under the environment lease, one transaction records the `deploy` operation, consumes the authorization (`authorization.consumed`), freezes the operation's intent (the authorization, source mapping, artifact digest and manifest, configuration version and identity, target set and environment identity) and starts its orchestration deadline (§4.1, §4.7).
6. **The effect, observed:** immediately before the effect the preconditions are read again, the issuing gate's eligibility among them (§4.1), and the service's admission is reserved with room for one post-deploy check (§4.7). One transaction records attempt 1 with its `deployment_generation` g and freezes the attempt's own intent: the unit names it may create, the prior instances it may replace, any cleanup it may do (§4.2). The adapter stops the previous generation and starts generation g in a `service` domain whose launcher runs nothing until the engine authorizes it, once (§9.2). The adapter's report is a claim; a reconcile read of a complete inventory of the environment confirms the effect (`applied`), and only then is the attempt `succeeded`. The finalizer writes the environment's `attempted` fact and creates the first verification round (§4.2).
7. **Verification by observation, in that round:** an identity read of every target; the required `post_deploy_identity` and `post_deploy_behavior` checks run by D3's runner against the service, each bound to the operation, attempt, generation and round; a second identity read. The engine writes one `deployment_verifications` row (§5.3). If it is `verified` and its round decides, the environment's `last_verified` moves to it (J5).
8. **Completion:** `alpha_complete` is evaluated for the candidate and the operation; satisfied, the candidate moves `developing → alpha_deployed` (`candidate.advanced`) and the work item completes (§5.5). The lease is released (§4.7).
9. **Afterwards:** the observation job reads the environment every `observation_cadence` and records its condition, `unknown` when it cannot tell (§6.2); a change nobody made through the engine is an out-of-band observation with a decision (§6.3); logs are collected by command and read as stored records (§6.1); `surety env teardown alpha` removes everything the engine created (§4.6). If the engine restarts while the service runs, the service keeps running but its supervision is `unknown`: nothing verifies on it, and its logs, relay and checks are refused until it is redeployed or torn down (§9.2, §7.3; E110, E116).

The journey has one human act that M4 requires (step 4, Q3) and two the owner performs once (steps 1 and 2). No agent takes part in steps 4 to 9.

## 2. The deployment adapter contract

**2.1 The calls** (A1; F §10). One interface every target implements, in engine code (§2.5). Two calls are **effects**; four are **reads**. Every call carries a deadline and an output bound and returns a typed result; nothing else crosses the interface. Appendix B gives the reference.

| Call | Class | Inputs | Returns |
|---|---|---|---|
| `deploy` | effect | a deploy capability (§2.2): environment, operation, attempt, generation, artifact (digest and sealed path), configuration version, target set, and from the attempt's frozen intent the unit names to create, the prior instances to replace and the cleanup allowed | a receipt: what the adapter did and saw, provenance `claimed` |
| `teardown` | effect | a teardown capability: environment, operation, attempt, and from its frozen intent the exact resources to stop and remove | a receipt, `claimed` |
| `reconcile` | read | environment, operation, attempt, the operation's and the attempt's frozen intents | `applied`, `absent`, `partial`, `conflicting` or `unknown`, with the inventory and per-target reads behind it (§2.4) |
| `status` | read | environment, the expected generation and application instance per target | per target: running state, the application instance `{invocation_id, pid, start_time}`, generation, supervision, and whether a read failed |
| `verify` | read | environment, per target the expected digest and application instance | per target an identity read `{target, method, expected, read, match, instance, generation, at}` (§3.4) |
| `logs` | read | environment, target, a byte bound | the service's recent output, through the redactor (§7.3); called only by the collection command, never by a read route (§6.1) |

**What a call promises.** An effect promises only that it tried; the engine never takes its receipt as the effect's outcome (§2.3). A read promises that every value it returns came from the target's own state at the time it names, and that a value it could not read is returned as unread, never as a default. **Bounds** (A.7): `adapter_effect_deadline`, `adapter_read_deadline`, `adapter_output_max_bytes`. A call past its deadline is cancelled (D1 §8.5): an effect becomes `ambiguous`, a read `unknown`. Output past its bound is `output_exceeded`, which for an effect is also `ambiguous`.

**2.2 The capability** (R2). An effect call takes exactly one capability object, minted from the attempt's frozen intent by the transition that records the attempt (§4.2) and never by anything else. It names the environment, the operation, the attempt and its generation, the engine incarnation, the environment lease generation, the artifact digest, the configuration identity and the exact names of the units the effect may create, stop or clean up. The adapter's one entry point (`adapterCall`) checks every field against the store before any host call: the attempt is `started` and current, the lease generation equal (D1 §8.3), the incarnation this one, every unit name derived from this environment's prefix (§9.3) and present in the attempt's frozen intent. A mismatch refuses the call with `deploy_capability_refused`, emits `deploy.capability_refused` with the field that failed, and issues nothing; the attempt ends `failed` with nothing applied. The capability expires when its attempt ends. A role's grant never holds one (§8).

**2.3 Outcomes and failure classes** (A1). An effect's adapter result is one of: `issued` (it ran its steps and saw no error), `refused` (the capability or a precondition stopped it before any host call), `not_issued` (it knows it changed nothing: a step before the first host change failed), or `uncertain` (anything else: a host call failed, timed out, or returned something it cannot interpret). **No adapter result completes an attempt.** `refused` and `not_issued` end the attempt `failed` with nothing applied. `issued` and `uncertain` are followed by `reconcile` (the effect probe, as D1 §7.10 probes a git write): `applied` makes the attempt `succeeded`; anything else makes it `ambiguous` and §2.4 applies. This is CH 8's lesson ("timeouts never duplicate a write") and AH §5.10's ("on ambiguous writes, reconcile the remote state using an operation identity before deciding whether to retry") made structural: the engine retries nothing it has not reconciled. A read's failure classes are `unavailable`, `deadline`, `output_exceeded`, `invalid_response`; each yields `unknown` for every value it should have returned, never zero, empty, `healthy` or `absent` (CH 9).

**2.4 Reconcile** (A2; F §3.7; D1 A.5; AR B02, E111). For an effect, reconcile answers "did attempt N take effect, partly, or not at all" from two sources only: **reads of the target's own state**, made now, and **the engine's own records of what it authorized** (the operation's and the attempt's frozen intents, §4.1 and §4.2, and the launch authorizations it granted, §9.2). It never consults the adapter's in-process memory or an earlier receipt; a restart that loses both changes no answer (`D4-A04`).

**First, a complete inventory.** Reconcile begins with a complete, bounded inventory of the environment: every resource the store recorded for it (units, domain cgroups, link sockets, runtime directories) and every unit whose name carries the environment's exact prefix, in any state, inactive and failed included, with the service manager's pending jobs for them. The inventory is a read: discovering a resource gives no authority to stop it, and every destructive action still uses positively owned exact resources (§4.6, §9.5). An incomplete inventory, or a required resource left unread, makes the answer `unknown`; a resource outside the states the attempt's intent permits makes it `conflicting`. **These two take precedence**, in that order, over `applied`, `absent` and `partial`, so every state has exactly one answer. No success predicate uses an empty result from a failed query.

**Settled before anything follows.** Before any reconcile read after a restart, the engine closes the attempt's launch (§9.2), so no launcher of an earlier incarnation can still make the effect happen after the read. Before the lease passes on, a retry starts or a replacement is dispatched, the engine also establishes **quiescence** of the prior effect: its host calls have returned or been awaited, and no service-manager create or stop job it caused is still pending. Killing a CLI or receiving a cancellation is not quiescence. While quiescence is not established the effect stays `ambiguous`, and no new effect is interleaved with it. This is the discipline the git journal already follows (`reconcile()` calls `othersChildrenGone()` before it probes, `src/journal/driver.ts`).

| Outcome, in order of precedence | Deploy of generation g | Teardown |
|---|---|---|
| `unknown` | the inventory is incomplete, or a read the answer needs failed, the binding of g's unit invocation to its recorded application instance included | as deploy |
| `conflicting` | a resource outside the attempt intent's permitted states: an active unit of a generation the intent does not name, whether or not `prior` is intact; two generations active; g active with an identity read that differs, or with an invocation or application instance other than the one authorized and recorded | a resource of the environment whose ownership is unexpected or uncertain, such as a prefixed unit no intent names |
| `applied` | the authorized unit invocation of g, running the original application instance recorded at its launch (§3.4), with an identity read matching the frozen digest; the termination of every `prior` instance the intent replaces established; nothing else of the environment active | closure and observed removal of every resource the effect covers: units, populated domain cgroups, link sockets and runtime directories |
| `absent` | g's unit and domain absent in every state; no launch for g granted; `prior` exactly as frozen; no unexpected resource of the environment; no outstanding host request or launcher that could still perform the attempt's effect | the entire frozen pre-state unchanged, and no outstanding stop or cleanup request that could still act |
| `partial` | anything else within the permitted states: `prior` stopped and g absent; g present but inactive or failed; a launch for g granted and its unit gone; a unit of g whose launcher was refused, still loaded | owned resources that survive |

**A refused grant is not proof of the unit's removal.** A refused launcher still represented by a unit is pending, and `partial` if it stays so, until bounded cleanup of that unit and a new read establish absence; it is never an applied deployment. **After an engine restart** the answer is still decided from the reads and the application instance recorded before the restart: if g's original instance was recorded and is read running, the effect is `applied`, but the service's supervision is `unknown` (§9.2) and no verification can pass on it (§5.3), so the operator redeploys or tears down (E110); if the instance was never recorded, the binding is unread and the answer `unknown`.

The ways on are D1 A.5's, as the git journal takes them (`src/journal/driver.ts`): `applied` → the attempt `succeeded` (`reconciled_succeeded` when it had been ambiguous), confirm and finalize; `absent` → `reconciled_absent`, and a new attempt is permitted after quiescence (§4.4); `partial` → `reconciled_partial`, a new attempt permitted only through the `rollout_partial` decision (D1 A.8); `conflicting` and `unknown` → the attempt stays `ambiguous` with a `blocker` decision naming what was read; it is reread each tick (D1 §8.1 step 2) and never retried, the environment lease stays held, and the operator's preempting teardown is available (§4.6).

**2.5 Where adapter code runs** (A4). In the engine process, as D1 §7 runs git: on the main thread with asynchronous spawns, argument arrays and never a shell, a constructed environment, bounded output and a deadline per call, and no transaction held across a call (D1 §6.1). Adapter code is engine code under `src/deploy/adapters/`; it is trusted (D2 §2.1) and it never executes candidate code. Candidate code runs only inside the `service` domain the adapter starts (§9.2), under D2's sandbox and boundary. `src/deploy/` joins the places permitted to start a process (E39 item 7), and only for the host tools its adapter names; the lint that enforces E39 item 7 enforces this. **Network:** the first adapter reaches nothing on the network: it talks to the user's service manager on the local bus and reads `/proc` and its own store (§9.3). A remote adapter (D5) would reach its target from the engine process, with its credentials resolved as §7 resolves the service's, never through D2's egress proxy, which serves sandboxed processes only.

**2.6 Qualifying an adapter** (A3; by analogy with D2 §7.2's attempts and D3 §2.8's runner self-test). The engine trusts an adapter on a host only while an `adapter_qualifications` row is current: same engine build hash, adapter id and version, host qualification and `service` profile fingerprint. Qualification runs by the operator's command (`surety qualify-adapter <adapter>`, `POST /v1/adapters/:a/qualify`), never at engine start and never by an agent, against **a qualification environment the engine creates for the run and removes after it**, with two fixture artifacts A and B the engine builds itself, through the real launcher, init, constructed root and launch authorization of §9.2. Each case runs beside a control that shows the same read able to succeed. **A case passes only by its explicit assertions and a working control**, never by an instrument's overall exit status (AR N03); a case whose control fails is `failed`, an unexercised one `not_exercised`, and either leaves the adapter unqualified (as D3 §2.8):

| Case | What must be observed |
|---|---|
| `deploy_read_back` | deploy A; the launcher's grant, the init's report and the host read agree (§3.4); `verify` reads A's digest on the target; control: B's digest differs |
| `replace` | deploy B as generation 2; A's unit gone, B read back, generation 2 recorded |
| `receipt_lost` | the engine-run instrument drops the receipt of an applied deploy within one engine process; `reconcile` answers `applied`. This is not an engine-crash test: kills of the engine with a real service are milestone tests (`D4-O03`, `D4-T07`) |
| `not_issued` | an attempt recorded and no effect issued; `reconcile` answers `absent` |
| `late_launcher` | a unit started after its attempt's launch was closed runs nothing (its launcher is refused); while the unit is still loaded `reconcile` does not answer `absent`, and answers `absent` once bounded cleanup has removed it |
| `out_of_band` | the instrument stops the unit by hand, then restarts it by hand, then changes one byte of a fixture artifact's sealed copy; each is detected (§6.3): `down`; a new invocation whose launcher is refused because the launch is single-use (§9.2), so nothing of the application runs again; an identity read that differs |
| `unreadable` | the instrument points the adapter's bus address at a path that does not exist (never by stopping the operator's manager); every read is `unknown`, never `absent` or `applied` |
| `refused` | capabilities naming another environment, another digest, another unit name, a stale attempt or a stale lease generation are each refused before any host call |
| `teardown` | `teardown` then `reconcile` answers `applied`; a host-side read finds no unit, cgroup, socket or runtime directory of the qualification environment |

The row records each case's result and control, the evidence as a `qualification_evidence` record, and the fingerprint it covers (`adapter.qualified`, `adapter.qualification_lapsed`). Without a current row, a deploy is refused before its intent (`adapter_unqualified`) and `alpha_authorize` is not satisfied (J4). **Cost:** no money and no model; host time not yet measured (the stand-in probe took about 2 s and covered far less); it creates and removes units that carry the engine home's prefix only (§9.5). **Alternative:** at every engine start, as D3's runner self-test; rejected because it would create and remove units under the operator's service manager at each start, which is an effect on the operator's host Sean should cause by command.

## 3. Artifact and configuration identity

**3.1 The artifact** (I1; F §7.7; AR B08, E117). For the first target **the artifact is a directory tree the engine projects from the candidate's revision**, and the engine builds it: from the object store, never through a work tree (E93 S2), so attributes, filters and hooks never touch its bytes. **The projection is exactly what is declared:** the revision's tracked files minus `.surety/` and minus the paths the configuration's `artifact.exclude` names. It is not a general claim to remove checks or private assets: a protected root configured elsewhere (D3 §1.1), or any other asset the project must not deploy, is excluded only if `artifact.exclude` names it, and for Alpha it must (AR N04). A symlink, submodule or special file in the projection refuses the build (`artifact_refused`), as D3's first runner refuses link inputs.

**Bounded preparation.** Preparation has finite limits, as D3 §2.4 bounds a check tree: `artifact_max_entries` entries and `artifact_max_bytes` bytes per artifact, `artifacts_max_bytes` for every artifact retained in the home, and `artifact_prepare_deadline` of elapsed work (A.7; their values are set by the M4 build spec, with Sean's approval). Before writing any staging data, admission checks that the artifact can be written while the engine home's filesystem keeps D2 §3.7's `host_reserve_disk` free and the retained total stays within its bound. Exceeding any limit refuses before deployment, records the specific bound (`ArtifactRefusal`), and removes only the unreferenced partial staging; a referenced artifact is never evicted to admit a new one. Materialization and hashing yield within the engine's existing API and tick responsiveness (D2 §3.7, `tick_step_budget`) and continue across ticks.

**Sealing.** The engine writes the projection into a staging directory under `$SURETY_HOME/artifacts/`, computes its manifest, removes write permission from every file, renames the directory to its digest's name and records the `artifacts` row `sealed` (`artifact.sealed`); if that digest is already sealed, it rehashes the sealed copy, discards the staging copy and reuses the bytes. Either way it records a mapping (below). A failed or refused build removes its staging state (`artifact.failed`). A sealed artifact is never written again; it is retained while any authorization, operation, verification round or environment record names it (D1 §14.3's rule, applied to artifacts).

**The digest.** `artifact_digest` is `sha256:` of the canonical manifest, the complete sorted list of `[path, type, mode, size, sha256(content)]`. **The mode is a canonical class**, as git's: `100755` for a file executable in the revision, `100644` for any other regular file. Sealing removes write permission and keeps the executable class; ownership, the umask and the removed write bits never change the digest, and a changed executable class does. The target read (§3.4) reconstructs the same class and separately checks that the tree is presented read-only with its pathname immutable. The manifest is complete: an extra or a missing entry, a link or a special file is refused or reads `differs`, never silently omitted. Content hashes are SHA-256 of the bytes, not git object ids, so a target can be read back without git (§3.4). The projection is deterministic: projecting the same revision under the same configuration again yields the same digest, on any host (`D4-I01`). That is the whole reproducibility claim, and for a projection it is exact. **Integrity:** the engine rehashes the sealed copy as an effect precondition of every deploy (§4.1); a difference refuses the deploy (`artifact_corrupt`), marks the artifact `failed`, and raises a `security` finding of severity `high` scoped to the project, since only a same-uid process outside every domain can have changed it (D2 §8 class C).

**Bytes and provenance are separate records** (RV3; AR N04). An `artifacts` row is the sealed bytes, one per digest per project. An `artifact_mappings` row is one source-to-artifact mapping (D1 A.3 `source_delivery_mapping`), immutable: `{dev_revision, delivery_commit: null, artifact_digest, artifact_spec_fingerprint, config_version, builder: "engine-projection@<engine version>"}`. Many mappings may name one artifact: two revisions that differ only in `.surety/` or in excluded paths project to identical bytes, and the second projection reuses the sealed bytes and records its own mapping, never borrowing the first's revision. The authorization, the operation's frozen intent and each verification round reference the mapping as well as the digest, so the provenance they carry is always their own candidate's. `delivery_commit` stays null until Beta (D5).

**A build step** (Q4, decided, E95). Most real projects need one (installing dependencies, compiling). D4 designs it as a **build execution**: D3's runner with a `build` profile identical to `check` except that a declared output directory is collected after termination, through the secret screen, into the staging directory, and the artifact is the output tree. The digest then identifies the output bytes, not a function of the source: a rebuild may yield a different digest, which is a different artifact with its own mapping recording the build definition's fingerprint and every program hash used (D3 Q6's limitation applies: a program hash does not pin its libraries). **M4 builds the projection only**, with the reference project needing no build step; the build execution waits for the first project that needs it, and until then a project that must be compiled or have dependencies installed is not supported (§11 class B).

**3.2 Configuration** (I2). Configuration is everything besides the artifact that decides what runs: the start command (an argument array whose program is the configured runtime and whose arguments name files in the artifact), the service's environment variables, its listen port inside its own network namespace, its resource limits (§9.2), its egress hosts (none, and in M4 none allowed, §10 X2), the artifact specification (`exclude`), the identity method, the target set, the adapter id and version, and the **secret references** (§7). It lives in the engine's store as **immutable `environment_configs` versions**, written only by the owner through `PUT /v1/projects/:p/environments/:e/config` (`surety env config`), never in the repository, because roles write the repository and configuration decides what code runs with which authority (Q5, decided, E95). A version is never edited; a change is a new version (`environment.configured`). An agent never writes configuration and its context package never contains a secret-marked value. **Deployment secret references have their own validated namespace**, distinct from the provider references `src/invoke/keys.ts` accepts today (`KEY_REFERENCES`, three backend references): M4 extends that parser for them, and a reference outside either namespace is refused (AR N04).

**`config_identity`** is `sha256:` of the canonical version content with each secret reference replaced by `{ref, digest}`, where `digest` is HMAC-SHA256 of the secret's value under a key the engine generates once per home (`$SURETY_HOME/secret-digest.key`, 0600, absent from every mount plan). The digests are part of the version and fixed with it, so the store holds no value and no unkeyed hash of one (D1 §5.5). **One rule for rotation** (RV5). The engine reads secret files only at start (as built, `holdSecretFiles`), so a held value changes only across a restart, and a version is never edited. At start the engine recomputes each held value's digest and compares it with every environment's current version: where one differs, that version becomes `secrets_changed`, deploys of the environment are refused (`config_secrets_changed`) and the environment read says why, until the owner writes a new version (`surety env config <env> --resolve-secrets` writes the same content with the newly resolved digests; any other edit does too). The new version has a new identity, so every authorization bound to the old one fails its precondition (§4.1), and a new request redeploys with the new value. A file replaced while the engine runs changes nothing until the next start: the engine keeps the value it read, and the identity still describes it. **Until the service is replaced**, the environment read shows the configuration and secret version the running service was launched with beside the current one, and reports `rotation_pending_replacement` (§6.1; E116); it never shows a value to explain it.

**3.3 The target set.** The environment's targets, each a name and the adapter's address for it (for `local_service`, the target name alone; §9.3). The set is part of the configuration version, so a target-set change is a new identity and a new authorization, and D1 §2.5's "deployment generation incremented on every target-set change" holds by construction. `local_service` accepts exactly one target in M4 (§10 X2).

**3.4 Identity reads** (I3; RV1; AR B01, E110). An identity read establishes, per target, what is actually running, from the target's own state and not from the artifact's account of itself. For `local_service` the method is `tree_digest`, and its first task is to find **the application process**, which is neither the unit's main process (that is the launcher, §9.2) nor the domain init. It is bound by a chain of facts, each read from the host:
1. **The unit.** The service manager's `ControlGroup` and `InvocationID` for exactly the frozen unit name; the cgroup must be the domain cgroup the engine recorded when it authorized the launch, and the invocation the one it authorized.
2. **The init.** At authorization the launcher, engine code that has run nothing of the application's, presents the init's host pid and start time; the engine accepts them only if `/proc` shows that process in the unit's cgroup, a child of the launcher, with innermost `NSpid` 1, and records them on the attempt.
3. **The application, once.** The init reports `started` with the application's pid in its namespace (D3 §2.6's report, on the channel application code cannot reach, D2 §2.3); the engine resolves it to the one member of the domain's `cgroup.procs` whose innermost `NSpid` is that pid and whose parent is the recorded init, and records **the original application instance**: host pid, start time (`/proc/<pid>/stat`), the executable's path and SHA-256 (`/proc/<pid>/exe`) and its arguments. The init's report and the host-side read must agree; neither alone binds anything, and a disagreement is `conflicting`. **The record is immutable for the domain's life:** neither the init nor the engine ever substitutes a descendant, a reparented child or any other process for it, and no later enumeration rebinds it, after a restart included.
4. **The read.** At each identity read the original instance must still exist with the same start time, so a reused pid is never taken for it; still be in the cgroup; have the same executable hash, which must be the configured runtime's, and arguments equal to the configured start command; `/proc/<pid>/mountinfo` must show `/surety/app` as a read-only bind whose source is the sealed directory of the expected digest; and the tree at `/proc/<pid>/root/surety/app`, walked from the host following no link and opening no special file, within `adapter_read_deadline` and the manifest's entry count, must hash to the digest, each file's mode class reconstructed as §3.1 says. **The read is a stable snapshot** (AR §8.3, B01's precision obligation): the instance's pid and start time, and the init's and the unit's, are checked before and after the executable, arguments, mounts and tree are read; a change between them, or an inconsistent snapshot, is `unread` or `differs`, never a mixture recorded as `match`.

The read's `instance` is `{invocation_id, pid, start_time}`; its `generation` comes from the unit name and the authorization record. A restarted unit, an application that exited (nothing restarts it, §9.2), a pid now held by another process, and an `exec` into another program or with other arguments each fail step 4 and read `differs` or `unread`, never `match`. **Not every `exec` is detected:** an application that re-executes the same runtime with identical arguments keeps its pid, start time, executable and arguments, so these fields do not distinguish it, and D4 does not claim to (§11 class C); what the read establishes is the runtime, its arguments and the tree it runs from. **What the probes showed of this chain** (preamble): the host-side reads of steps 1, 3 and 4 on this host, with a stand-in launcher and init; the init was found by enumeration and the application's pid came through a scratch file. The launch-time report, its agreement with the host read under the real launcher, and the record's retention against pid reuse are established only by the adapter's qualification (§2.6, `deploy_read_back`) and `D4-I05`.

**Why the service cannot satisfy its own read.** The read never asks the service anything: it reads the kernel's view of the service's filesystem. The service cannot alter that view: the artifact is mounted read-only, and the `service` profile holds its pathname immutable, ancestors included, for the domain's life (D3 L6's property, §9.2), so renaming a directory and putting other bytes at the same path is refused. A version endpoint, a banner, a log line or a `post_deploy_identity` check that asks the application which revision it is, is the application's claim; such a check may be required in addition (§5.1), and it never substitutes for the engine's read (V3). **What the read cannot establish** (§11 class C): that the running code never loads code it wrote or fetched at run time; a process the service starts from its volatile filesystem is the artifact's own behaviour.

## 4. The deploy operation

**4.1 From authorization to operation** (O1; D1 §9.6, RN R1).

**The request.** `POST /v1/projects/:p/deployments {candidate, environment}` (`surety deploy`). In the request's transaction sequence the engine: (1) seals the artifact for the candidate's revision under the current configuration version (main thread, outside a transaction, as D3 §2.4 builds a check tree), or finds it sealed; (2) records the authorization `proposed`, binding the candidate, the environment, the sealed digest and mapping, the current configuration identity and the target set, all engine-derived (J3: the production route accepts no caller-supplied digest, identity or targets, which `proposeAuthorization` does as built under SEAM §75); (3) evaluates `alpha_authorize` for that authorization, which, with J4, also requires that the completion's obligations can be met (a current adapter qualification, the identity method declared, and at least one required `post_deploy_behavior` check in the completion scope); (4) satisfied: `issued` (an earlier issued authorization of the candidate for the environment is superseded, as built) and a `deploy` work item with trigger `(deployment_request, <authorization id>, 1)`; not satisfied: the response carries the evaluation's reasons and nothing else happens. **Repeated requests coalesce** (J3, E118): a request for a candidate and environment whose deployment for the same binding is pending (its authorization issued and not consumed, or its operation not terminal) returns that authorization and work item and creates nothing, so a retried request or a lost response never becomes a second deployment. A deliberate request after the earlier operation is terminal makes a new authorization, because `binding_hash` includes the authorization's `generation` (as built, the same binding returns the existing, possibly consumed, row). Caller-supplied bindings exist only for harness fixtures, routed through `src/testing/` under M74's confinement, never through a harness branch in the production route.

**The intent.** The Release Operator claims the work item, then takes the **environment lease** (`LeaseKind` `environment`, J2): one deploy, rollback or teardown operation per environment at a time, **held from the intent until the operation's verification is computed and its completion evaluated**, or until §4.7's rule for its way out releases it (RV2; AR B06); only the operator's preempting teardown takes it earlier (§4.6). One transaction then: checks the authorization `issued`; records the `operations` row (kind `deploy`, target `{environment}`, subject `{candidate, artifact_digest}`, `authorization`, `idempotency_key` = sha256(`deploy`, environment, authorization, semantic generation), `deadline_at`, and the orchestration deadline and stage of §4.7); moves the authorization `issued → consumed` (`authorization.consumed`); writes **the operation's frozen intent** into `finalizer_inputs`, which the database already refuses to change (`0003`): the authorization, the source mapping, the artifact digest and manifest record, the configuration version and identity, the target set, and the environment's identity and prefix; and appends the journal's `intended` event (J1). The operation's intent names no unit and no prior state: those belong to each attempt (§4.2; AR B03, E112), so a retry never needs the frozen operation changed and the trigger that refuses its change stands unamended. One authorization makes at most one deploy operation; retries are attempts of it (§4.4).

**Rechecked as effect preconditions, immediately before each attempt's effect** (D2 C2 and K8's pattern, D1 §3.4 `effect_intents.preconditions`):
- the authorization is still this operation's and not superseded;
- **the issuing gate's eligibility, revalidated** (AR B04, E113): `alpha_authorize`'s rule re-evaluated for the operation's exact candidate and authorization binding against the current effective protected version, policy, deciding registrations and results, required sign-offs and approvals, findings and evidence integrity. This read neither issues nor consumes another authorization; the operation's own consumption of its authorization is expected and is not a change. A registration or invalidation a trigger owes is a barrier to eligibility, so an earlier satisfied evaluation never stands in for it (as D3 L2 makes Gates wait for it);
- the candidate has no `superseded_by` (D3 Q9);
- the environment's current configuration version is the frozen one and is not `secrets_changed` (§3.2);
- the sealed artifact rehashes to the digest (§3.1);
- no out-of-band observation of the environment is open (§6.3);
- the adapter qualification and the host qualification are current;
- the environment lease is held at the expected generation;
- no unit or domain of the environment is of unknown ownership or unaccounted reservation (§9.2);
- the service's admission, with the check capacity it reserves, is granted (§4.7); this one alone may wait, within the orchestration deadline.

Each precondition and the dependency it read are recorded in the attempt's durable **precondition manifest**. A failed precondition ends the operation `failed` with `outcome_detail` `EFFECT_PRECONDITION_CHANGED` naming the fact, before any adapter call; the consumed authorization is not restored, and deploying again takes a new request.

**4.2 Attempts, their intents, the journal and the generation** (J1; AR B03, E112). Each attempt is one transaction before its first host call, recording: the `operation_attempts` row `started`; the environment's next **`deployment_generation`** (one monotonic counter per environment, `environments.deployment_generation`, so a generation names one attempt across every operation of the environment); **the attempt's frozen intent**, immutable as the operation's is: the exact unit names it may create (generation g's), the prior resource instances it may replace (`prior`: the unit, invocation and application instance the environment's last confirmed deployment left running, or none), and any cleanup of earlier attempts of the operation it is explicitly authorized to do (only after `partial`, §4.4); the capability (§2.2), minted from that intent; the attempt's launch state `authorizable` (§9.2); and the journal's attempt event. The attempt's capability and its reconcile probe use the attempt intent. No attempt changes the operation's authorized inputs (a retry with a different artifact or configuration is refused) or acquires authority over a resource its intent does not name.

Then, with no transaction held, the adapter's `deploy`; then the receipt (`applied` claimed, or the adapter result) as a transition; then `reconcile` as the probe; then the confirmation transition (`confirmed`); then the **finalizer**, keyed on the operation and idempotent (D1 §7.10): it records the confirmed effect once, writes the environment record's `attempted` fact `{operation, attempt, generation, outcome: applied, at}`, and **creates, or on replay returns, one durable verification round** (§5.3). The identity reads and check executions of that round happen outside the finalizer's transaction, against the round's identity. Replaying the finalizer returns the same receipts and creates no second round; recovery resumes the round or explicitly supersedes it (§5.3). **A confirmed effect is not a completed deployment** and not a verified one: `succeeded` means the target was observed running generation g; verification (§5) and completion (§5.5) are separate facts.

**4.3 A kill at every step** (O2). "Kill" is SIGKILL of the engine (D1 §18); the service, being its own unit under the service manager, survives it (§9.2), with its supervision `unknown` thereafter (E110).

| Kill point | What is durable | What recovery does |
|---|---|---|
| Before intent | the request; perhaps the issued authorization and the work item | the work item is eligible again; no operation exists; the next claim intends exactly once (the idempotency key and the consumption are one transaction); a repeated request coalesces (§4.1) |
| After intent, before the attempt | the operation `intended`, the authorization consumed, the operation's frozen intent, its orchestration deadline | the preconditions are read; holding, attempt 1 starts as the ordinary course; otherwise the operation fails before any effect (§4.1) |
| After the attempt row, before or during the adapter's effect | the attempt `started` by an earlier incarnation, with its frozen intent | the attempt's launch is closed first, and a launch request of the earlier incarnation is refused even before recovery visits its row (§9.2); the attempt becomes `ambiguous`; quiescence is established (§2.4); `reconcile` then decides: `applied` confirms and finalizes, and the round it opens ends `unknown` because the service's supervision is `unknown`, so the operator redeploys or tears down (E110); `absent` permits a retry (§4.4); `partial` raises `rollout_partial`; `conflicting` and `unknown` block, with preempting teardown available (§4.6) |
| After the effect, before its receipt | as above | as above; the read finds the effect applied and nothing is deployed twice |
| After confirmation, before the finalizer | the journal `confirmed` | the finalizer runs; `attempted` written once; one verification round, created once |
| During verification | the round open; check executions in flight; no verification row | the service survives with supervision `unknown`, on which no verification passes (§5.3) and against which every check is refused `redaction_unavailable` (§7.3); interrupted executions take D3 §2.6's recovery and no result is synthesized; the round is recorded `unknown` naming `supervision_unknown`; the lease is released by §4.7; the operator redeploys or tears down (E110's accepted cost) |
| After the verification row, before completion | the row; evaluations stale | `alpha_complete` is recomputed at the next tick (D1 §8.1 step 7) from the current evidence (§5.5); the advance and the evaluation are one transaction |

The invariants D1 §16.2 states hold for deployment: after a kill at any point no authority to launch a service survives except through a fresh authorization of the current incarnation; no surviving service is adopted, its supervision staying `unknown` until it is replaced or torn down; every attempt is terminal or `ambiguous` with a decision; no generation is used twice; one finalizer replay creates no second round; no verification is credited to an attempt or round it was not bound to (§5.3); no duplicate deployment exists (`D4-O03`).

**4.4 A failed or partial deployment** (O3; F §3.6, §7.7). **The record:** `attempted` carries the attempt's outcome (`failed`, `partial`, `ambiguous`, or later `verification_failed` and `verification_unknown`, §5.3); **`last_verified` is never changed by a failure** and is never erased; `observed` is whatever the next read shows. Because the first target runs one generation at a time (§9.3), a failed attempt can leave nothing running while `last_verified` still names the previous generation: the record shows exactly that, three facts, and `last_verified` is never read as running (F §3.6). **What the operator can do next:**
- **Retry**, a new attempt of the same operation with a new generation and its own frozen intent (§4.2), permitted only after `reconciled_absent` or `reconciled_partial` (D1 A.5) and after quiescence of the earlier attempt (§2.4). After `reconciled_absent` the engine retries by itself at most `deploy_auto_retries_max` times (default 1; Q9, decided, E95), absence having been established as §2.4 requires; after `reconciled_partial` only the human's answer to `rollout_partial` (options `retry`, `teardown`, `abandon`) does. **A partial retry authorizes only the bounded remaining effects** (AR B03, E112): the decision's preview names the reconciled state and the effects the retry will perform (the cleanup of the earlier attempt's resources and the start of the new generation); its dependency manifest (D1 §9.7, A.8) binds the operation, attempt, environment and lease generations, the configuration, the qualification, the resource identities and the observations from which those effects were derived; a change to any of them stales the preview (BS §6 correction 22), and a retry never replays the original stop and start sequence against a different state. An ambiguous attempt is never retried.
- **Teardown** of the environment (§4.6).
- **Abandon:** the operation ends `failed` by the human's answer; the authorization stays consumed; the lease is released by §4.7; a later deployment is a new request and a new authorization.
- **Roll back to the last verified:** not built in M4 (Q8, decided, E95). For a disposable Alpha environment, teardown and a new authorized deployment cover it, and they are not a tested production recovery plan; F §7.7's rollback ("selects a previously approved release and verifies recovery") is Live's, with D5.

**4.5 Concurrency** (O4). **Two authorizations for one environment:** issuance supersedes an earlier `issued` one of the same candidate and environment (as built); a repeated request for a pending one coalesces (§4.1); authorizations of different candidates coexist, and each deploy work item waits for the environment lease, shown as the hold `environment_busy`. **A new candidate authorized while an earlier one is deploying:** the deploying operation continues under its consumed authorization; the new work waits for the lease. If the earlier candidate is superseded before its attempt's effect, the precondition fails and nothing is deployed; if after, the deployment completes and is verified as an environment fact (`last_verified`, J5), and `alpha_complete` for the superseded candidate is refused (D3 Q9), so it never becomes Alpha Deployed. **A deploy while the observation job runs:** reads never take the lease. Each observation carries its read interval, the expected-state revision and the environment generation it compared against (§6.2; AR N01); one made while an operation of the environment is non-terminal compares the target with the attempt's frozen `prior` and `next`, and a state between them is recorded as observed, never as out of band, as D3 X1 never reports the engine's own registry write as out of band; a comparison a newer generation has made stale is retried or kept as history, never installed as current drift. **Checks:** environment-bound executions run under D3's `max_concurrent_checks` and D2's envelope, like any check, with the capacity §4.7 reserves.

**A newer deployment overtaking an older one's verification** (RV2; J9; AR B05, E114). The lease makes this unusual, not impossible: a preempting teardown, recovery, an out-of-band change, or a callback delayed past any of them can leave an older operation's verification or completion arriving after the environment has moved on. So every write that speaks for the environment checks, in its own transaction, the **environment-wide current generation**, `environments.current_generation`, set in the transaction of each attempt of any operation of the environment whose effect may reach the target, **and, for verification, the deciding round** (§5.3). A verification row whose generation is not current is still recorded with its computed outcome, but with `invalidated_at` and `invalidated_reason` `generation_superseded` in the same transaction; a row of a round that no longer decides is likewise recorded with `round_superseded`; `last_verified` is written only from a row whose generation is current and whose round decides at that write; `attempted` only by the attempt whose generation is current; and `alpha_complete` is not satisfied by a row whose generation is not current at the evaluation (`DEPLOY_GENERATION_SUPERSEDED`) or whose round does not decide. Obsolete evidence is kept and shown as history, never deleted and never counted.

**4.6 Teardown.** Operation kind `teardown`, by the operator's command (`surety env teardown <env>`, `POST /v1/projects/:p/environments/:e/teardown`), no gate: it removes only what the engine created for that environment. It is intended, attempted, probed and finalized as a deploy is, with its own attempt intent (the exact resources it may stop and remove) and capability. **Ownership is positive or nothing is touched:** a unit is the engine's to stop only if its name is in a frozen attempt intent of this environment in this store **and** the service manager reports for it the domain cgroup the engine recorded; a cgroup, socket or directory only if the store recorded it for this environment. A unit carrying the environment's prefix that no intent names, or whose cgroup differs, is listed and left alone, and recorded as out of band (§6.3) for the operator to deal with by hand. The same holds after the store is restored from a backup: a unit the restored store cannot account for is listed, never adopted and never cleaned by prefix, and it blocks deployment as §9.2 says. **What the teardown records is not the environment's condition.** The teardown's attempt follows §2.4's teardown column: `applied` only after closure and observed removal of every unit, populated domain cgroup, link socket and runtime directory it covers; owned resources that survive make it `partial`; an unowned or uncertain resource makes it `conflicting`; unread state makes it `unknown`. Its `cleanup` record, kept on `attempted`, lists every resource it removed and every resource it left, with the reason. **The teardown never writes `observed`:** the condition comes only from the next read (§6.2); an unowned unit left running keeps the out-of-band observation open and the condition `degraded`, or `unknown` if it cannot be read. The record keeps `last_verified` as history. An ordinary teardown waits for the environment lease.

**Preempting teardown** (RV4; AR B06, E115). A deploy whose attempt stays `ambiguous` (`conflicting` or `unknown`, §2.4) keeps the lease, and so does a confirmed deploy waiting in verification; a teardown that waited for either could wait for ever. So the operator can preempt both, through the blocker's `teardown` option or `surety env teardown <env> --preempt`: (1) an in-flight adapter call of the preempted attempt is cancelled and awaited, and quiescence is established as §2.4 requires, or the teardown's own attempt is `ambiguous` and nothing is interleaved; (2) in one transaction, before any host call, the launch state of every non-terminal attempt of the environment is closed, so no launcher can be authorized again (this needs only the store and always succeeds), the lease passes to the teardown with a new generation, pending verification executions are cancelled, and an open verification round is recorded `unknown` naming them; (3) the positively owned resources are terminated as above, each by D2 §3.2's closure, `cgroup.kill` written only to a recorded domain cgroup; (4) the teardown is reconciled. The preempted deploy becomes the teardown's `linked_prior` and is `superseded` (D1 A.5); its attempt is kept as it was, never relabelled succeeded or absent. If the service manager cannot be read, step 2 still holds, the teardown's attempt is `ambiguous`, nothing of uncertain ownership is ever stopped, and the environment shows `unknown` until a read succeeds.

**4.7 Bounded orchestration and the lease's release** (AR B06, E115). Holding the lease through verification is only safe if every path out of an operation ends.

**The deadline.** Each deploy operation has a durable **orchestration deadline**, recorded at intent from `deploy_orchestration_deadline` (A.7; its value is set by the M4 build spec, with Sean's approval), and a durable orchestration stage (`effect`, `verification`, `completion`, `ended`), both independent of the effect's success. The deadline bounds admission waiting, verification registration, identity reads and infrastructure retries; it survives a restart, and no tick or retry renews it. Reaching it records the verification `unknown` with the identities of the missing executions or resources (`missing`); it never synthesizes a check result and never claims a termination it has not observed (D3's rule that an unknown termination yields no result stands). Reached before the effect, it is a pre-effect refusal: the operation ends `failed` with nothing applied.

**Every way out releases the lease by an explicit rule.** The lease is released only once the operation's outstanding effects are quiescent (§2.4) and the ingress it opened is closed (no service link of its check executions remains open). By way out:
- **refused before the effect** (a failed precondition, admission not granted by the deadline): released at once, nothing having been issued;
- **reconciled failure** (`absent` not retried, `partial` abandoned): released after quiescence;
- **`conflicting` or `unknown`**: held, with the blocker of §2.4, until the human's answer or a preempting teardown;
- **verification `failed` or `unknown`, a candidate superseded meanwhile (whose queued checks D3 cancels), or a refused completion**: released; the work item waits on a blocker that names the cause and offers re-verification (a new round, §5.3), abandonment of completion, or preempting teardown, as each applies;
- **completion satisfied**: released after the completion's transaction;
- **cancellation by a preempting teardown**: passed to the teardown (§4.6).

A domain or check execution whose termination is unknown keeps its quarantine and its reservation after the operation has ended; it confers no authority.

**Verification capacity is reserved before deployment.** Admitting a service domain reserves, beside its own memory, the capacity for at least one serial post-deploy check under the configured envelope (one `check` domain at its profile's limits, D2 §3.7), for as long as the service runs; if the envelope cannot hold both, the attempt waits for admission within the deadline, shown as D2's `resource_envelope` hold, and is refused before the prior service is stopped. Recovery restores every surviving service's reservation, this one included, before it dispatches anything (§9.2). So no deployment's own reservation can make its mandatory verification impossible (CH 6: two correct guardrails must not deadlock). The cost: one fewer role run fits beside a running Alpha service than Q6's figures alone suggest (E115).

## 5. Verification by observation

**5.1 The environment-bound check** (V1; D3 §5 X3, completed). A check definition of kind `post_deploy_identity` or `post_deploy_behavior` with `requires: ["environment", "artifact_digest"]` and `gate_kinds` including `alpha_complete`, written by the Verifier through the protected path like any check (D3 §1). Such checks are **release-required obligations** (D1 §9.1): in the `alpha_complete` scope regardless of delivered requirements. They run only from the trigger `deployment_verification`; from any other trigger they record `environment_unbound`, as D3 built. Registration freezes, on `check_executions.deployment` (reserved by `0012`): `{operation, attempt, deployment_generation, round}` (§5.3), with `environment` and `artifact_digest`; the result row carries the same binding, and D1 §9.2 step 2 matches it (`D4-V01`). **The check tree holds only the protected inputs, no candidate source** (D3 X3): the source projection is empty, and the check judges the running service from outside. **The check's reach** is the environment's targets and nothing else: for `local_service` through the service link (§5.2), for a public target through D2 §2.4's proxy with exactly the target hosts as its egress list (J8). **Secrets:** only references the configuration allows for checks and the definition names (§7). An execution against a service whose supervision is `unknown` is refused, not run: `redaction_unavailable` (§7.3). Everything else of the `check` profile, and every rule of D3 §2.6 on what is established, applies unchanged: an environment-bound check's verdict is its own process's exit, judged by the engine's observation.

**5.2 The service link and the operator relay** (J8, E118; Q7, decided, E95; AR N04). The `local_service` target listens only inside its own network namespace (§9.2); it is on no host interface. A check reaches it through an engine-brokered link built as D2 §2.4 builds egress: the engine binds a per-domain unix socket into the check's sandbox, the check's domain init forwards `127.0.0.1:<port>` to it, and the engine relays each connection to the socket of the service domain of **the generation frozen on the execution**, and to nothing else. The check's environment names the address (`SURETY_TARGET_<NAME>=http://127.0.0.1:<port>`). If that generation is no longer running, the relay refuses; **a tunnel already open when that generation's domain terminates is closed, and a reconnection is never retargeted to another generation**, so a check bound to attempt N can never be answered by attempt N+1's service. **The link carries application data only:** it is not a control endpoint, the service's replies are untrusted input to the check, and a reply grants no reverse connection and no control capability; the init's control channel (§9.2) is a separate connection neither the application nor a check can reach. The relay has finite limits (`service_link_connect_timeout`, `service_link_tunnel_max_seconds`, `service_link_tunnels_max`, `service_link_buffer_max_bytes`); every connection, accepted or refused, is written to the execution's `service_link_log` record, bound to the execution, round, operation, attempt, generation and application instance, through the redactor. D2's proxy, and M215's egress restrictions on it, are unchanged. The link does not inspect content.

**The operator relay.** On Sean's command (`surety env open <env>`, `POST …/environments/:e/relay`) the engine opens a per-environment relay on `127.0.0.1:<port>` to the current generation's service, with the link's limits and its generation binding. It is closed by default; it closes on command (`DELETE …/relay`), at teardown, and when that generation's domain ends; a port already in use is refused without touching its owner. While open it exposes the application to other local users and to browser-originated requests (§11 class C); it exposes no engine token and no control endpoint. The link and the relay to a service whose supervision is `unknown` are refused (`redaction_unavailable`, §7.3).

**5.3 Verification rounds and the verification row** (V2; D1 §9.6, A.3; J7; AR B05, E114). For operation O, attempt N, generation g, environment E:

1. **The round, registered before any read.** A verification request (the finalizer's first, §4.2, or the operator's `POST …/operations/:o/verify`) records, in its initiating transaction, a durable **round** k of O's attempt N, numbered monotonically, which freezes the candidate and source mapping, O, N, g, the configuration identity, the effective protected version and the **required check set** (every required check of kinds `post_deploy_identity` and `post_deploy_behavior` in the `alpha_complete` scope for the candidate and O), and the adapter qualification current at its start; in the same transaction it marks the dependent `alpha_complete` evaluations stale. **The newest registered round decides**, whatever order rounds complete in; while it is open, interrupted, cancelled or quarantined, no earlier round's `verified` row satisfies completion. Earlier rows and the environment's `last_verified` stay visible as history.
2. **First identity read** (`verify`, §3.4) at t0, naming round k: every required target must match the frozen digest at generation g, with the original application instance recorded at launch; the service's supervision must be `attached` (§9.2).
3. **Registration** of the round's required checks, trigger `(deployment_verification, O:N, k)`, bound as §5.1 with the round.
4. **Execution** by D3's runner; registration decides (D3 L7).
5. **Second identity read** at t1, after the last required execution's result is recorded, naming round k: every target must match again, with the same original instance as at t0. The two reads bracket the checks within one durably bound round, so the behaviour the checks observed belongs to the bytes the reads identified, and a restart, a byte change or another generation between them is caught (J7). The bracket is not continuous attestation of execution between the reads (§11 class C).
6. **The row:** `deployment_verifications` with round k, O, N, g, E, the target set, digest, mapping, configuration identity, effective protected version, both identity reads per target (`identity_reads`), `behavioral_results` (the deciding `check_results` of every required post-deploy check), `computed_at`, `outcome`, and `missing`:
   - `verified` iff both reads match on every required target with the original instance throughout, every required post-deploy check is `passed` by D1 §9.2 with L4 and L7 at these bindings and this round, at least one of them is of kind `post_deploy_behavior`, no out-of-band observation of E falls between t0 and t1, the service's supervision was `attached` throughout, and the adapter qualification was current at the round's start and is current at its finalization;
   - `failed` iff some read `differs`, the instance changed, or some required check is `failed`: evidence that this deployment is not the authorized one or does not behave;
   - `unknown` otherwise: some read unread; some check `skipped`, `missing` or `stale` after `check_infra_retries_max`, or not run (`redaction_unavailable`); supervision `unknown` (E110); the qualification lapsed before finalization, so that a fresh qualified round is needed; or the orchestration deadline reached (§4.7). `missing` names the absent executions, reads or resources. Absent evidence is never read as failure or as success.
7. **Supersession and recovery.** A change to the round's required check set or to the effective protected version supersedes round k: a fresh round, with fresh bracketing reads and registrations, is needed, and no read or result of round k is ever relabelled into it. Recovery preserves the bounded retry accounting of round k's executions (D3's `check_infra_retries_max`, a restart resetting nothing) and records a new deciding round when the bracket must restart. Under E110 a restart leaves the service's supervision `unknown`, so no recovered round can be `verified` on it.
8. **Effects**, in one transaction that checks both the environment's current generation (§4.5) and that round k decides: `environment.verified`; `verified` writes the environment's `last_verified` `{candidate, artifact_digest, config_identity, generation, round, at, verification}` (J5); `failed` and `unknown` write `attempted.outcome` `verification_failed` or `verification_unknown`. A row that no longer decides, or whose generation is no longer current, is recorded invalidated (§4.5). Any later attempt of O invalidates every earlier row of O (`later_attempt`, D1 §3.4). The operator may ask to verify the current attempt again: that is a new round (item 1), and the rows of earlier rounds stay visible beside it (D3 §2.6's history rule).

**5.4 What "verified" can never mean** (V3; F §3.7). Not tests passing on the candidate, however many: workspace checks are inputs to `alpha_authorize`, never to `alpha_complete`'s verification. Not the adapter's `issued` or a confirmed effect: §2.3, §4.2. Not the application's claim about itself: a `post_deploy_identity` check that asks the service its version can be required and can fail the verification, but no outcome is `verified` without the engine's own identity reads (`D4-V05`). Not an observation: the observation job's `healthy` is a condition, never a verification (§6.2). **What these mechanisms do not make true** (RV6). Sealing, identity reads and exit-status judgment establish what ran and what verdict a check returned. They do not make a behavioural check meaningful: a check that greps a substring of a page, or a smoke test that accepts "degraded" (Switchboard's deploy verifier and smoke script, CH's history), passes under every mechanism here. Whether a required post-deploy check tests the behaviour it covers is the Verifier's construction and the Reviewer's assessment (F §4.1), as D3 §6 class C says of every check, and §11 class C repeats it. What D4 does exclude from that history is the deployment of a working checkout one commit past the tag: the artifact is sealed from the object store at the candidate's revision.

**5.5 Completion and Alpha Deployed** (X3; F §3.3; D1 §9.6). `alpha_complete` is evaluated with the candidate and O: D1 §9.6's requirements; the verification row being of the deciding round of O's current attempt, with outcome `verified` and its generation the environment's current one (§4.5, J9); and D3 Q9's refusal of a superseded candidate. **The evaluation does not trust a stored `verified` label** (AR B05): it re-reads the dependencies and evidence the row rests on as they are now (the round's bindings, the deciding results under the effective protected version, the integrity of their evidence, the qualification). Satisfied: in the evaluation's transaction, the candidate `developing → alpha_deployed` (`candidate.advanced`) and the `deploy` work item `complete` (D1 §4.3: an operation-backed kind completes only when its operation is `succeeded`, and here also when its completion gate is satisfied). Not satisfied: the reasons name the missing, pending, unknown or failed verification (`DEPLOY_VERIFICATION_MISSING`, `…_PENDING` for a newer round still open, `…_UNKNOWN`, `…_FAILED`) and the pending executions by D3 L7. **M4 writes no `releases` row**: Alpha has no delivery commit, publication or promotion record; `releases` stays reserved for D5, and `alpha_deployed` is the candidate fact, `last_verified` the environment fact.

## 6. Environments and observation

**6.1 The record** (N1; F §3.6; D1 §3.5). One `environment_records` row per environment, three facts never merged: **`last_verified`**, written only from a `verified` row whose generation is current and whose round decides at the write (J5, §4.5) and never erased; **`attempted`**, the latest operation and attempt with its outcome; **`observed`**, the current observation with `condition`, `detail`, `observed_at`, `source`, `freshness` and `expires_at`. The environment read (`GET /v1/projects/:p/environments/:e`) shows all three; the configuration version and identity, and the configuration and secret version the running service was launched with, with `rotation_pending_replacement` when they differ (§3.2; E116); the current generation; the running service's supervision (`attached` or `unknown`, §9.2) and any `redaction_unavailable` condition; any open or acknowledged out-of-band observation; and the operation in flight. `freshness` is computed at the read from `observed_at` and `observation_freshness_bound` (as built, `0006`): `stale` past half the bound, `expired` past it; **an expired or `unknown` observation is shown as such and is never displayed, returned or used as `healthy`** (D1-28).

**Reads are stored reads** (AR N02, E118; D1 §11.3, SEAM §91). The environment and logs routes return stored snapshots and existing screened records, with their source timestamps. Reading a route never calls the adapter, never writes a record and never refreshes an observation's age. New observations come only from the observation job (§6.2); new log records only from the collection command (`POST /v1/projects/:p/environments/:e/logs`, `surety env logs --collect`), a bounded adapter `logs` read; a log not yet collected is reported missing or pending, never fetched by the read.

**6.2 The observation job** (D1 §8.1 step 5). One `observation_jobs` row per configured environment, `cadence_s` from `observation_cadence` (default 30 s). Each due job makes one bounded `status` read and, every `identity_observation_every` observations (default 10), one `verify` read, and records the result as a transition (the first writer of observations other than SEAM §91's fixture), appending `observation_history`. **Each observation carries its read interval, the expected-state revision and the environment generation it compared against** (AR N01); a comparison made stale by a change the engine made meanwhile is retried, or kept as history or unread, never installed as current drift. **Condition, in this order of precedence**, per target and then for the environment:
1. a required state unread → `unknown`;
2. no application of the environment active and no unexpected active unit → `down`;
3. an unexpected active resource, or out-of-band drift open or acknowledged (§6.3) → `degraded`;
4. every expected application instance (the original one of its launch, §3.4) running with the generation the record expects and, where read, a matching identity → `healthy`;
5. anything else (some required targets active and some not) → `degraded`.

A unit whose launcher or init is active while its original application has exited is not `healthy`. An out-of-band fact stays visible beside a `down` condition. A read past its deadline, a service manager that does not answer, and a job that misses its freshness bound each yield `unknown` (`environment.observation_missed`), never the previous value; a read failure never creates an out-of-band fact.

**What an observation can claim:** at `observed_at`, the service manager reported these units in these states, and, when an identity read was made, the kernel's view of the original application instance showed this tree. **What it cannot claim:** that the service behaves (only checks observe behaviour); that it was up between observations; anything past `expires_at`; that nothing else runs on the host; that a service of `unknown` supervision is supervised.

**6.3 Out-of-band changes** (N2; J6; AR N01; by analogy with D1 §7.6). A change to an environment that no operation of the engine made: a unit of the environment stopped, started or restarted by hand (a manual restart is a new invocation whose launcher is refused, the launch being single-use, §9.2, so nothing of the application runs again); a unit carrying the environment's prefix with a generation no operation names; an identity read that differs. Detected by the observation job or by any adapter read, it records an `out_of_band_changes` row with subject kind `environment` (J6), expected and found, emits `environment.out_of_band`, and raises `out_of_band_change` with two options: **`teardown`** (a journaled teardown, §4.6) or **`acknowledge`**. The decision binds exactly the resources it names and the observation it rests on (its dependency manifest, D1 §9.7), so a change to either stales it. **Acknowledgment** records the change and leaves it in place, with a persistent marker that stays unresolved until an engine operation replaces what runs; until then the environment shows `degraded`, or `down` with the drift beside it. An acknowledgment changes neither the expected application identity nor verification eligibility; it adopts no deployment and establishes no termination (BS §6 correction 2 stands); and re-verification never adopts a different instance of the same attempt, so after a manual restart the redeploy is the recovery. Until the observation is dispositioned: deploy preconditions fail (§4.1), so a pending deploy waits; an in-flight attempt is reconciled as usual, but a verification whose t0 to t1 interval contains the observation is not `verified` (§5.3); `alpha_complete` carries `OUT_OF_BAND_CHANGE`. Nothing the engine reads is ever adopted as verified: there is no `adopt` for an environment, because the engine cannot know what bytes a hand deployment came from.

## 7. Secrets for deployment

**7.1 Storage and access** (S1; F §10; D1 §5.5, §17 item 5; D2 §2.5). Deployment secrets are held exactly as M2 holds the provider credential (E74, `src/invoke/keys.ts`): the operator names each as `surety serve --secret-file <ref>=<path>`, with `<ref>` in the deployment namespace (§3.2), a 0600 file outside every mount plan; the engine reads and holds the value in its resolver; the store, records, events, responses, backups and logs hold the reference only. Who can read a value: the engine process, the service or check process it is delivered to, and, outside every domain, the operator's own uid (D2 §8 class C). A configuration names references in two places: `secrets`, a map from an environment variable of the service to a reference, and `check_secrets`, the references environment-bound checks of this environment may receive.

**7.2 Delivery.** **To the service:** never as a unit property, a command-line argument or a file under the service manager's control, since transient unit definitions are written under the user's runtime directory and are readable through `systemctl show`. The value travels only on the launch authorization's reply (§9.2), from the engine to the service's domain init over the engine's launch socket, and the init places exactly the configuration's variables in the service process's environment. **To an environment-bound check:** a definition may name references in a `secrets` field (a governed definition field, D3 §1.3, added here); at launch the engine delivers, the same way, only those references that the definition names **and** the environment's `check_secrets` allows; any other reference refuses the launch (`secret_not_allowed`, a not-run reason). A workspace check never receives one (D3 §2.3, unchanged). **To an agent:** never. No role's grant names a deployment secret, the context package carries no secret-marked configuration value, and the Release Operator is not an agent (§8).

**7.3 Never in a record, and withheld when it cannot be screened** (AR B07, E116). Every resolved deployment secret is registered with the redactor and the secret screen (D1 §14.2, D2 §2.5) for as long as the engine holds it, so the service's logs, check output and service-link logs are redacted before disk and screened before publication; a screen hit refuses that publication and raises the critical finding as for a role.

**Raw output stays inside the domain until it is screened.** The init captures the service's output in its own protected, unswappable volatile memory (D2 §2.5), bounded by `service_log_max_bytes`; none of it goes to the unit's standard output or error, the service manager's journal, or any other persistent sink. Fields the engine reads from the host about the service's processes (arguments, error details) are untrusted output for publication and pass the same screen before they are recorded.

**After an engine restart, a surviving service's output is withheld.** The restarted engine holds only the secrets it read at its own start, which may no longer be the ones the service was given (§3.2), and it cannot recover from the service which they were: there is no reattachment in M4 (E110). So until that service is replaced or torn down, its logs, its service link and operator relay, and every check against it are refused with `redaction_unavailable`; no old capture and no new output is published under a redactor that knows only the newly read secrets; and the records of reads of that service keep match results, hashes and numeric identifiers only, withholding the free-form fields the host returned, which cannot bypass the refusal. Recovering a surviving service's old secret versions over an authenticated channel, to screen its output, is D5's with reattachment (§11 class B).

**7.4 What a leaked deployment secret reaches** (S2), in D2 §8's form, class C. The deployed service is agent-written code, and it holds every secret its configuration names: it can send one to any host its egress allows (none in M4), write it into a response a check receives (redacted and screened, registered forms only), or encode it so no detector recognizes it. A secret given to an environment-bound check is held by Verifier-written code in the same way. Therefore **an Alpha environment should hold only Alpha-scoped, disposable secrets** that authorize nothing outside that environment; the recommendation for the first target is an engine-independent random token the operator generates for the reference service, and none of Sean's real credentials. **Revocation:** rotate the value at its issuer, replace the file and restart the engine; the current version becomes `secrets_changed` and deploys stop until the owner writes a new version with the new digests (§3.2); every authorization bound to the old identity then fails its precondition, and a new request redeploys with the new value. The old value is not erased from a running service until that redeploy or a teardown; until then the environment read reports `rotation_pending_replacement`, and, the rotation having taken an engine restart, that service's output is withheld (§7.3).

## 8. The Release Operator

**8.1 Engine code, not an agent** (R1; approved with D4's recommendations, E95). F §4.1 gives the Release Operator "export, release mapping, publication, deployment, recovery records" through "scoped capabilities", and forbids it to "waive checks; alter code; supply its own independent verdict". In Alpha deployment every step is fixed by the authorization and the configuration: seal an artifact, consume an authorization, call an adapter, read back, register rounds and checks, compute a verification. None needs judgment, and judgment is what the role may not supply. **The Release Operator is an engine component, `src/deploy/release-operator.ts`, with no model**, for five reasons: (1) it would otherwise hold deploy authority and target credentials inside an agent's context, which the predecessors' most reused rule forbids ("the model never ... holds a deploy credential", recommendation R8 of `sdlc-review-claude.md`); (2) an agent asked to perform effects and adversarial-looking probes is refused inconsistently by its own safeguards (E82, E86), and anything of that kind is the engine's to run; (3) the engine already performs every other external effect (D1 §1.1) and journals it; (4) determinism: an operation's attempts are comparable only if the same code makes them; (5) cost: a deployment spends nothing. The `Role` value `release_operator` stays in D1's enumeration, reserved; no run of it is dispatched in M4. **Alternative:** an agent role with a tool that calls the adapter; rejected for (1) to (4). If D5's export or recovery planning needs authored content (release notes, a recovery plan's prose), that is a run of an existing authoring role whose output the engine validates, not a Release Operator agent.

**8.2 Its capabilities** (R2; F §4.2 least privilege). The Release Operator may: seal artifacts; record deploy and teardown operations, their attempts and their attempt intents; consume an issued authorization; mint and present the capability of §2.2; take and release the environment lease (§4.7); register verification rounds and their `deployment_verification` executions; write identity reads and verification rows; write the environment record's `attempted` and, from a `verified` row of the deciding round, `last_verified`. It may not: issue an authorization (only a satisfied evaluation does); write a check result or a check state (D1 §17 item 8); evaluate `alpha_complete` other than through the gate function; advance a candidate other than through that evaluation; write configuration; or call an adapter effect without a capability. Its scope is one authorization at a time: the capability names one operation's attempt, and every adapter effect checks it (§2.2). **An attempt outside its scope** (another environment, another digest, a unit name the attempt intent does not hold, a stale attempt, generation or lease) is refused before any host call and recorded (`deploy.capability_refused`, `D4-A05`). Since the Release Operator is engine code, such an attempt can only come from a defect or a forged internal call; the refusal is the guard that makes a defect visible instead of effective. No role's result schema has a field that requests a deployment, and no role grant holds a capability (`D4-R01`).

## 9. The first target: `local_service`

**9.1 The choice** (T1; Q2, decided, E95). **A disposable service on the engine's own host, run by the user's service manager in a D2 sandbox domain of a new profile `service`, reachable only through the engine.** It is **real**: a process outside the engine's process tree, owned by a service manager the engine does not control, which outlives an engine crash, can be stopped or restarted by hand, and must be read back to be known; so exactly-once under a kill, reconcile from the target's state, out-of-band detection and teardown are all exercised for real. It is **minimal**: no network, no remote credentials, no container runtime, no new dependency (the service manager is already H3's). It is **reversible and safe**: the engine creates every unit under a name derived from a hash of its home and the environment id (§9.3), never stops a name it did not derive and record, binds no host port, and removes everything by teardown. Sean's sessions on the workstation and his staging containers on `mini-hp01` are untouched by construction: the adapter never invokes `docker` or the system manager, never stops a unit by pattern, and never runs on `mini-hp01`. Persistent user units and their ongoing memory reservations are real operational costs, even with no cloud bill.

**Alternatives considered.** (b) **A dedicated user or user unit on `mini-hp01` over Tailscale:** a real remote, which would also exercise network partitions and remote credentials; rejected for M4 because the engine would hold an SSH credential (§7's whole problem, a step earlier), Tailscale's check mode can stop on a browser login Sean must open (E69), and the host runs his staging containers under a root Docker daemon. It is the natural second adapter, through this contract, in D5 or later. (c) **A container on either host:** Docker's daemon makes its caller root-equivalent (D2 §2.2); a rootless runtime is neither installed nor qualified here, and its isolation would need D2's guarantees re-established (D3 §2.8 says the same of the `container` runner class). (d) **A process inside the engine's own incarnation scope:** not real, because it dies with the engine and recovery would kill it (D2 §3.3).

**9.2 The `service` profile and its domain.** A service domain is a D2 execution domain bound to a **deployment attempt** instead of an invocation or a check execution (J2). **Mount plan**, validated as D2 §2.3 validates a role's: `/usr`, `/bin`, `/lib`, `/lib64` and the enumerated `/etc` read-only; the configured runtime (for the reference project, the engine's own `node`, pinned by path and hash) read-only; **the sealed artifact at `/surety/app`, read-only, its pathname immutable with its ancestors for the domain's life** (D3 L6's property); a volatile filesystem for `/surety/home`, `/tmp` and `/surety/state`, bounded by `service_writable_bytes` and `service_writable_inodes` and lost when the domain ends (so no deployment inherits state, X2); private `/proc`, minimal `/dev`, private `/dev/shm`. Absent: the engine home, every workspace and repository, the context package, any git metadata, any backend, the operator's home. **Network:** a namespace with only its loopback; the service listens on its configured port there; the domain init forwards from an engine-bound unix socket to that port, so the service link and the operator relay (§5.2) are its only ingress; egress only through D2's proxy, to hosts the configuration names, and in M4 to none (§10 X2). **Limits:** `service_memory_max`, `service_tasks_max`, swap 0, the writable bounds, and `service_log_max_bytes` for the init's rolling capture of the service's output, held in its protected volatile memory (§7.3) (Q6, decided, E95). A service domain is admitted by D2 §3.7's envelope like any domain, holding its memory reservation, and the capacity reserved for one post-deploy check (§4.7), for as long as it runs.

**Placement and launch.** The adapter creates the unit with `systemd-run --user`, as a transient service named for the generation, with `Delegate=yes`, the limits as unit properties, **automatic restart disabled**, standard output and error carrying nothing of the application's (§7.3), and as its command the engine's launcher, which is D2's launcher started with the `service` profile. The unit's main process is therefore the launcher, never the application; §3.4 binds the application process. The unit's cgroup is the domain's cgroup, outside the engine's incarnation scope, which is why the service survives the engine. Before authorizing a launch the engine reads the limits back from the cgroup files (as D2 §3.7 and the slice-13 brief require). The launcher builds the sandbox, places itself, and asks for **launch authorization** over the engine's launch socket (`$SURETY_HOME/run/`), presenting the domain, the deployment attempt, the incarnation, the environment lease generation and, having forked the domain init and before the init runs anything of the application's, the init's host pid and start time (§3.4 step 2); the engine grants it in one transaction only if all four are current, the attempt is `started`, and the attempt's launch state is `authorizable` (D2 §3.2 with the attempt in the invocation's place). The reply carries the service's secret values (§7.2). Without the grant the launcher exits having run nothing. **A launch is single-use** (AR B01, E110): the launch state moves `authorizable → authorized` once and never back (as built, `0008`), so a launcher started again under the same unit, by the manager or by hand, is refused and runs nothing; nothing reruns the application under a spent grant.

**The domain's life** (J2 with AR B01's variant, E110, E118). After launch the service does not depend on the engine. The init records the original application's identity (§3.4) and, when the application ends, its terminal exit, in trusted, bounded memory for the domain's life, and never substitutes a descendant or another process for it. When the application exits, the init records the exit before draining its output, closes ingress, and terminates the remaining descendants within the domain's closure (D2 §3.2); it never restarts the application. **Natural exit, a refused setup and a failed `exec` are legal endings** of a service domain: it becomes `terminated`, with closure observed, from `launched` or directly from `allocated`. A termination that cannot be observed leaves it `quarantined`, and a later observed closure moves it `quarantined → terminated`. Otherwise a service domain ends only through a teardown or the stop step of a later deploy of the same environment, each terminating it with D2 §3.2's closure (state `closed`, `cgroup.kill` on the domain's cgroup only, observed `populated 0`); only an observed termination is `terminated`.

**Supervision, and no reattachment in M4** (E110). The init's control channel to the engine is the connection its launcher opened to the launch socket at launch, distinct from the data link of §5.2 and unreachable by application and check code (D2 §2.3). It is never reopened. While that connection stands, in the current incarnation, the domain's **supervision** is `attached`; once it is lost, above all at an engine restart, supervision is `unknown` for the rest of the domain's life. A lost channel is never a stop: a service of unknown supervision keeps running and is still read through the service manager and `/proc` (§3.4, §6.2), but no verification passes on it (§5.3), and its logs, link, relay and checks are refused `redaction_unavailable` (§7.3) until it is redeployed or torn down. Authenticated reattachment, in which a new incarnation proves it speaks to the same domain, init and application and recovers the original identity and exit state, is deferred to D5 with Live (§11 class B).

**Recovery** (J2; AR B01 part 3, E110). Correction J2 exempts service domains from D2 §3.3's restart closure: recovery observes them and never closes or kills them, while role and check domains are closed exactly as before (M112 to M118 and M216 unchanged). At start, **before it accepts any launch request**, the engine closes the launch state of every attempt of an earlier incarnation, so a request from a previous incarnation is refused even before recovery has visited its row. **Before admitting any new domain**, recovery accounts for the reservation of every surviving or uncertain service domain (its own and the check capacity of §4.7), from its recorded domain and a read of its cgroup. A unit or domain whose ownership is unknown, or which a restored store cannot account for (a unit carrying the prefix with no recorded attempt intent, or with a different cgroup), blocks deployment to its environment, and admission wherever its reservation cannot be accounted; it is never adopted and never stopped automatically. Inspection, and recovery by hand of exactly that resource, stay available.

**9.3 The adapter against the contract.** Appendix B gives the interface; here, what `local_service` does with each call.
- **Names.** Every unit is `surety-<h>-<env>-g<n>.service`, where `<h>` is the first 12 hex characters of SHA-256 of `$SURETY_HOME` (D2 §3.1's scope naming) and `<env>` the environment id; every name is computed by the engine, recorded in an attempt's frozen intent before the unit exists, and validated character by character before any host call. No effect call takes a pattern; the inventory (§2.4) lists, read-only, the units whose names carry the environment's exact prefix.
- **`deploy`:** rehash nothing (the precondition did); stop the attempt intent's `prior` unit if any and observe its domain terminated; reset its failed state; create g's unit as §9.2 says; wait, within the deadline, for the unit to be active and for the launch authorization the engine granted; return `issued` or `uncertain`. One generation runs at a time, so a read of "the environment" is never ambiguous about which generation answers; Alpha accepts the gap between stop and start.
- **`teardown`:** stop and reset every unit its attempt intent names, observe each domain terminated, remove the environment's recorded link sockets and runtime directory, and leave whatever is not positively owned (§4.6).
- **`reconcile`, `status`:** take §2.4's inventory: the store's recorded resources and every unit carrying the prefix, in any state (`ActiveState`, `SubState`, `Result`, `InvocationID`, `MainPID`, `ControlGroup`), with the manager's pending jobs for them; read the engine's launch-authorization rows; and check the recorded application instance by §3.4 steps 1 to 3 (`MainPID` locates the launcher and nothing else); map by §2.4 and §6.2.
- **`verify`:** §3.4's `tree_digest`.
- **`logs`:** the init's rolling capture, collected only by the collection command (§6.1), through the redactor, as a `deployment_logs` record within `adapter_output_max_bytes`; refused `redaction_unavailable` for a service of unknown supervision. Logs are never evidence of verification.

**9.5 Safety** (E64, absolute; brief §4). Every test that deploys deploys only to an environment the test created in a home the test created, and tears it down. Destructive instruments fail closed in two halves: **the adapter** refuses any unit name not derived from its own home's hash and recorded in its store, and refuses any stop, kill or cgroup write outside a domain cgroup it recorded; **the test** reads, from the host side, that every unit it is about to touch carries its own home's prefix before it releases an instrument, and after teardown that no unit, cgroup, socket or directory with that prefix remains. The inventory's prefix listing (§2.4) is a read, never a licence: every destructive action is on a positively owned exact resource (§4.6), and a unit a restored store cannot account for is listed, never cleaned by prefix. A test that seeds a decoy (`D4-T02`) creates the decoy itself, under a name outside every Surety prefix, and asserts it untouched. No test stops, restarts or reloads the user's service manager; the unreadable case points the adapter at a missing bus address instead (§2.6). The Builder's audit list of every kill, signal, stop, remove and mount site (E64 item 2) gains every `systemctl` and `systemd-run` site; the Reviewer checks it.

**9.6 What is proved before the build, and the order of the build** (RV1; E95; AR N03). The persistent service supervisor is this design's main complexity risk, so M4's build spec opens with the **feasibility probe**'s confirmation, whose results either confirm §9.2 and §3.4 or come back to Sean as a decision before any slice starts (E95). The probe ran on 2026-10-07 with Sean's approval, with a stand-in launcher and init; the preamble lists what its log records and the limits of what that establishes. What it could not observe stays in §11 class B, each item with the qualification case or milestone test that will establish it; real-launcher recovery and the death of an engine incarnation scope need sandbox evidence (`D4-O03`, `D4-T07`), and behaviour across a restart of the user manager or the host is not claimed unless separately exercised. No destructive manager-restart probe is added. Then the slices follow the journey and nothing else: **deploy → identify independently → verify behaviourally → crash and recover → tear down**; observation, out-of-band handling and the operator relay follow once the journey passes. Cloud and remote adapters, production telemetry, the Mechanic and the eBPF observer stay outside M4.

## 11. What D4 does not claim

In the form of `docs/acceptance/reports/M2-not-claimed.md`: class A is outside the threat model, class B is real behaviour no test has yet established or that M4 does not build, class C is a limitation accepted by design.

**Class A.** As D2 §8 class A, a compromised operator account included. A post-deploy check the Verifier wrote to pass whatever the service does (D3 §6). A change to the service manager's state by the operator's own account while the engine is down, beyond what the next read shows.

**Class B, not yet established** (AR N03): each names the qualification case or milestone test that will establish it.
- D2's launcher, domain init and constructed root (`pivot_root`) running in a service unit; launch authorization over the engine's socket; the init's launch-time report agreeing with the host read; the original application identity retained against pid reuse: qualification case `deploy_read_back`, `D4-T01`, `D4-I05`.
- The single-use launch under a manual or manager restart: case `out_of_band`, `D4-T06`.
- A launcher creating child cgroups under `Delegate=yes`; the immutable-pathname property for the `service` profile; the isolation of the init's control channel from application and check code: `D4-T01`, `D4-V02`.
- The unit surviving the death of an engine incarnation scope (the probe's creator ran in `/init.scope`); recovery with a real service domain at an engine restart (launch authority closed first, supervision `unknown`, reservations accounted): `D4-O03` in the sandbox lane, `D4-T07`, `D4-T08`, `D4-T09`.
- The qualification's host time and the headroom of Q6's figures, which are starting caps, not measurements: the first qualification run (`D4-A06`) and the sandbox lane measure what they take.
- Behaviour across a restart of the user's service manager or of the host: not attempted and not claimed unless separately exercised, beyond that the units are gone and the next observation says `down` or `unknown`.

Established by the probes on this host, with stand-ins only and with the preamble's limits: a transient user service with `Delegate=yes` and its limits, outside its creator's cgroup; survival of its creator's SIGKILL; a new `InvocationID` on restart; observed removal on stop; the host-side reads of §3.4.

**Class B, not built in M4.** **Reattachment after an engine restart:** a surviving service's supervision is `unknown` until it is redeployed or torn down, and no authenticated recovery of its supervision, original identity or exit state is built (E110); with it, recovery of the old secret versions that would let a restarted engine screen that service's output (E116); both are D5's, with Live. The build execution (§3.1, Q4): a project that must be compiled or have dependencies installed is not supported. Any adapter but `local_service`, and any remote target: network partitions, remote credentials, a target the engine reaches over a network. Beta and Live (Q1). Rollback (Q8); teardown and a new authorized deployment are not a tested production recovery plan. Enduring effects of deleted modules on a stateful target (X2).

**Class C.** **Re-execution:** an application that re-executes the same runtime with identical arguments is not distinguished by the identity read's fields (§3.4). **Identity:** the read establishes what was mounted and started, not that the running code never loads code it wrote or fetched at run time (§3.4); the two bracketing reads of a round are not continuous attestation of execution between them (J7). **Check quality** (RV6): every mechanism here establishes what ran and the verdict a check returned, never that a post-deploy check tests the right behaviour (D3 §6 class C). **Secrets:** the deployed service and any check given a secret hold it and can leak it by any channel open to them; the screen detects registered forms only (§7.4); a same-uid process outside every domain can read the secret files and the HMAC key. After an engine restart a surviving service's output is withheld, not screened (§7.3). **Artifacts:** the sealed copy in the engine home can be changed by a same-uid process; a rehash at every deploy detects it then, not before. **Availability:** one generation runs at a time, so each deploy has a gap; an engine crash during verification ends that round `unknown`, and the operator redeploys (E110); the observation job samples, so the service can be down between observations without a record of it; `healthy` describes liveness and identity, never correct behaviour. **Freshness:** an observation is a fact at `observed_at` and nothing after `expires_at`. **The service link** relays bytes and does not inspect them. **The operator relay**, while open, exposes the application to other local users and to browser-originated requests on the host; it exposes no engine token or control endpoint (§5.2). **The environment** runs on the operator's own host: a service that exhausts its envelope takes its own reservation, not the host, but its reservation, one check's capacity included, reduces what role runs can be admitted while it runs.

## Appendix B. The adapter interface

The reference, in TypeScript notation; the types are A.2's. Every method is asynchronous, bounded by its deadline, and never throws for a target condition: what it cannot read it returns as unread.

```ts
interface DeploymentAdapter {
  readonly id: AdapterId; readonly version: string;
  readonly reach: 'service_link' | 'proxy';             // how environment-bound checks reach targets (J8)
  readonly identityMethod: IdentityMethod;

  deploy(cap: DeployCapability, signal: AbortSignal): Promise<EffectReceipt>;
  teardown(cap: TeardownCapability, signal: AbortSignal): Promise<EffectReceipt>;

  reconcile(op: OperationIntent, attempt: AttemptIntent, signal: AbortSignal): Promise<Reconciliation>;
  status(env: EnvRef, expect: TargetExpectation[], signal: AbortSignal): Promise<TargetStatus[]>;
  verify(env: EnvRef, expect: TargetExpectation[], signal: AbortSignal): Promise<IdentityRead[]>;
  logs(env: EnvRef, target: string, maxBytes: number, signal: AbortSignal): Promise<LogTail>; // collection only (§6.1)
}

interface Instance { invocationId: string; pid: number; startTime: number }   // §3.4
interface DeployCapability {
  environment: string; operation: string; attempt: string; generation: number;
  incarnation: string; leaseGeneration: number;
  artifact: { digest: string; sealedPath: string }; configIdentity: string; configVersion: number;
  targets: string[];                                     // from the operation's intent
  createUnits: string[];                                 // from the attempt's intent, as are prior and cleanup
  prior: { unit: string; instance: Instance }[]; cleanup: string[];
}
interface EffectReceipt { result: AdapterEffectResult; steps: { at: string; step: string; detail: string }[] } // provenance: claimed
interface InventoryEntry { resource: string; kind: 'unit' | 'cgroup' | 'socket' | 'directory'; recorded: boolean; state: string | 'unread'; pendingJob: boolean | 'unread' }
interface Reconciliation { outcome: ReconcileOutcome; complete: boolean; inventory: InventoryEntry[]; reads: TargetStatus[]; identity: IdentityRead[] }
interface TargetStatus { target: string; unit: string | null; active: boolean | 'unread'; instance: Instance | 'unread'; generation: number | 'unread'; supervision: Supervision; at: string; failure?: AdapterReadFailure }
interface IdentityRead { target: string; method: IdentityMethod; expected: string; read: string | 'unread'; match: IdentityMatch; instance: Instance | 'unread'; generation: number | 'unread'; at: string }
```

**`local_service` against it.** `reach` `service_link`; `identityMethod` `tree_digest`; host tools `systemd-run` and `systemctl`, both with `--user`, resolved to absolute paths and recorded with their versions on the qualification; the bus address from the engine's own environment (the qualification's unreadable case alone overrides it). `deploy` and `teardown` as §9.3, on exactly the capability's names; `reconcile` and `status` take §2.4's inventory (the store's recorded resources, every unit carrying the environment's exact prefix in any state, read-only, with the unit properties `ActiveState`, `SubState`, `Result`, `InvocationID`, `MainPID` and `ControlGroup` and the manager's pending jobs) and the store's launch authorizations; `verify` checks the recorded application instance and walks `/proc/<pid>/root/surety/app` as §3.4 (the unit's `MainPID` is the launcher and locates nothing else); `logs` reads the init's capture through the redactor, and refuses `redaction_unavailable` for a service of unknown supervision. It refuses configurations with persistent state, a non-empty egress list or a target count other than one in M4 (§10 X2).
