## 1. The journey, with design

D6 §1's journey with the design steps inserted, for a project whose policy is `design: both`. Steps D6 already has keep their numbers' meaning; the inserted ones are lettered.

1. to 4. **As D6 §1**, with two additions. The approved spec states the product's **targets** (`**Targets:** web, android` in its header, G3; a product decision on F §9.1's floor, Q7 decided). The Architect's module map marks each module's **surface** (`ui`, `api`, `cli`, `library`, `none`), gives each `ui` module the targets it serves and the **UI technology** for each (React Native for Android and iOS, HTML and CSS for web, and so on), and gives every interface a UI module consumes its request and response shapes and error cases (§4.1; G1). Phase 1's plan is published as D6 §5.5; its stages that touch a `ui` module are **UI stages** (§8.1).
4a. **The engine derives the interface inventory** (§4) from the approved architecture, the spec and the environment at publication: per target its technology, its **preview capability** (§5.2), its layouts, the conventions its screens must declare and the **default design requirements** (themes, layouts, asset slots and variants), which the design may narrow with the owner's approval (§5.8); and it writes a **placeholder** for every default asset slot (§6.3). `design.inventory_derived`. If the project's policy is not `off` and the module map has a `ui` module, it raises **`design_due`** (§11) asking the owner to open a Designer session. No model.
5. **Phase 1 opens with check authoring** as D6 §6.2. **Backend stages build** as D6 §6.3 (their milestones are D6 §6.4's two); **UI stages are held `design_pending`** (§8.2), visibly, with `design_due` open.
5a. **A Designer session** (§3): the owner and the role talk; the role writes tokens, flows, each target's screens, navigation and interaction states, mockups, and asset proposals, fed with the engine's fixtures (§4.4); at each save the engine runs the **design check** (§5.6) and tells the session what failed; `surety design preview` deploys the checkpoint to the **preview environment** (§5.7), where web mockups run in the owner's browser and every other target's mockups are shown inside an engine frame labelled **simulation**. Close raises **`design_approval`** consolidated with a **`spec_change`** carrying the design's proposed criteria (§7).
5b. **The owner approves** (both, one batch): `design_revisions` 1, recorded current against the spec version n+1 the batch creates (§7.4), `baseline.design_approved`; each proposed asset he did not hold becomes its slot's **effective** version, and a held one leaves the previous effective version (an approved file or the placeholder) in place (§6.4); the spec change's effect per D6 §4.5 (version n+1, the design criteria and one design human-test requirement per target registered, `check_correction` registered for the uncovered criteria). When the protected version covering the design criteria is applied, **`design_ready_at`** is set (§7.5) and the UI stages' work becomes eligible: `design.ready`, `work.dependency_met`. **Asset status takes no part in readiness**: a design whose every asset is still a placeholder is ready.
6. to 11. **As D6 §1**, with the UI stages' Builders given the approved design and its **effective asset set** in their packages (§8.4), each Builder returning where it placed each asset (**asset bindings**, §6.5), and the design checks run like any other on every candidate.
12. **Alpha** as D6 §1 step 12. No asset status is read by `alpha_authorize` (§6.7).
12a. **The design review** (§10): on `alpha_complete` the engine raises `design_due` (stage `alpha_review`); the owner opens a Designer session in review mode, browses the running Alpha through the operator relay (D4 Q7) for the web target, and the role compares it with the approved design and the engine's observations of the served files. A target M6 cannot run is reviewed **on the owner's command against a build he names**, with screenshots or recordings he supplies, labelled owner-supplied (§10.5); until then it is `not_observed`. With no design approved before build, the review produces the **first design** (§10.6). The role's verdicts are proposals; **the owner confirms them** (§10.3). Close records the review and, if there are deltas, raises a new `design_approval` with **one** spec change carrying them; approval re-verifies and rebuilds through the ordinary path (§10.3; G7).

**Human acts the design adds:** opening the Designer session (or answering `design_due` otherwise), the consolidated `design_approval` + `spec_change`, an asset-only `design_approval` when he adds or replaces a logo later (§6.4), and the review: its session (at Alpha, or `surety design review` for a native build), the confirmation of its verdicts, and its approval if it found deltas. Opening the preview is the owner's choice, not a gate.

**The next proof** (M535, the M6 journey row): one real run that carries a **web design** (native preview), a **labelled mobile simulation** (an `android` or `ios` target of the same product, `simulated_html`), and a **held-then-approved logo replacement** all the way into the built application: the held logo absent from every Builder package and check, the previous effective logo built; on approval, `asset_updated` work from the recorded bindings integrates the new file and the parity checks pass against the new `slot@version`. **No role approves anything** (E12), and the design moves nothing on F §9.1's floor: the criteria it proposes enter the spec only through the floor's spec approval.

## 2. The policy

`design` (project policy, D1 policy revision; A.7): **`off`** (default), `before_build`, `at_alpha`, `both`. The policy is target-blind: it says when design happens, not for which platform.

| Value | Before build | At Alpha |
|---|---|---|
| `off` | nothing; no inventory is derived; UI stages have D6's milestones only | nothing |
| `before_build` | inventory derived; `design_due` raised; UI stages wait on `design_ready` | nothing |
| `at_alpha` | inventory derived (it is the review's reference); no hold | `design_due` (`alpha_review`) raised on `alpha_complete`; with no approved design, the review produces the first one (§10.6) |
| `both` | as `before_build` | as `at_alpha` |

**Changing the value** is an ordinary policy change. Turning design on mid-project applies to UI stages not yet dispatched (a tightening; no `policy_widening`). Turning it off releases the holds and records the waiver on each held stage (`design.waived`): the design human-test requirements, if any were approved, stay visibly pending. A project with no `ui` module derives an inventory with no screen obligations and raises nothing; the policy is then inert, and `GET …/design` says so rather than showing an empty design as complete.

## 3. The Designer session

**3.1 A session as D6 §2, unchanged in mechanism.** A run of kind `session`, role `designer`, one capability grant, one cumulative budget, turns that are one-shot invocations with the transcript in the package, settlement before idle, save and close through the journal, idle timeout and budget exhaustion by one protocol, resume from durable records. **One open session per project** (D6 §2.7): a Designer session and a Spec Writer or Architect session never run at once on a project. **But a Designer session admits one-shot runs beside it** (G12, a correction to D6 §2.7 and `D6-S08`, decided in this draft; draft 2's question 5): Builders, Verifiers, Reviewers, check runs and the Spec Writer one-shot of §7.1 dispatch on its project while it is open, and it may open while they run, each turn admitted by the envelope as a `role` domain at `role_memory_max` like any run (D6 §6.4; K2). **Why it is safe.** D6's reason for exclusivity is that a session and a one-shot "both write the same branch" (D6 §2.7). For the Designer the write scopes are disjoint by construction: it writes only `.surety/design/` less `inventory/`, and no other role may write there (§3.3, G9); every commit, a Designer save included, is serialized on the integration lease and, when its base is behind, rebased and re-validated by D1 §7.5, which with disjoint paths cannot conflict. The Designer holds no lease between saves, and nothing a one-shot reads resolves to a Designer checkpoint: Builders read the **approved** design only (D6 §3.5's rule that no package resolves to a checkpoint; §8.4). What a one-shot can change under an open session is the Designer's *inputs* (an approved spec or architecture change re-derives the inventory), and that is caught, not prevented: the next save fails `DESIGN_INVENTORY_STALE` (§5.6 clause 1) and the role is told. I found nothing in D6 §2 or §6.4 that this exemption breaks; Spec Writer and Architect sessions keep D6-S08 unchanged, because their products are the inputs of every other role.

**3.2 Model and limits.** `model_designer` default **Opus**, as Spec Writer and Architect (E139 Q6): design is judgement and its product is read by every UI Builder. `deadline_designer` 30 m per turn (as `deadline_spec_writer`). The session's cumulative budget is `designer_session_budget_billable_tokens`, default **3,000,000** (A.7): a trial value, double the run budget, because a mockup turn writes several files, a cross-platform design repeats screens per target, and each turn re-sends the transcript and the inventory (D6 §2.2). No figure is a measurement; §13 says what M6 records.

**3.3 What the Designer may write** (D6 §2.5's rule, enforced at save by D1 §7.3 step 1, `diff_violation` refusing the save whole): **`.surety/design/` and nothing else**, minus the engine-owned `.surety/design/inventory/` (§4.4), which it may read and may not change (`DESIGN_INVENTORY_MODIFIED`). Never source, never `.surety/spec/`, `.surety/architecture/`, `.surety/adrs/`, `.surety/roadmap/`, `.surety/phases/`, `.surety/checks/` or the policy. **The converse holds too, and is the lesson of `339e116`:** no Builder, Verifier, Reviewer, Spec Writer or Architect may write `.surety/design/`; a Builder implements the design in source (copying asset files to the source paths its stage needs, §6.5), and a finding never asks a Builder for a `.surety/design/` change. An interface, target or permission the design needs that the inventory lacks is **not** the Designer's to add: it is a `requirement_conflict` or `contract_conflict` finding in the role's result (D3 X2), routed to `change_spec` or to an Architect session, and the session is told so (§4.5). The Designer may set an asset slot to `placeholder` or `proposed`, never to `approved` (§6.4), and **writes no owner verdict**: whatever it records as a verdict, a match or a delta is a proposal the owner confirms by his own act (§10.3).

**3.4 The package states what the engine reads** (E151; M442's principle). The Designer's context package carries: the role prompt (engine-authored, D2 §1.2; the SAP's five phases recast as listen, reflect, explore, **render**, document); the transcript so far; the **interface inventory** (§4) and its fixtures; the approved spec's semantic representation (statements, criteria, marks, targets) and the identity block's `users` and `non_goals`; the module map with surfaces, targets and technologies; the ADRs that name the UI technologies; the environment's runtime and start command (TPL §7); **Appendix B's design schemas verbatim, the design check's reason codes and what each means, the table of required conventions per target (§5.3), the closed criterion catalogue with the targets and technologies each kind applies to (§7.2), the mockup kinds each target's preview capability admits (§5.4), the default design requirements and the floor below which a selection may not narrow them (§5.8, §6.2), the pinned-URL rule, the configured layouts**, and the engine's notes on the last save. The package states plainly that an HTML mockup of a non-web target is a simulation and must be declared one. In review mode (§10) it adds the approved design (if any), the Alpha candidate's UI source read-only, the design checks' results on that candidate, the engine's observations of the served files, and, for an owner-invoked review, the owner's build identifier and his evidence files, screenshots as images and recordings by name only, each labelled `owner_supplied` (§10.5). Nothing else; in particular never the Spec Writer's or Architect's transcripts (D6 §3.5's rule).

**3.5 The turn result** (B.12): `{reply, artifact_changed, questions_for_owner?, done?, findings?}`, D6 B.7's session result plus `findings` (D3 X2) for an interface, target or requirement the design cannot honour.

## 4. The interface inventory

**4.1 What the spec and the Architect now state** (G1, G3; B.3 extended). **Three axes, never merged:**
- **Target** (`Target`, closed: `web`, `android`, `ios`, `macos`, `windows`, `linux`) is a product decision. The spec header gains `**Targets:**` (one or more) and, optionally, `**Cross-platform:** yes`, meaning the targets share branding and workflows and every platform-specific difference is stated (§5.3). The Spec Writer writes them; the floor approves them (**Q7 decided: targets belong in the approved spec**; the Architect chooses only the technology beneath each). Under `design` not `off`, a spec with a `ui` module and no `**Targets:**` line refuses the plan check (`SPEC_TARGETS_MISSING`, routed to `change_spec`); the engine does not assume web.
- **UI technology** (`UiTechnology`, closed: `html_css`, `three_js`, `streamlit`, `react_native`, `flutter`, `swiftui`, `compose`, `other`) is the Architect's choice beneath a target, recorded in its ADRs. Each `ui` module gains `targets: [{target, ui_technology, form_factors?}]` (`form_factors` from `phone`, `tablet` for `android` and `ios` only) and, for `android`, `ios` and `macos`, `platform_permissions: [{target, permission, why}]`. The plan check refuses a module target the spec does not list (`ARCH_TARGET_UNKNOWN`), a spec target no `ui` module serves (`ARCH_TARGET_UNCOVERED`), and a pair the admissibility table refuses (`ARCH_TECHNOLOGY_TARGET_MISMATCH`):

| UI technology | Admissible targets |
|---|---|
| `html_css`, `three_js`, `streamlit` | web |
| `react_native` | android, ios |
| `flutter` | android, ios, web, macos, windows, linux |
| `swiftui` | ios, macos |
| `compose` | android |
| `other` | any; its preview capability is never `native` |

- **Preview capability** (`PreviewCapability`: `native`, `simulated`, `none`) is the engine's, computed per module and target (§5.2), never stated by a role.

Each interface gains `consumed_by: [module]` and, for an interface a `ui` module consumes or exposes, **`request`, `response` and `errors`**: shapes in the closed shape language of B.8 and errors as `[{code, when}]`. **Under `design` not `off`, a UI-consumed interface without them refuses the plan check** (`ARCH_INTERFACE_SHAPE_MISSING`, a new clause 5 of D6 §5.3, G2), naming the interface, so the Architect's session is told before close; under `off` they are optional. Today's `{name, kind, path?, description}` interfaces and modules without `targets` parse unchanged.

**4.2 What the engine derives** (a pure function of the approved bundle; `inventory.json`, B.9; recorded with `inventory_digest`):
- **Interfaces:** every interface whose `consumed_by` includes a `ui` module or which a `ui` module exposes, with its shapes and errors, its module and the requirements the roadmap assigns to that module.
- **UI requirements:** every requirement not withdrawn that is assigned to a phase whose modules include a `ui` module **and** that a UI stage implements, or whose subsection carries the mark `**Surface:** ui` (B.2 gains the mark, G3), optionally narrowed by `**Surface:** ui (android, ios)` to some targets. The mark lets the Spec Writer name a UI requirement before any plan exists.
- **State obligations**, mechanically, per target the consuming module serves: `loading` for every `http` or `event` interface; `error:<code>` for each declared error; `empty` for every response holding a `collection`; `invalid_input` for every request property with a bound or an enum; `permission_denied:<permission>` for each `platform_permissions` entry of that target; `ok` always. Each obligation names its interface or permission and its target.
- **Targets:** per `ui` module and target, the technology, the preview capability (§5.2), the layouts (§5.3: `design_widths` for web, the module's form factors in both orientations for `android` and `ios`, the window sizes the design declares for desktop targets), the conventions every screen of that target must declare (§5.3's table), and the default asset slots and variants (§6.2); the default themes are `light` and `dark` (§5.8). The ADR keys that name the technologies and the environment's runtime come with them.

**4.3 What it does not derive.** Screens, flows or navigation. The engine cannot read screens out of prose; it derives obligations, and the Designer proposes the flows and per-target screens that meet them (§5.3), which the design check then holds to the obligations. Mapping a requirement to a screen is the role's claim; the check proves coverage, never that the screen is good (§15 class C).

**4.4 Fixtures and placeholders.** For each interface and state obligation the engine writes deterministic fake data under `.surety/design/inventory/fixtures/<interface>.<state>.json`, generated from the shapes with a seed derived from `inventory_digest` (strings from the property name and bounds, numbers within bounds, `collection` arrays of three items and of none for `empty`, the declared error body for `error:<code>`, a value violating the first bound for `invalid_input`). It commits them with `inventory.json`, and the placeholder asset files of §6.3, as an engine `intent` revision (D1 §7.8), journaled, before the session opens. The Designer may add its own data under `mockups/data/`; every file there must validate against the shape it names (`DESIGN_FIXTURE_INVALID`). **The inventory is the contract the design is drawn against, and the Designer may not change it** (§3.3).

**4.5 When the inventory is wrong.** A missing interface, a wrong shape, a missing error case, a missing permission or a target the product needs and the spec lacks is an architecture or spec change, never a design workaround: the role reports a finding (§3.5); the engine routes `contract_conflict` to the owner's question with the options D3 X2 gives plus `architect` (open an Architect session; the route D6 §3.4 already has for a later Architect session), and `requirement_conflict` to `change_spec` (D6 §4.2). The design session may continue meanwhile; its approval is blocked while a finding it raised is open against an interface its screens use (`DESIGN_INTERFACE_DISPUTED`).

## 5. The design product

**5.1 Files** (`.surety/design/`; closed schemas in Appendix B):
- `design.json` (B.10): the manifest the engine reads first: `{version, origin, inventory_digest, selection, targets: [{module, target, ui_technology, form_factors, preview_capability, layouts, window?}], cross_platform?, tokens_file, flows_file, screens_file, navigation_file, criteria_file, assets_file, mockups: [...]}`. The three axes are separate fields of every target entry; `preview_capability` is copied from the inventory and checked equal (§5.6 clause 6).
- `tokens.json` (B.11): **platform-neutral** design tokens: colours per selected theme (§5.8), type, spacing, radii, durations, and `pairs` (every text-on-background use). Sizes are in the **logical unit** `lu` (1 CSS px, 1 Android dp or sp, 1 Apple pt, 1 desktop device-independent px), names dotted (`color.text.primary`). The engine generates per-technology bindings from it: `tokens.css` (CSS custom properties, `--color-text-primary`) for `html_css` and `three_js`; the neutral `tokens.json` itself for every other technology, which its Builders read from a source path the stage names. **CSS is one binding, not the source of truth.**
- `flows.json` (B.12): target-independent workflows `F<n>`, each a sequence of steps naming requirements and interfaces. This is where a cross-platform product's shared workflow lives.
- `screens.json` (B.12): screens `S<n>`, **each for exactly one target**, realising flow steps, with states, layouts, inputs and that target's conventions (§5.3).
- `navigation.json` (B.15): per target, the navigation graph (§5.3).
- `criteria.json` (B.13): the criteria the design proposes (§7.2), each scoped to targets.
- `assets/manifest.json` and `assets/`: the asset manifest and its files (§6; B.16).
- `mockups/`: the mockups (§5.4); `mockups/data/`: the role's own fixtures.
- `design.md`: prose for the owner and the Builders. Not parsed.

**5.2 Preview capability.** What the engine can show for a module's target, computed from the target, the technology and the `design_preview` policy (A.7), recorded in the inventory and on every preview deployment:
- **`native`**: the mockup runs in the target's own runtime. In M6 this is **web with `html_css` or `three_js`** only: the owner's browser is web's runtime. A native preview is evidence about the mockup, never about the product; the product's evidence is the checks on candidates.
- **`simulated`**: an HTML stand-in for a target the engine cannot run. In M6 every `android`, `ios`, `macos`, `windows` and `linux` target, and web under `streamlit`, `flutter` or `other` unless question 2 builds stack previews. **A simulation is never native execution evidence** (§5.7, §10.2): back gestures, safe areas, permission prompts, window chrome, menus and shortcuts are drawn, not exercised.
- **`none`**: no rendered preview: `design_preview: off`, or a target whose design supplies screens, navigation, states and images only.

Native behaviour of a non-web target is ultimately validated on the appropriate simulator, emulator or device. M6 builds the design artifacts for every target and the simulated preview; a native preview runner per platform is a later milestone's (§15 class B), and the design product needs no change when it arrives: only the computed capability does.

**5.3 Screens, navigation, interaction states and platform conventions.** Each screen is `{key, target, title, flow_steps, requirements, interfaces, states: [{obligation, mockup?, fixture}], layouts, inputs: [{interface, property, label, unit?}], conventions, notes?}`. **States** are the inventory's obligations for that target plus any the role adds (`focus`, `pressed`, `disabled`, `offline` as `custom:<name>` states); each names its fixture. **Navigation** (B.15) is per target: entry screens and edges `{from, to, trigger, kind}` with `NavKind` `push`, `replace`, `modal`, `sheet`, `tab`, `back`, `deep_link`, `menu`, `shortcut`, `window`. **Conventions** are the fields a screen of that target must declare; the design check requires each to be **declared** (file-level), and §7.2 says which can be checked as **honoured** in the implementation in M6:

| Target | Each screen declares (required by the design check) | Honoured in the implementation, M6 |
|---|---|---|
| web | `route` or `transient`; what browser back and forward do on leaving it; a keyboard path to every action and the focus order; pointer and touch both; layout at each configured width | CSS kinds for `html_css` and `three_js` (§7.2); the rest human test |
| android | system back: `back` to a screen, `exit`, `confirm` or `dismiss` for every non-root screen; each permission's prompt moment, rationale and `permission_denied` state; touch interaction (gestures used); layout per form factor and orientation | `not_checkable_yet`: human test on an emulator or device |
| ios | navigation container (`stack`, `tab`, `modal`, `sheet`) and edge-swipe back where `stack`; safe-area edges the content respects; permission prompts as android; phone and tablet layouts | `not_checkable_yet` |
| macos, windows, linux | window minimum and default size and the layout at the minimum; the menu entry (menu, item) of each action that has one; keyboard shortcuts, none duplicated within one window; hover and context menus where used | `not_checkable_yet` |
| cross-platform group | shared flows, tokens and assets; each step of a shared flow has a screen on every target of the group, or a stated `difference: {target, what, why}` | file-level only |

**5.4 Mockups.** Closed kinds (`MockupKind`), each admitted by its screen's target and preview capability:
- `static_html`: HTML and CSS reading the generated `tokens.css`, the role's scripts if any; **web targets whose capability is `native` only**.
- `scene_html`: an HTML page with a module script importing three.js from a pinned URL, rendering a minimal scene or still from a fixture's time series; web under `three_js`.
- `simulated_html`: an HTML stand-in for a screen of a target whose capability is `simulated`; it **must** declare `simulates: {target, form_factor?, layout}`. An HTML mockup of a non-web screen not declared a simulation is refused (`DESIGN_SIMULATION_UNDECLARED`).
- `image`: a still (`png`, `svg`, `webp`) of a screen state; any target; capability `none` is enough.
- `source_stub`: a source file in the module's technology (a SwiftUI view, a Compose function, a Flutter widget, a Streamlit page), shown as source and never run in M6.

Each mockup is bound to the screen states it renders and the fixtures it reads. **External URLs** a mockup loads must name an exact version on the configured allowlist (`design_external_urls`, A.7; `DESIGN_EXTERNAL_URL_UNPINNED`): the owner's browser fetches them, the engine never does.

**5.5 The size bound.** The design tree is at most `design_tree_max_bytes` (default 32 MiB, raised from draft 1 for per-target images and asset variants) and `design_tree_max_files` (default 800); beyond either the save is refused naming the bound. Binary files are admitted (`png`, `svg`, `webp`, `ico`) and counted.

**5.6 The design check** (`checkDesign(tree, inventory)`, a pure function like D6 §5.3's, run at every save and again at close; recorded as a `design_check` record; each reason names its subjects, the target among them; A.4):
1. **Schema:** every machine file parses with its closed schema (`DESIGN_SCHEMA_INVALID`, naming the field); `design.json`'s `inventory_digest` is the current inventory's (`DESIGN_INVENTORY_STALE`).
2. **References:** every requirement key is a UI requirement of the inventory for that screen's target (`DESIGN_UNKNOWN_REQUIREMENT`); every interface is in the inventory (`DESIGN_UNKNOWN_INTERFACE`); every screen's target is a target of the inventory (`DESIGN_UNKNOWN_TARGET`); every mockup and fixture file named exists, and no mockup exists that no screen names (`DESIGN_MOCKUP_MISSING`, `DESIGN_MOCKUP_ORPHAN`).
3. **Coverage, per target:** every UI requirement is on at least one screen of each target it applies to (`DESIGN_REQUIREMENT_UNCOVERED`); every state obligation of the target is a state of a screen of that target that uses its interface (`DESIGN_STATE_UNCOVERED`); every screen declares every selected layout of its target (`DESIGN_LAYOUT_UNCOVERED`); every request property with a `unit` is an input with a label naming it (`DESIGN_INPUT_UNLABELLED`).
4. **Navigation and conventions, per target:** every edge names screens of its target (`DESIGN_NAV_UNKNOWN_SCREEN`); every screen is reachable from an entry (`DESIGN_SCREEN_UNREACHABLE`); every convention §5.3 requires for the target is declared (`DESIGN_CONVENTION_UNDECLARED`, naming target, screen and convention); no shortcut is duplicated within one window (`DESIGN_SHORTCUT_DUPLICATE`); in a cross-platform design, every shared flow step has a screen on every target of the group or a stated difference (`DESIGN_TARGET_DIVERGENCE_UNSTATED`).
5. **Tokens:** every token a pair names is defined in every selected theme (`DESIGN_TOKEN_UNDEFINED`); **every pair's WCAG 2 contrast ratio is at least 4.5:1 in each selected theme** (`DESIGN_CONTRAST_BELOW_AA`; arithmetic on the declared hex values, nothing rendered, every target).
6. **Axes and mockups:** each target entry's technology and preview capability equal the inventory's (`DESIGN_AXIS_MISMATCH`); each mockup's kind is admitted by its screen's target and capability (`DESIGN_MOCKUP_KIND_MISMATCH`); `simulated_html` declares what it simulates (`DESIGN_SIMULATION_UNDECLARED`); external URLs pinned (§5.4).
7. **Criteria:** every proposed criterion's `kind` is in §7.2's catalogue (`DESIGN_CRITERION_UNCHECKABLE`) and **applies to the target and technology of every screen its requirement is on** (`DESIGN_CRITERION_NOT_APPLICABLE`, naming kind, target and technology); a criterion that reads files names the implemented paths.
8. **Assets and selection:** §6's rules (`DESIGN_ASSET_*`, A.4); a selection below §5.8's floor is `DESIGN_SELECTION_BELOW_FLOOR`, naming what it dropped.

The check reads JSON, SVG text and raster headers and computes; **it executes nothing the Designer wrote** (M5 §4.1 rule 14 holds), and it does not judge a mockup's look. A failed check is the engine's entry on the next turn; close is refused until it passes, or the owner closes with `--refuse`, which records the product and raises nothing (D6 §3.4's form).

**5.7 The preview environment** (G4, a correction to D4). The owner needs to click through mockups, so the engine can serve a design checkpoint on the `local_service` adapter:
- **Environment `design-preview`**, reserved, engine-configured (no owner configuration act), one per project, adapter `local_service`, its configuration the engine's: the runtime the engine's own `node`, the start command **an engine-authored static file server** (read-only, in the engine's install, hashed), its document root the sealed design tree. The design's own code is served, never run on the host: HTML and scripts run in the owner's browser; only under `design_preview: stack` (question 2) does a `source_stub` for a web technology run, and then only as a service domain's application, as any candidate's code runs (D4 §9.2).
- **Simulations are labelled by the engine, not the role.** A `simulated_html` mockup is served only inside an **engine-authored frame**: a fixed banner, "Simulation of <target> (<form factor, layout>). Not native behaviour: back, safe areas, permissions, gestures, window chrome and menus are drawn, not exercised", around a sandboxed iframe (scripts allowed, same origin not, so the mockup cannot reach or remove the banner). A direct request for a simulated mockup's path is answered with the frame. The index page lists every mockup with its target and its capability. `surety design export` writes an engine-authored `SIMULATIONS.txt` naming every simulated mockup beside the tree.
- **The subject is a design revision, not a candidate.** `surety design preview [--revision <checkpoint|approved>]` seals `.surety/design/` at that revision (D4 §3's sealing, same limits), deploys it through D4's operation with **no `alpha_authorize`** and **no behaviour check**: verification is the two identity reads (`tree_digest`) only. A preview deployment is never a candidate progress, never `alpha_deployed`, and never evidence for any gate; its record carries each mockup's `preview_capability`. `design.preview_deployed`.
- **Admission:** `preview_memory_max` (default 256 MiB) under the envelope as built; **no shared check capacity is reserved** (no check runs on a preview), unlike E126's service. One preview generation per project; a new preview replaces the last (D4's stop-then-start).
- **Access** through the operator relay (D4 Q7), opened only by the owner's command, on `127.0.0.1`; `surety design preview` prints the URL.
- **Teardown** at the session's close plus `design_preview_ttl` (default 24 h), on a newer approved design, or by `surety design preview --stop`; D4 §4.6's rules, the unit name derived from the home as D4 §9.3.
- **Without a qualified adapter** the preview is unavailable and says why; `surety design export <dir>` always works: it writes the design tree at the named revision to a directory the owner names (a read, no host call beyond the write), and he opens the files himself.

**5.8 Design requirements are selected, not imposed.** Not every product needs both themes, five logo variants or every layout. The inventory gives **defaults**: themes `light` and `dark`; §6.2's slots and variants per target; §4.2's layouts (`design_widths`, each form factor in `design_orientations`, the declared window sizes). `design.json`'s **`selection`** (B.10) states what this design commits to: its themes, per slot kind its variants, per target its layouts. The design check holds the design to the selection, not to the defaults: tokens and contrast in the selected themes, screens at the selected layouts, slots and variants only as selected (§6.2), and the human-test requirement of §7.3 names the selection. **Narrowing is the owner's act:** the Designer proposes a selection; every narrowing below the defaults is listed on the `design_approval` ("narrowed: dark theme; logo variants `monochrome`, `on_dark`") and takes effect only when he approves it. **A floor no selection goes below** (`DESIGN_SELECTION_BELOW_FLOOR`): one theme; one layout per target; a `logo` with one variant; and per target the one kind a build of it cannot ship without (`favicon` for web, `app_icon` for every other target) with one variant. Widening a selection later is an ordinary design revision.

## 6. Branding and assets

**6.1 The asset manifest** (`assets/manifest.json`, B.16) is part of the design tree, so every design revision binds one version of it. It has its own `version`, which increments on any change to a slot or a file, and each slot its own **`slot_version`**, which increments whenever any of its files changes (`DESIGN_ASSET_VERSION_INVALID` otherwise), so **`slot@version` names one set of files exactly and forever**. Each slot keeps its history of `{slot_version, design_version, status, files}`, the engine placeholder's entry included, so the placeholder is always recoverable. A **slot** is `{key, kind, purpose, platforms, placement?, variants, alt_text?, slot_version, status, provenance, status_since}`; a **variant** is `{name, format, size?, transparency, file?, digest?}`:
- `kind` (`AssetKind`): `logo`, `app_icon`, `favicon`, `banner`, `splash`, `illustration`, `image`.
- `platforms`: the targets the slot applies to, each a target of the inventory (`DESIGN_ASSET_PLATFORM_UNKNOWN`).
- `placement`: required for `banner` (`website_hero`, `store_listing`, `social_card`, or `named:<text>`; `DESIGN_ASSET_PLACEMENT_MISSING`) and for an `illustration` (the screen states that show it, such as an `empty` state).
- `variants` (`AssetVariant`): `full`, `compact`, `monochrome`, `on_light`, `on_dark`, `adaptive_foreground`, `adaptive_background`, `default`; each with `format` (`svg`, `png`, `webp`, `ico`), `size` in pixels for raster formats, and `transparency` (`required`, `forbidden`, `any`).
- `alt_text`: required for `logo`, `banner` and `illustration` (`DESIGN_ASSET_ALT_MISSING`); an `image` slot states `decorative: true` or has it.
- `status` (`AssetStatus`): **`placeholder` → `proposed` → `approved`**; `provenance` (`AssetProvenance`): `engine_placeholder`, `designer`, `owner`, `observed`.

**6.2 Default slots.** The engine derives the **default** slots for each target, by kind and variant only, from a closed table: every product a `logo` (variants `full`, `compact`, `monochrome`, `on_light`, `on_dark`); `web` a `favicon`; `android` an `app_icon` (with the adaptive variants); `ios` an `app_icon` and a `splash` (launch); `macos`, `windows` and `linux` an `app_icon`. These are defaults the selection narrows with the owner's approval, down to §5.8's floor; they are not requirements of every product. Banners, illustrations and other images are the design's to add, each for a named placement. A selected slot or variant missing from the manifest is `DESIGN_ASSET_SLOT_MISSING`. **The table names kinds and variants, not sizes**: sizes and store requirements are platform guidance, recorded in §6.6, never hard-coded in the engine.

**6.3 Placeholders work immediately.** At inventory derivation (and when targets change) the engine writes a placeholder for every default slot and variant that has none, with no model and no new dependency, deterministic from the project's name and a fixed neutral palette: a **labelled logo block** (SVG, the name and the word PLACEHOLDER), a **generated initials icon** (SVG), a **correctly proportioned banner** for a named placement whose size is declared (SVG), and for a variant whose format is raster, a flat PNG of the declared size encoded with the engine's own code (node's zlib). Provenance `engine_placeholder`, status `placeholder`. The Designer may replace a placeholder by proposing a file (status `proposed`, provenance `designer`; in practice SVG, since the role writes text); the owner may supply one himself with `surety design asset add <slot> <variant> <file>`, which validates it against the slot (§6.1's rules and the header checks below) and commits it as an engine `intent` revision on `.surety/design/assets/`, status `proposed`, provenance `owner`. **Header checks** (file-level, no decoding): the file's format matches its magic bytes or SVG root (`DESIGN_ASSET_FORMAT_MISMATCH`); a raster's dimensions in its header equal the declared size (`DESIGN_ASSET_SIZE_MISMATCH`); `transparency: forbidden` admits no alpha channel and `required` requires one (`DESIGN_ASSET_TRANSPARENCY_MISMATCH`); an SVG holds no script, event attribute or external reference (`DESIGN_ASSET_SVG_ACTIVE`, §14).

**6.4 Approval and the effective asset set** (**Q8 decided:** assets are approved through the existing `design_approval`, and placeholders are usable throughout development). Only the owner moves a slot to `approved`, by answering a `design_approval`: `approve` approves the design revision and every slot version it holds as `proposed`, except those the owner lists in `assets_held`, which stay `proposed` in the manifest until a later asset-only approval (raised by `surety design assets submit`, A.8). A save whose manifest marks a slot `approved` that the last approved revision did not approve with the same digests is refused (`DESIGN_ASSET_STATUS_FORGED`). **An asset-only revision** (one whose diff from the approved revision touches only `assets/`) needs no Designer session when the owner supplies the files; it runs the design check, raises `design_approval` **with no consolidated spec change**, stales no screen and changes no readiness.

**The effective asset set** is the only set of asset files that ever leaves the design tree: per selected slot and variant, **the latest approved `slot@version`, else the slot's engine placeholder**. A `proposed` file, held or not yet answered, is never effective: it reaches no Builder package, no check, no deployment. So when the owner approves a layout but holds its proposed logo, Builders receive the previous approved logo, or the placeholder if none was ever approved, and never the held proposal. The engine records the set at every approval (`design_effective_assets`, A.3; `design.assets_approved`), each entry `{slot, variant, slot_version, source: approved | placeholder, digest}`; **the Builder package, the check runner and every projection read only that record**, never the manifest's latest files. An effective version changes only by an owner's approval, never by a save.

**6.5 Into the build: the effective set, bindings and versioned parity** (G11, G14).
- **The package.** A UI stage's Builder package carries the effective set for the slots its targets use, each file with its `slot@version` and its source (approved or placeholder), read-only; the Builder copies them to the source paths its stage needs and writes nothing under `.surety/`. A placeholder builds like any file: **asset status never fails a check and never holds work**.
- **Bindings.** The Builder's result (D2 §1.4; B.17) declares an **asset binding** for each effective file it placed: `{slot, variant, target, path, form}`, `form` `copy` (the file at `path` is the effective file byte for byte) or `derived` (made from it, such as a raster rendition or a platform icon set, recorded with the source `slot@version`). The Architect may declare bindings beforehand (`asset_paths` in the module map, B.3 as G1 extends it), which the package then states as where each file goes. At integration the engine validates each binding with D1 §7.3's validation: the path exists in the integrated tree (`ASSET_BINDING_PATH_MISSING`), it names a slot and variant of the effective set the package carried (`ASSET_BINDING_UNKNOWN_SLOT`), and a `copy` binding's digest equals the effective file's (`ASSET_BINDING_MISMATCH`); a failure refuses the integration like any validation failure. Valid bindings are recorded with the stage and the revision (`asset_bindings`, A.3; `design.asset_bound`). A slot an integrated stage's package carried and no binding names is shown **unbound** in `GET …/design`.
- **Updates.** Whenever a slot's effective version changes (a proposal approved; a first approval replacing the placeholder), the approval's effect registers **one `fix` work item** (E43's form) with cause `asset_updated`, naming the slot, the old and new `slot@version` and every recorded binding of it, on the latest integrated candidate; the Builder updates those paths (re-deriving the `derived` ones) and returns the bindings anew. A slot carried to an integrated stage but unbound gets the same work with no paths: the Builder places it and declares the binding. A slot no integrated stage has carried needs no work; the next UI stage's package holds the new version. **No criterion is needed for an approved asset to reach the app**: the bindings are its implementation path.
- **Versioned parity.** The design may propose an `asset_parity` criterion (§7.2) for a `copy` binding: the file at the bound path equals the effective file. The check reads the effective file from the engine's record, and **its result records the `slot@version` it compared against**, so a result is evidence about that version only. When the slot's effective version changes, the engine registers a check obligation with reason `asset_version_changed` (G14) for every check reading the slot: the parity obligation is new, earlier results stay true of the version they name and are never read as evidence for the new one, and the gate waits on the `asset_updated` candidate's results as on any obligation. The criterion's text does not change, so no spec change is needed.

**6.6 Platform packaging requirements.** Icon sizes, adaptive-icon layers, launch-screen rules, store listing graphics and favicon sets are platform guidance, which changes. The manifest records them as `packaging: [{target, slot?, requirement, guidance, status}]`, `guidance` naming the source and the date the role or the owner read it; `PackagingStatus` is `recorded` or `not_checkable_yet` in M6. They are **checked against the applicable platform guidance only when native packaging is implemented** (a later milestone, which adds `checked_pass` and `checked_fail`). The engine never fetches guidance and M6 claims nothing about conformance to it.

**6.7 The release-policy hook** (G10; a hook for D5, inert until D5 is built). `assets_required_for` (project policy, A.7): `none`, `beta`, `live` (**default `live`**, Q8 decided). For that environment tier and every later one, D5's authorization adds one condition: every selected slot whose platforms include a deployed target has an effective version whose source is `approved` (`ASSETS_NOT_APPROVED`, naming the slots). **Under the default, `live` does not require approved branding for a Beta, public or not**: a public Beta may ship with placeholders, and only Live waits for approved assets; an owner who wants branding before a public Beta sets `beta`. **The key's range excludes Alpha by construction**: no asset status is read by `alpha_authorize`, `design_ready`, stage dispatch or any gate of D6, and a missing logo never stops functional development. `GET …/design` shows the count of unapproved slots against the policy, e.g. "required for live: 3 slots not approved".

## 7. Approval, and how design enters the specification

**7.1 The choice** (question 1). The design proposes criteria; the spec is the governed source of criteria (D6 §4), written only by the Spec Writer (D6 §2.5) and approved on the floor. Three ways to join them:
- **(a) Consolidated** (recommended): at close the engine files one change request (`source: design`, A.2) whose text is `criteria.json` and the design human-test requirements (§7.3); a Spec Writer one-shot writes the diff on its side ref (D6 §4.3); the impact is computed (D6 §4.4); **`design_approval` and that `spec_change` are raised under one `batch_key`** (D1 §10.3). The owner sees mockups, check record, criteria diff, asset manifest and impact together and answers once per decision. One spec author, one floor control, one sitting.
- **(b) Separate:** design approval first; the owner later runs a Spec Writer change himself. Simpler, but the design is approved with no criteria bound to it, and UI stages would build against a design nothing checks.
- **(c) Design-owned criteria:** the gates read `criteria.json` as a second criterion source beside the spec. Rejected: it splits the governed specification in two and bypasses D6 §4's impact and invalidation.

**7.2 What a design criterion can be: a catalogue scoped by target and technology.** Each `DesignCriterionKind` is a static read of implemented files the Verifier knows how to write (as V1's `accept-r8.mjs` showed for one web page), and **declares the targets and technologies it applies to**. A criterion is admitted only where its kind applies (§5.6 clause 7). **CSS rules never become universal requirements**: a CSS kind applies to web screens built in `html_css` or `three_js`, and to nothing else, not even web under `streamlit`.

| Kind | Targets | Technologies | What the check reads |
|---|---|---|---|
| `tokens_only` | web | html_css, three_js | every colour, size, spacing, radius and duration literal in the named stylesheets is a custom property defined once in the tokens stylesheet |
| `layout_at_width` | web | html_css, three_js | no fixed width, min-width or grid track exceeds the named width outside a media query that excludes it |
| `label_with_unit` | web | html_css, three_js | every input has an associated label naming its unit where the shape has one |
| `focus_visible` | web | html_css, three_js | every focusable element has a focus style not removed |
| `reduced_motion` | web | html_css, three_js | every transition and animation is disabled or reduced under `prefers-reduced-motion` |
| `token_parity` | all | html_css, three_js (the CSS binding); any technology whose code reads the neutral `tokens.json` from a named path | the implemented tokens equal approved design version d |
| `contrast_aa` | all | as `token_parity` | every implemented text-on-background pair meets 4.5:1 in each selected theme |
| `state_marker_present` | all | all | for each state obligation of a screen, a named marker is present in the implemented files: a selector in the page (web) or a test id, key or accessibility identifier in the module's source; presence only, never that the state is reached or shown |
| `asset_parity` | all | all | the file at a `copy` binding's path equals the effective file of the slot's variant; the result records the `slot@version` compared (§6.5) |
| `human` | all | all | nothing; judged by a person |

**Native conventions are not criteria in M6.** §5.3's conventions that only a running native build can show (system back, safe areas, permission prompts, touch interaction, window resizing, menus, shortcuts, platform navigation; `NativeConvention`, A.2), and web's browser back and keyboard path, are recorded per target and screen as **`not_checkable_yet`** (`design_native_obligations`, A.3) and listed in that target's human-test requirement (§7.3). They are not dropped: `GET …/design` counts them per target, and a later milestone with native checks turns them into criteria by an ordinary spec change. A criterion of such a kind proposed now is refused `DESIGN_CRITERION_NOT_APPLICABLE` with the hint `not_checkable_yet`. Each admitted criterion is written into the spec as an ordinary `R<n>.<m>` and its check is authored by the Verifier like any criterion (D6 §6.2): the design proposes; the Verifier's checks and D3 §4.2's required set decide.

**7.3 The human-test requirements.** Every approved design adds or updates **one requirement per target**: "The <target> UI matches approved design version d: screens …, layouts …; with these conventions, not checkable yet: …", marked `**Human test.**` (B.2), assigned to the phase that holds the last UI stage for that target. For a target whose preview capability is `simulated`, the requirement says it is judged on a simulator, emulator or device, **not on the simulated preview**. As D6 §11 class C says of every human-test requirement, it has no check and is never `verified` by a gate; it is shown pending with a reference to the approved design, and a design review (§10) records the owner's **confirmed** verdict against it, with the runtime he observed on and the provenance of the evidence (question 4).

**7.4 `design_approval`** (A.8 row, G5). Subject the design revision; binds the design version **and** the semantic bindings it was checked against: the architecture version, the `design_check` record's hash, the asset manifest's version, the selection (with its narrowings listed, §5.8), the blobs of the design tree, and **the specification it will be current against**. Raised alone (an asset-only revision), that is the current spec version and its `inventory_digest`. **Raised in a batch with its consolidated `spec_change`, it binds the spec version that change creates** (the change request's diff hash and the version number it will take) **and the inventory derived from that version**, which the engine derives and design-checks when it raises the batch. The batched spec change is therefore not a change to the design's bindings, and the batch's approval records the design current against version n+1 in the transaction that applies n+1: **a design approval never stales itself.** This holds because the batch carries only `criteria.json` and the design's human-test requirements (D6 §4.2's one-pending rule), and those requirements are never UI requirements of the inventory (they refer to the design; nothing is drawn on them), so n+1's inventory equals n's; the engine still derives and compares it, and a difference refuses the batch at raise. Any other change to a binding (another spec change approved first, so that n+1 is no longer the number it takes; an architecture revision; a later save) stales it (D1 §4.6). **Human only; not on F §9.1's floor**, like `architecture_approval` (D6 §3.4); its criteria reach the floor through the consolidated `spec_change`. Options: `approve` (with `assets_held?`, §6.4), `revise` (back to a session with the owner's note: `design_due` re-raised with stage `revise`), `reject` (the product kept as history; the policy's holds remain and `design_due` stays open). **Option blockers:** the design check not passing; a finding the session raised open against an interface its screens use (§4.5); the consolidated `spec_change` answered `reject` (a design whose criteria were refused is approved only through `approve_without_criteria`, an explicit option that records the absence on the revision and in every projection). **Effect:** `design_revisions` row (A.3) with `current_against_spec`, `baseline.design_approved`, the slots approved and the effective set recorded (§6.4), `asset_updated` work registered for every changed effective version (§6.5), the stage-to-screen binding computed (§8.1), the preview's TTL restarted on the approved revision. An asset-only revision's `design_approval` has no consolidated spec change and no criteria blocker.

**7.5 Design readiness** (B07's rule applied to design). `design_ready_at` is set when the design is approved **and** the protected version that covers its criteria (the `check_correction` the spec change registered, D6 §4.5) is applied, or when the design was approved without criteria. A captured, rejected or unapplied proposal establishes nothing; the design criteria carry `ACCEPTANCE_SCOPE_INCOMPLETE` on every gate until their checks exist, as D6 §4.5 says of any uncovered criterion. Asset status and the native conventions' `not_checkable_yet` take no part. `design.ready`.

## 8. Planning and execution

**8.1 UI stages.** A stage is a **UI stage** when any of its modules has `surface: ui`. Its **screens** are the approved screens, of the targets its modules serve, that name a requirement the stage implements; the engine computes the binding at design approval and at each plan publication (`stage_screens`, A.3), so the first plan, approved before any design existed, needs no Architect re-entry. Plans published after a design exists may name `screens` per stage (B.5 gains the field, G6); when they do, the plan check verifies them.

**8.2 The third milestone** (D6 §6.4 extended, G6). Under `before_build` and `both`, a UI stage's `stage_build` work depends on D6's two milestones **and on `design_ready`** for every screen bound to it. Unmet, the work is held **`design_pending`** (no approved design) or **`design_stale`** (§9), recorded as `work.held` intervals like every hold (D6 §7.6). **Backend stages are untouched**: their work never waits on design, so a phase's API stages build, verify and pipeline while the owner designs. A dependant of a UI stage waits on that stage's code milestone as always; design never blocks a stage that is not a UI stage, and **assets never block any stage**.

**8.3 Plan check additions** (D6 §5.3; G2, G6; A.4):
- clause 5, **interfaces and targets:** `ARCH_INTERFACE_SHAPE_MISSING` (§4.1), `SPEC_TARGETS_MISSING`, `ARCH_TARGET_UNKNOWN`, `ARCH_TARGET_UNCOVERED`, `ARCH_TECHNOLOGY_TARGET_MISMATCH`, under any `design` other than `off`;
- clause 1, **references:** a `screens` key not in the approved design is `PLAN_SCREEN_UNKNOWN`;
- clause 4, **obligations:** under `before_build` or `both`, when an approved design exists, a UI stage implementing a UI requirement that no approved screen of a target it serves covers is refused **`PLAN_DESIGN_UNCOVERED`**, naming the requirement and target. The replan's repair (D6 §5.6) cannot fix design coverage, so the blocker after its repair offers **`design`** (open a Designer session; `BlockerOption`, A.2) beside `retry`, `replan`, `cancel`. Before any design exists the clause records a **planned design obligation** per UI stage instead of refusing (the first plan's case), and the hold of §8.2 carries it.

**8.4 The Builder's package** (D6 §3.5; E151) for a UI stage adds: the neutral `tokens.json` of the approved design version, and `tokens.css` where the stage's technology is `html_css` or `three_js`; the stage's screens for its targets with their states, layouts, inputs and conventions, and each target's navigation graph; the mockups and fixtures of those screens, **read-only, as reference**, each simulated mockup labelled as such; the **effective asset set** of §6.5 with each file's `slot@version`, any Architect-declared `asset_paths`, and the instruction to return a binding for every file it places; the design criteria the stage's requirements carry; and the plain statement that **the Builder implements the design in source and writes nothing under `.surety/`** (`339e116`). The Verifier's phase-authoring and correction packages add §7.2's catalogue with what each kind reads and where it applies, and the implemented paths the criteria name.

**8.5 Pace inside the phase.** With `design: before_build`, a phase whose UI stages wait costs the owner's design time on those stages only; the pace read shows it as the `design_pending` hold interval per stage and the human wait of `design_due` and `design_approval` (D6 §7.6's union rule).

## 9. Staleness: spec changes, architecture revisions and replans

**9.1 What a design is bound to:** the spec version it is current against (for a batched approval, the version its own spec change created, §7.4), the architecture version and `inventory_digest`. The impact analysis of D6 §4.4 gains a **design class** (G8): the screens whose requirements are `text_changed`, `criteria_changed`, `withdrawn` or newly UI, the screens whose interfaces changed shape, and **every screen of a target added to or removed from the spec, or whose technology changed**.
- **An approved spec change** listing design-class subjects (never the change batched with the design's own approval, whose criteria and human tests are not design-class subjects of that design, §7.4) marks those screens `stale` (`design.stale`, the screens named), recomputes the inventory, and registers the obligation to revise them; the design's own criteria are handled by D6 §4.5 like any criterion. A target added derives its required asset slots and placeholders; a target removed marks its slots' `platforms` stale for the Designer to tidy, and stales no other target's screens.
- **An architecture revision** (a later Architect session, D6 §3.4) that changes `inventory_digest` marks stale the screens whose interfaces, requirements, technology or preview capability moved; a revision that leaves the digest unchanged stales nothing.
- **A replan** that only moves requirements between phases stales nothing; it recomputes `stage_screens`. A UI requirement newly assigned to a UI stage with no screen is §8.3's `PLAN_DESIGN_UNCOVERED`.
- **An asset-only revision** stales no screen (§6.4); a changed effective version makes `asset_updated` work and new parity obligations (§6.5), which are not staleness.
- **Stale screens hold** the UI stages bound to them that are not yet dispatched (`design_stale`) and raise `design_due` (stage `revise`) naming them (§11); stages already running or integrated keep their history (D6 §4.6's rule); their later findings and gates see the current spec as always.
- A design revision approved under the same protocol (§7) clears the staleness for the screens it covers; `design_revisions` keeps every version.

## 10. The design review, at Alpha and on the owner's command

**10.1 When.** Under `at_alpha` or `both`, `alpha_complete` (D4) raises `design_due` with stage `alpha_review`, bound to the Alpha's deployment and candidate. Nothing waits on it: the candidate is `alpha_deployed` and stays so. **A review also opens on the owner's command** against a native build he ran (§10.5), under any policy but `off`. When the product has no web target (a native-only product whose Alpha is its backend service), `design_due`'s question names that command rather than a browser review, and `later` is its natural answer until he has a build.

**10.2 The session in review mode.** A Designer session whose package adds (§3.4): the approved design, if there is one (§10.6); the candidate's UI source, read-only; the design checks' results on the candidate; and, **for the web target**, the engine's observations of the served files: for every web screen's route, the response the engine fetched through the service link (D4 §5.2) at the review's start, recorded through the redactor as `observed` records within `adapter_output_max_bytes`, never fetched by the role (its domain has no reach to the service, D2 §2). The owner browses the web Alpha himself through the operator relay and types what he sees. **For every other target** M6 has no native runtime (D4's Alpha is a service; no emulator, simulator or device runner exists): each screen is `not_observed` with reason `no_native_runtime` until an owner-invoked review brings evidence (§10.5); what the owner types about a simulator, emulator or device he ran is recorded `owner_reported`, with its `observed_on`. **A verdict whose `observed_on` is `simulation` is recorded but never counts as native evidence** in any projection: the human-test requirement of that target stays pending. The role writes `.surety/design/reviews/review-<n>.json` (B.14), every verdict in it a **proposal**: per target and screen `matches`, `deltas` (each with the owner's words, the screen and state, and whether it is a design change, an implementation defect, or both) or `not_observed`; and, if the owner agrees in the session, a **revised design** in the same tree.

**10.3 Close, and the owner's confirmation.** Close records the review (`design_reviews`, A.3; `design.review_recorded`) with the role's verdicts as **proposals** (`VerdictStatus` `proposed`). **Close confirms nothing**: an owner verdict is an owner act, recorded only through a decision or the CLI, never inferred from the role's file, from the session's transcript or from the close command. Close raises **`design_verdicts`** (A.8 row; subject the review; human only; binds the review file's hash and its evidence records; 2 d), answered in the decision or by `surety design verdicts <review> confirm [--edit …] | reject`: `confirm`, with any verdict he edits or strikes, records each confirmed verdict against the per-target human-test requirements of §7.3 as owner evidence bound to the review's subject (the candidate, or the owner's build, §10.5), each with its `observed_on` and the provenance of the evidence it rests on (`design.verdicts_confirmed`); `reject` records none. Question 4 asks whether a confirmed verdict may do more. What follows comes from **confirmed** verdicts only:
- **No deltas:** nothing else.
- **Implementation defects only** (the design was right; the code is not): each is filed as a finding against the review's candidate (for an owner build, the candidate he named or else the latest integrated one holding that target's UI modules, with the build identifier on the finding) (D3; severity he states in the confirmation, default Medium), dispositioned by the owner; `fix` makes fix work as E43, the design criteria's checks deciding.
- **Design deltas:** close raises `design_approval` for the revised design with **one** consolidated `spec_change` (D6 §4.2's one-pending rule; the deltas are one request, not many), batched with `design_verdicts`; the approval is blocked until the verdicts it rests on are confirmed. Approval runs D6 §4.5: version n+1, invalidation, obligations, `check_correction` for the changed criteria, and a replan.

**10.4 The rebuild after the last phase** (G7; a finding about D6 as it reads, and a decision for Sean, question 6). D6 §4.5 registers `replan` "when the impact touches the current or a later phase". After the last phase, a change to requirements of completed phases touches neither, so as D6 reads **nothing schedules the rebuild**: the affected criteria carry obligations, the runner re-runs, and a check that now fails has no stage to repair it: a silent stall of exactly the kind the real runs found worst. G7 closes it for every spec change, not only design: an approved change whose impact names a requirement of a completed phase, with no open phase, registers `replan` with trigger `post_phase_change` (`ReplanTrigger`, A.2), and the Architect's result adds a **delivery phase** to the roadmap for the affected requirements; the roadmap change routes to `plan_approval` (D6 §5.4), and the new phase's stages rebuild and re-verify through the ordinary path, then Alpha under the project's `alpha_deploy`. (An approved asset change does not need G7: §6.5's `asset_updated` fix work carries it.)

**10.5 The owner-invoked review of a native build** (G13). M6 has no Android, Apple or desktop adapter, so for those targets the review starts with the owner: `surety design review --target <t> --build <id/version> [--candidate <c>] [--evidence <file>…]` (`POST …/design/reviews`) records a **review subject** `{kind: owner_build, target, build_ref, candidate?}`, the build identifier verbatim as he gives it (a version name, a build number, a commit), and opens a Designer session in review mode bound to it. The engine **does not verify** that the build exists or was made from any candidate, `--candidate` included: both are his word (§15 class C). Evidence is kept **by provenance and never merged** (`EvidenceProvenance`, A.2):
- **`engine_observed`**: what the engine itself fetched (§10.2's served files of the web Alpha); nothing else ever carries it.
- **`owner_supplied`**: files he hands over, screenshots (`png`, `webp`, `jpeg`) and screen recordings (`mp4`, `webm`), each checked by magic bytes and size (`design_review_evidence_max_bytes`, A.7; `REVIEW_EVIDENCE_INVALID`), stored as `design_evidence` records with digest, target, build reference and the `observed_on` he states (`device`, `emulator`, `simulator`), never decoded beyond the header nor executed (§14). The role sees screenshots as images and recordings by name only.
- **`owner_reported`**: what he types in the session.

Every verdict names the evidence it rests on; every projection labels its provenance (device evidence "owner-supplied", served pages "engine-observed"); **no owner-supplied or owner-reported evidence is ever shown or counted as engine-observed**, and `observed_on: simulation` stays non-native as §10.2 says. The review closes and is confirmed as §10.3.

**10.6 A first design at Alpha.** Under `at_alpha`, or under `both` when the design before build was waived, a review may find no approved design. It then **produces the first design**, not a delta: the role draws it from what is observed (the engine's served-file observations, the candidate's UI source, the owner's evidence and words) and what the owner asks for, as retrofit draws an observed design (§12), `origin: observed`; the design check applies as to any design. Close raises `design_approval` with scope **`initial_review`**: approved as an **initial design**, with no deltas recorded (there is nothing to differ from), its criteria and per-target human tests through the consolidated `spec_change` of §7.1 and §7.4, placeholders written for default slots that have no file, and implementation defects from confirmed verdicts filed as §10.3. Its criteria name requirements of completed phases, so G7's `post_phase_change` replan schedules the work that makes the built application meet them.

## 11. No silent stalls

The real runs' worst failures were stalls with nothing asked (`aa06dcf`, `5bf01a4`, the owed-finding rules of E152 item 2). D7's rule: **no design hold exists without an open owner question naming it.**
- **`design_due`** (A.8 row; subject the project; human only): raised when a UI stage is first held `design_pending` or `design_stale`, when a design is rejected or sent back for revision, and on `alpha_complete` under `at_alpha`/`both`. Its question names the held stages, the stale screens with their targets, and the exact command (`surety session open designer`, or for a target M6 cannot run, `surety design review --target <t> --build <id>`, §10.5). Options: **`open`** (allocates the Designer session, D6 §2.1: no process starts until the owner's first turn); **`waive`** (the named UI stages proceed with no design; recorded on each stage with the owner's reason, `design.waived`; the design human-test requirements, if any, stay pending); **`policy_off`** (sets `design: off`, a policy revision); **`later`** (re-raises at a target time the owner gives, at most `design_due_max_defer`, default 7 d). One `design_due` is open per project at a time; a new cause updates its subjects, which stales and re-raises it (D1 §4.6), never a second row.
- **Escalation:** `target_seconds` 2 d (A.8's approvals default); `decision.escalated` as D1 §10.
- **A Designer session that ends without a product** (idle timeout, budget exhaustion, a close with `--refuse`) leaves `design_due` open and says so on the next read; it never closes the question.
- **A held UI stage's pace** is the `design_pending` interval; `GET …/plan` shows each held stage with its hold, the open question and its age.
- **Assets cannot cause a stall**: no hold reads them (§6.7), and every change of an effective version makes `asset_updated` work for each slot an integrated stage carried, bound or not (§6.5).
- **Unconfirmed verdicts are a question, not a silence:** `design_verdicts` stays open, escalates as any decision, and the review's deltas and defects wait on it visibly (§10.3).
- **The engine never answers `design_due`** and no harness default does outside the scripted human acts of the test seam (M5 spec §8's form).

## 12. Retrofit (D6 §8)

An adopted repository with an existing UI captures its design as **observed**. A Designer session in retrofit mode (a package variant, as D6 §8.2) reads the UI source and writes, per target the retrofit spec confirms: tokens extracted from the existing stylesheets or theme files, a screen inventory and navigation graph of the existing routes, activities, views or windows mapped to the confirmed requirements, the conventions the code shows (a declared back destination where the code has one; `unknown` where it cannot tell, which the design check reports as `DESIGN_CONVENTION_UNKNOWN`, blocking approval under `before_build` and shown under `at_alpha`), and mockups that are **copies of the existing pages as static files** for web where the technology allows (none otherwise). Existing logos, icons and banners found in the repository become slots with provenance `observed` and status `proposed`; default slots with no file get placeholders. `design.json` carries `origin: observed`. Its approval is `design_approval` as §7.4 with the origin shown; its proposed criteria go through the same consolidated spec change, but **are scheduled to the first change phase, never to the conformance set** (B11's reasoning: the conformance phase carries the code unchanged, and a design criterion the adopted code fails would block conformance on an aspiration). An owner's intended design change is an `intended` requirement in a later phase, delivered as any. The interface inventory of an adopted repository needs the Architect's retrofit module map to state shapes and targets (§4.1); where it cannot, the inventory lists the interface with `shape: unknown` and the design check reports every screen using it (`DESIGN_INTERFACE_SHAPE_UNKNOWN`), with the same blocking rule. Unknown is a value; the engine does not invent a shape, a target or a convention.

## 13. Pace and cost

**What it costs, by construction.** One Designer session per design revision (Opus), usually one before build and at most one per Alpha review; one Spec Writer one-shot per consolidated change; one `check_correction` Verifier run for the design criteria; the checks, the placeholders and an owner-supplied asset-only revision cost no model. A session's turns re-send the transcript and the inventory (D6 §2.2), mockup turns write more output than the Architect's, and a cross-platform design writes screens per target: V1's Architect session was one turn of 232 s with the Spec Writer's two turns 266 s, sessions together 98 k billable, 648 k cached and 51 k output tokens. **No Designer figure exists yet**; that comparison suggests a design session of several turns at a few minutes each for one target, more for several, which is a guess for planning the real run, not a claim.

**What the pace read adds** (D6 §7.6, as projections from recorded events, `unknown` where an observation is missing): per project, `baseline.spec_approved` → `baseline.design_approved` → `design.ready`; per session, the Designer's turns, time and tokens with `cached_in` apart, and the screens written per target; per UI stage, the `design_pending` and `design_stale` intervals; per preview, the deploy's time and its domain's `memory.peak`; per review, its subject (candidate or owner build), its time, the deltas by kind and target and the evidence by provenance; per asset approval, the time from approval to the integration of its `asset_updated` work; per Designer session, the one-shot runs of its project that ran beside it (G12); per project, slots by effective source, unbound slots and `not_checkable_yet` conventions by target. M6's real runs (C-sketch M519, M535) record them, so `designer_session_budget_billable_tokens` and `preview_memory_max` are revisited on measurements.

## 14. Boundary and security notes

The Designer's turns are `role` domains with D2's mount plan and the proxy as their only egress; nothing changes there. **Mockups and assets are role- or owner-written files.** The engine parses the design's JSON with closed schemas, reads SVG as text and raster files by their headers only, and executes none of the tree (§5.6). The preview's server and its simulation frame are the engine's own, read-only and hashed; the design tree is served as data. Mockup scripts run in the **owner's browser**, at the relay's `127.0.0.1` origin: the engine's API is a unix socket the browser cannot reach, and the operator relay is opened only by the owner's command, but a mockup script can reach any other service listening on the owner's loopback, as any page he opens can; the pinned-URL allowlist bounds what it loads, not what it does (§15 class C). A simulated mockup runs in a sandboxed iframe without same-origin, so it cannot alter the frame's label. **SVG assets are refused if active** (script, event attributes, external references; `DESIGN_ASSET_SVG_ACTIVE`), because an SVG opened directly runs its script and a Builder places assets in the product. Owner-supplied asset files are validated before they are committed. **Owner-supplied review evidence** (§10.5) is checked by magic bytes and size, stored as records, never decoded beyond its header, never executed and never placed in the product; screenshots reach the role's package as images, as the owner's words reach it as text, and are data, never instructions. Under `design_preview: stack` a stub runs only as a service domain's application with D4 §9.2's isolation. Fixtures are engine-generated or validated against the inventory's shapes, so no fixture carries a real record; the owner's typed feedback is redacted as every transcript (D1 §14.2). The engine's fetches of the Alpha's served files for review go through the service link and the redactor, bounded, and are records, never instructions to the role (D2 §2.1).

## 15. What D7 does not claim

**Class A.** An owner who approves a design he did not look at, or a simulation he took for the device; a Designer that draws what the owner asks when he asks for something unwise.

**Class B, not built.** Native preview or execution for `android`, `ios`, `macos`, `windows` or `linux`: no emulator, simulator, device runner or desktop build in the preview or the review; native checks of §5.3's conventions; packaging checks against platform guidance and any store submission (§6.6); token bindings generated for Swift, Kotlin or Dart (Builders read the neutral file); image generation and any raster asset the Designer could draw; rendered screenshots, pixel or perceptual comparison, and any browser in the engine or the check toolchain (question 3); previews that run a technology's runtime unless question 2 is answered so; **native building, packaging and device testing** of any target (the owner-invoked review of §10.5 records his build and evidence; it builds and runs nothing); a component library or design-token export to a third-party tool; designs for Beta or Live beyond §6.7's hook.

**Class B, not yet established:** that a Designer session produces a design an owner approves, for one target or several; that a simulated mockup is faithful to what the native technology can build; that a UI Builder given the design implements it; that §7.2's static checks catch what a person would call off-design; that the design session's cost is near §13's guess; that Builders' declared bindings are where the app really loads its assets, so that an approved replacement reaches the screen. Each is the real runs' to show (M519, M535), and none is a property a test can pin.

**Class C.** **Coverage is not quality:** the design check proves that every UI requirement, state obligation and required convention has a screen and a declaration on each target, and that every declared text pair meets AA arithmetically; it never proves a screen is usable or beautiful, nor that a declared back destination or safe-area rule is honoured. **A simulation is a drawing:** the label says so, but a simulated permission prompt or back gesture shows intent, not behaviour, and a verdict given on one is recorded as such. **Static checks are approximations:** `layout_at_width` reads CSS rules, not a rendering; a layout broken by content length or a script is invisible to it; contrast is checked on declared token pairs, not on every pixel; `state_marker_present` proves a marker exists in the files, not that the state is reached or appears. **Asset checks read headers:** format, size and alpha channel, never what the image shows or whether it is legible at small sizes; `transparency: forbidden` refuses an alpha channel even when every pixel is opaque. **Placeholders may reach Alpha and Beta**, by design (§6.7). **Bindings are declarations:** a `copy` binding is digest-checked at integration, but that the app shows the file at that path is the human test's to judge, and a `derived` binding (a rendition) is recorded with its source version and never compared. **Owner builds and device evidence are his word:** the engine cannot tell whether a build identifier names a real build, which candidate it came from, or whether a screenshot shows that build; it records them labelled owner-supplied and never as its own observation. **The human-test requirements** stay pending until the owner judges them, and the review's verdict is his word, recorded. **Mockup scripts** run in the owner's browser with that origin's reach to his loopback (§14). **Fixtures** are plausible data from shapes, not representative data. **The inventory** is as good as the Architect's shapes and permissions; an undeclared error case or permission has no state obligation.
