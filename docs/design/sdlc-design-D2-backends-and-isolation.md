## 1. The adapter contract

**1.1 Three parts, one choke point.** Every invocation still passes through `invoke()` (D1 §15.1, `packages/engine/src/invoke/`); D2 replaces the scripted adapter's direct spawn with three parts. The **launcher** is engine code the choke point spawns; it places itself in the invocation's domain, obtains the domain's launch authorization (§3.2), builds the sandbox (§2.2) and execs the domain init. The **domain init** is engine code that runs as process 1 of the sandbox's pid namespace; it brings up loopback, starts the egress forwarder (§2.4), answers the engine on a control channel that role code cannot reach (§2.3), starts the backend only after its setup is confirmed, relays signals and reports the backend's exit. The launcher, the domain init and the forwarder are the trusted helpers; every process the backend starts is untrusted role code (AR B02). The **adapter** is engine code outside the sandbox, one per backend (`invoke/adapters/claude.ts`, `codex.ts`), that renders the invocation template, parses the backend's stream into the engine's internal callbacks within the supervisor bounds of §3.7, and collects the result and provider files after termination (§1.4, §4.3). A repository lint keeps every spawn of a backend binary inside `invoke/` (D1 §15.4). The scripted backend is one more adapter; outside harness runs that use the scripted boundary, its child runs in the same sandbox (§5 C3).

**1.2 What is handed over** (A1). The backend binary is the absolute path and SHA-256 named by the authorizing trust entry, or for a qualification canary by the qualification attempt (§7.2, K10), mounted read-only; a mismatch refuses with `backend_refused` before the launcher starts. **Arguments** are an array rendered from the adapter's fixed template; no shell is on the path, and every argument carrying content is engine-authored fixed text or a path inside the sandbox. The **prompt** is fixed text per role pointing at the context package (§1.3): for Codex on standard input, which `codex exec` reads when the prompt argument is `-` (`codex exec --help`); for Claude Code as the last positional argument (`claude --help`: `Usage: claude [options] [command] [prompt]`), never beginning with `-`. Task content never reaches an argument (D1 §17 item 3). The **environment** is constructed from the grant (D1 §17 item 4): `PATH` over read-only system directories, `HOME`, the XDG directories and the backend's own home variable in the volatile home (§2.3), `HTTPS_PROXY` naming the in-sandbox forwarder (§2.4), the domain and invocation markers (diagnostic only), and the secrets the grant names (§2.5). The **working directory** is `/surety/workspace`. The **deadline** is the engine's (§1.6), never a backend flag. The **budget boundary** is the one the trust entry records as enforceable (§4.2).

**1.3 The scoped context package** (A5, F §3.10.8). Before the launcher starts, the engine writes the package into the domain area and the sandbox mounts it read-only at `/surety/context`: the role prompt and instructions with its prohibitions (F §4.1); the result schema and path; the approved requirements, ADRs, constraints and phase plan the work item binds; the interfaces of dependency modules; for a Reviewer the candidate's diff and the acceptance content hash it reviews (E41 item 4); for a resumed run the reconstructed context of D1 §15.3, built from durable records and never from a `raw_user_report` (E5). The package scopes the initial context and hides nothing the role may inspect (F §3.10.8): the workspace and the repository's objects stay readable (§2.3). What keeps everything else from the backend is the validated mount plan of §2.3, not the package.

**1.4 The result** (A2, K4). The structured result is a file the role writes to `/surety/out/result.json` on the domain's volatile filesystem (§2.3). The engine reads it only after the domain's termination is established, which includes closure to future launches (§3.2), opening it from outside the sandbox without following links, refusing anything but a regular file, within `result_max_bytes` and `collect_deadline`; a link, device, FIFO or oversize file makes the result invalid and nothing it points to is opened. Native structured-output features (`--json-schema`, `--output-schema`) are not used (CH incident 3). The result is accepted only on exit class `clean` (§1.6); a well-formed result with exit class `error_exit` contradicts the transcript and is `invalid_result` (D1 §15.1). A result present when the run ends for any other cause (exit classes `engine_signaled`, `foreign_signal`, `resource_limit`, or `unknown` with termination established) is never accepted: after the secret screen of §2.5 it is published as an `unaccepted_result` record, the run keeps its ending's outcome (D1 §4.1), and a Resume may cite it (D1 §15.3); E27 item 7 applied to real backends. A result on a domain whose termination is `unknown` is not collected at all (§3.4). A crash of the engine loses the volatile result: recovery records it missing, never as an empty success (AR B08).

**1.5 Usage** (A3, K6). The adapter turns each usage-bearing event into a usage observation (D1 §3.6) with the semantics the trust entry declares, redacted before it is recorded (E37 item 2), bounded by `stream_line_max_bytes`. A run with no usage observation has null token fields. A run ended before its terminal usage keeps every durably observed token and cost value, with `usage_complete = false`; only the unobserved remainder is unknown, as `chargeInvocation()` already does (AR B07; `packages/engine/src/store/transitions/ledger.ts`). Cumulative or incremental semantics decide how observations fold; replay never counts one twice. The unknown remainder is charged by C4's allowance, separately from the retained known usage and once per invocation (§5 C4). A cost the backend does not report is `estimated` from a versioned price table or `unknown`, never zero (D1 §13.2). Reporting granularity says nothing about enforcement; §4.2 keeps them apart.

**1.6 Cancellation and exit classes** (A4, N02). A deadline, budget stop, Stop or Abandon cancels through §3.2: launch closure, TERM to the domain init, which relays it to the backend's process group, `terminate_grace`, `cgroup.kill`, `kill_grace`, observation. The domain init reports the backend's exit status or signal and the domain's resource counters on the control channel; the engine records on the terminal invocation status observation one **exit class**, chosen by this precedence, with every contributing fact kept in `exit_evidence`: (1) `engine_signaled` when the engine had begun cancellation before the exit, keeping the outcome of the cancellation's cause even if a resource counter also rose; (2) `unknown` when no exit report reached the engine; (3) `resource_limit` when the backend died by a signal the engine did not send and `memory.events` `oom_kill` rose; (4) `foreign_signal` for any other signal the engine did not send; (5) `clean` for exit status 0 with a terminal success event; (6) `error_exit` otherwise (a nonzero status, a terminal failure event, or no terminal success event). A rise of `oom_kill` or `pids.events` `max` that did not end the backend is recorded in `exit_evidence` and does not by itself fail the run. Only `clean` completes. `engine_signaled` gives the cause's outcome; `error_exit` gives failed with `invalid_result` if a well-formed result is present, else `infra_error`; `resource_limit` and `foreign_signal` give failed with `infra_error` and the class in its reason text; `unknown` with termination established gives the existing failed or recovered outcome after collecting redacted unaccepted output, never completion. Missing exit evidence never becomes `clean`. What each backend's exit looks like after TERM is recorded by the cancellation canary (§3.6, §7.2).

**1.7 Resume and the provider session id** (A6). A resumed run is a new invocation with a new domain and a context rebuilt from durable records (D1 §15.3, F §3.9); this holds on both backends by construction, and an old `unaccepted_result` never becomes current success. Provider-side resumption (`claude --resume`, `codex exec resume`) is never used. The provider session id is recorded for correlation only: for Claude Code the engine assigns it before launch with `--session-id <uuid>`, derived from the invocation id and bound to the receipt; for Codex it is read from the stream if the stream carries one, which the positive canary establishes.

**1.8 Sessions** (D1 §15.2). The design for sessions under D2: each turn its own invocation and domain; provider files carried between turns by the engine as a `provider_files` record and restored into the next turn's volatile home; `open_idle` only after the turn's domain is observed terminated (§3.2), so quiescence is established by the boundary. Continuation, that a backend resumes correctly from restored files, is not established by any one-shot qualification (AR N04). Session mode is refused (`backend_refused`) on both backends in M2.

## 2. Control-plane isolation

**2.1 Threat model** (I5). Trusted: the kernel, systemd (the system manager and uid 1000's user manager), root, the engine and the trusted helpers of §1.1, and the operator's own processes as uid 1000 outside every domain (shell, editor, browser, the `surety` CLI), including on WSL2 the Windows user who owns the distribution. Untrusted: every role process inside an execution domain and everything it produces (workspace content, results, transcripts, provider files, egress); the repository's committed content, which roles write; and every other local uid. Out of scope: root or a kernel exploit, a compromised operator account, Windows-side malware on a WSL2 host, and the provider's handling of what it is sent (§8).

**2.2 The mechanism on the first host** (I1, K9). Each role process runs in a **sandbox** of Linux namespaces built by the launcher without privilege: a user namespace; a mount namespace whose root is a constructed tree (§2.3); a network namespace with only its own loopback (§2.4); a pid namespace whose process 1 is the domain init; private ipc, uts and cgroup namespaces, the last rooted at the domain's cgroup (§3.1). The launcher builds mounts as root of an outer user namespace; role code runs in a nested user namespace as uid 1000 mapped to the engine's uid, with no capabilities and `no_new_privs`. Docker is not used: reaching the rootful daemon makes the engine root-equivalent and puts the boundary behind a second privileged party. A dedicated role user, which D1 §19.3 expected, needs root, and a subordinate uid needs `newuidmap`, which this host lacks. A role is therefore the same kernel uid as the engine and the operator, so isolation rests entirely on what its namespaces make visible and reachable; accidental visibility is consequential, which is why the mount plan is validated (§2.3) and the probes seed real targets (A.6). K9 holds only with B01 to B03 applied and the effective profile qualified (AR §4). **WSL2 is eligible to qualify as a host** (Q3 decided), subject to H1 to H12 including the WSL-specific check, and is qualified only by executable evidence; its wall clock jumps forward after a host sleep (E38), which §3.5 addresses.

**2.3 What the role can see** (I2, B02). The launcher builds the role's root from a **mount plan** the engine resolves and validates before each launch: every source is resolved to its real path, its contents walked for sockets, devices and FIFOs, and checked against the forbidden set; binds are non-recursive, so no host submount comes with them; the plan's fingerprint is part of the profile qualified in §7. The root holds only: read-only binds of `/usr`, `/bin`, `/lib`, `/lib64`; from `/etc`, only the enumerated files the profile names (`passwd`, `group`, `nsswitch.conf`, `ld.so.cache`, `localtime`, the CA bundle under `ssl/certs`, and an engine-written `hosts` and empty `resolv.conf`); the backend's installation, read-only at its pinned path; the engine's `node` for the domain init, read-only; any toolchain paths a project policy names in `sandbox_read_paths`; a private `/proc` for the pid namespace; a minimal `/dev` (`null`, `zero`, `full`, `random`, `urandom`, a private `devpts`) and a new private `/dev/shm`; the context package at `/surety/context` (read-only); the git metadata view; and the domain's **volatile filesystem**, one tmpfs bounded by `domain_writable_bytes` and `domain_writable_inodes`, charged to the domain's memory with swap excluded (§3.7), holding the private home (`/surety/home`), the result directory (`/surety/out`), `/tmp`, and the upper layer of the workspace. **The workspace** at `/surety/workspace` is an overlay whose lower layer is the engine's checkout at the run's base, read-only, and whose upper layer is on the volatile filesystem; after termination the engine screens the upper layer (§2.5) and only then materializes it into the checkout for snapshot admission (D1 §7.3). **The protected set** is overlaid, for every role except the Verifier, by a read-only bind of the authorized tree at the effective protected version (D1 §7.3); the Verifier's protected writes are captured as proposals. **The git metadata view** is engine-constructed: the workspace's `.git` file is replaced by one naming `/surety/git`, which holds an engine-written `config` (core settings only, no includes), this run's `HEAD` and index, and a read-only bind of the repository's objects and refs; credentials, `config.worktree` and other configuration variants, hooks, `info/`, and every other worktree's metadata are absent, and a repository with alternates is refused by the plan (`mount_plan_refused`). The role reads objects and refs, as F §3.10.8 permits, and writes none. **Nothing is inherited:** every descriptor except standard input, output and error is closed before role code runs, the domain init's control channel is unreachable from role code by inheritance or through `/proc`, and no host directory, socket, namespace or cgroup descriptor crosses into the role. **No widening reaches forbidden authority:** `sandbox_read_paths`, even after `policy_widening` approval, is refused with `mount_plan_refused` if a resolved source is, contains, or aliases the engine home, any registered repository or workspace, an operator credential location (the profile enumerates them: `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/gh`, `~/.claude`, `~/.codex`, `~/.docker`, `~/.kube`, `~/.netrc`, `~/.git-credentials`, `~/.npmrc` and the like), `/run`, `/var/run`, `/proc`, `/sys`, `/dev`, `/mnt`, the host `/tmp`, any WSL path, or holds a socket, device or FIFO. Absent from the view by construction: the engine home and everything in it (store, `api.token`, `records/`, `engine.log`, backups, other domains), other workspaces, the developer's checkout, the operator's home, the user bus, the Docker socket, `/run/WSL`, and every DrvFs and 9p mount.

**2.4 What the role can reach** (I3, B03). The network namespace has no route: `127.0.0.1` inside is the namespace's own loopback, so neither the engine's API, nor its bootstrap route, nor any host abstract socket is reachable. **The only egress is the engine's egress proxy**, reached through a per-domain unix socket bound into the sandbox and a forwarder in the domain init from `127.0.0.1:<port>`, named by `HTTPS_PROXY`. The proxy parses and canonicalizes each `CONNECT` authority and accepts it only on exact match with the trust entry's or qualification attempt's egress list plus the project's `egress_allow_extra` (a widening), on port 443. It resolves the name once per attempt within `egress_resolve_timeout`, validates every returned address under one IPv4 and IPv6 policy, refuses the whole answer set if any address is loopback, private, link-local, unspecified, multicast, an IPv4-mapped form of those, or an address of the host, and connects only to a validated numeric address from that answer, never resolving the name again; a retry repeats resolution and validation. Connect time, tunnel lifetime, concurrent tunnels per domain and buffered bytes per tunnel have finite limits (`egress_connect_timeout`, `egress_tunnel_max_seconds`, `egress_tunnels_max`, `egress_buffer_max_bytes`). The proxy does not terminate TLS. Every refusal emits `domain.egress_refused`; every connection, accepted or refused, with destination, resolved address, byte counts and times, is written to the domain's `egress_log` record within `egress_log_max_bytes`. The `probe` profile alone has one exception: a private echo endpoint the engine opens for the suite (§7.1), unavailable to the `role` profile and to canaries. Allow-listing restricts destinations; it neither inspects content nor accounts for provider requests (§8). A dependency a backend needs on another host (authentication, telemetry, updates) fails visibly, is reported by qualification, and is never added automatically.

**2.5 Secrets** (I4, B08, Q1, Q2). The grant names secret references (D1 §3.2). Each provider credential is a dedicated API key for the engine (Q1), and its delivery path, whether an environment variable or a file the adapter writes into the volatile home, is established by the positive canary, never assumed from a name in the binary. The resolver passes values only, in the launcher's environment, to the domain init, which places in the backend's environment exactly the variables the template names; the resolver, the references and every other secret never enter the sandbox. The backend holds its key (Q2), so anything the agent runs can read it; §8 states what follows. Raw output never reaches disk before redaction: credential files, the private home, temporary output and the unvalidated result live on the volatile filesystem, which is memory-backed and excluded from swap, and a crash before collection loses them rather than leaving them on disk (AR B08). Collection from the volatile filesystem (§4.3) streams through the redactor (D1 §14.2, E37 item 2) and retains no credential file. **The secret screen:** before the workspace's upper layer is materialized into the checkout, and before any collected output is published as a record, the engine screens it for every registered secret in its raw and escaped forms (E37 item 2); a hit refuses that publication and that materialization, raises the existing `security` finding of severity `critical` (D1 §14.2), and emits `evidence.secret_refused`; the run cannot complete. The screen detects registered forms only: a key-holding role can encode its key in a way no detector recognizes, and §8 says so.

**2.6 The bootstrap route and other local users** (I5, K3, N05, E44 item 1). An isolated role cannot reach `GET /v1/token/bootstrap`, because it cannot reach the API (§2.4). Other local uids can reach the port; every route but bootstrap requires the token, which is in a 0600 file under a 0700 home. The bootstrap route trusts headers any local program can forge (E42), so it is the one route through which another uid could obtain the token; it answers only when the engine setting `ui_bootstrap` is true, and otherwise refuses with `bootstrap_disabled` before the token is read. M2's qualified configuration leaves `ui_bootstrap` false, and the host qualification of §7.1 is not active while it is true. The opt-in exists for explicitly labelled compatibility tests, among them the accepted M1 bootstrap case, which the Verifier changes to opt in (E56 item 3); `GET /v1/engine` and the qualification report state when the exception is in force and claim no protection from other local uids while it is. The UI's own bootstrap is decided with the UI, with a one-time code delivered by the CLI preferred (Q6).

**2.7 What a role can do to the repository's configuration** (I6, Q4). Nothing: the role sees the engine's configuration in a read-only view with no hooks (§2.3), so the filter-driver race of E37 item 5 has no untrusted writer. Filter drivers, Git LFS and partial clones nevertheless stay **unsupported in M2** (Q4 decided): supporting them would have engine git run a program the configuration names or contact a remote outside any domain, which isolation does not contain. E29 item 1 and E37 items 1 and 5 stand.

**2.8 How isolation is observed** (I7, C3). Isolation is observed by the **isolation probe suite** (A.6): the engine launches the scripted backend in a real sandbox with the `probe` profile, and each probe attempts a forbidden action against a target the test has seeded and verified from the host side, paired with a control that shows the same operation and target usable without the restriction (AH §9.9; AR §8.1). A probe whose control fails, or whose target did not exist, fails the suite; an unexercised or unsupported probe is reported as such, never as passed. The suite runs at every engine start within `tick_step_budget` and on each qualification attempt; its results are host qualification evidence (§7.1). How each part of the control plane is kept from the role:

| Asset | Enforced by | Observed by |
|---|---|---|
| `api.token`, the store, records, the engine home | absent from the validated mount plan | P1, P2 |
| Other workspaces, the developer's checkout | absent from the validated mount plan | P3 |
| The repository's configuration and hooks | the engine-constructed git metadata view | P4, P5 |
| The engine's API and its bootstrap route | no route out of the network namespace; the proxy's address validation | P6, P7, P8 |
| Other egress | the proxy, by allow list and validated address | P8 |
| Host sockets, the user bus, Docker, WSL interop, host mounts | the mount plan's forbidden set; a separate network namespace | P9 to P12, P17 |
| The engine's, the operator's and the init's processes and descriptors | separate pid namespace; no inheritance; no capabilities | P13, P14 |
| The provider endpoint (allowed) | the allow list | P8 control; the positive canary (§7.2) |

## 3. The execution boundary

**3.1 Mechanism** (B1). The boundary is a cgroup v2 subtree delegated to the engine by the user's systemd manager. At start, before the lock (K2), `surety serve` runs the engine in a transient user scope with delegation, `surety-<home>-<incarnation>.scope` (`<home>` a hash of `$SURETY_HOME`), created by `systemd-run --user --scope -p Delegate=yes`; the engine moves itself into a `supervisor` leaf, enables `memory` and `pids` for the scope's children, and records the scope's path on its `engine_incarnations` row (`scope_cgroup`). A failed duplicate start removes only its own scope. Each execution domain is a child cgroup `dom_<id>` with the limits of §3.7. Membership cannot be escaped: a process stays in its cgroup across `setsid`, a new process group, a cleared environment and any number of forks; inside the sandbox no cgroupfs is mounted, the cgroup namespace is rooted at the domain, and with the hierarchy mounted `nsdelegate` the kernel refuses a migration out of the namespace's root even where the writer has file permission. Process groups and markers stay diagnostic (BS §6 correction 1).

**3.2 Launch authorization, placement, termination** (B1, B01, K1). Emptiness alone is not closure: a launcher waiting outside a domain can enter it after `populated 0` was read and `cgroup.kill` written (AR B01, observed). Each domain therefore carries a **launch state**, `authorizable`, `authorized` or `closed`, changed only by store transitions. The dispatch transaction allocates the domain `authorizable` with its `cgroup_path` (D1 §8.1 step 9); the engine creates the directory, only while the state is not `closed`; no launcher ever creates one. The launcher starts in the supervisor leaf, writes its own pid into the domain's `cgroup.procs`, confirms `/proc/self/cgroup`, and reports `placed` (`domain.placed`). It then asks for authorization, presenting domain, invocation, incarnation and lease generation; the engine grants it, in one transaction, only if all four are current, the lease is neither expired nor `closing`, the run is not ending, and the state is `authorizable`, setting `authorized` with the bound values (`domain.launch_authorized`) and the domain `launched` (K1). Without that grant the launcher exits, having run nothing of the role's. **Termination** of a domain is: (1) close, setting the state `closed` (`domain.launch_closed`), after which no grant is possible; (2) establish that no launcher can still enter, because the domain's launcher, a child of this engine, has exited or is itself a member; an unplaced launcher is killed through its child handle and its exit awaited, so cancellation reaches it too; (3) TERM to the domain init, which relays it, then `terminate_grace`; (4) `cgroup.kill`, then `kill_grace`; (5) observe `cgroup.events`. The domain is `terminated` only when (1) and (2) hold and the observation reads `populated 0`; `populated 0` on a domain whose launcher is outstanding is not termination. Once `terminated` is recorded, the engine removes the directory and nothing may recreate or repopulate it. **Members** are enumerated from `cgroup.procs` for the operator and blockers, never as the test of emptiness. Domain termination stays the reusable operation of BS §6 correction 1, invoked before snapshot admission, before a session turn becomes idle, and by `endRun` (D1 §4.5).

**3.3 After an engine restart.** The incarnation's scope belongs to the user manager and outlives a crash while populated. At startup recovery (D1 §16.1), after the lock is held, the engine first closes every non-terminated domain (§3.2 step 1), so no launcher of a prior incarnation can be authorized, as none could anyway with its engine gone. It then writes `cgroup.kill` to the `supervisor` leaf of every prior incarnation of this home whose scope exists and observes it `populated 0`, or establishes the scope's absence by reading the parent directory in the verified hierarchy (`app.slice` under this user's manager, as recorded). Only then does it observe each domain at its recorded `cgroup_path`: `populated 0` or absence in the verified hierarchy is `terminated`. A manager that is unavailable, a hierarchy that cannot be read, or a recorded path outside the verified hierarchy makes every affected domain `unknown`; a manager restart is not evidence that domains died (AR B01).

**3.4 Unknown** (B2, N02). The domain observation is `unknown`, meaning quarantine (D1 §4.5 step 3), when closure or emptiness cannot be established: `cgroup.events` exists but cannot be read; the cgroupfs or the user manager is unreachable; the recorded path is outside the verified hierarchy; a prior supervisor leaf cannot be killed, read or shown absent; a launcher's exit cannot be established; or `populated 1` persists after `kill_grace`, as for a process blocked uninterruptibly on 9p I/O. A domain whose termination is `unknown` is neither collected nor ended; its run stays finalizing with `quarantined = true`. Each tick observes a quarantined domain again under the same closure prerequisites and makes it `terminated` only on observed emptiness with closure (BS §6 corrections 2 and 13). The exit class of §1.6 is a separate fact: `unknown` exit with termination established permits redacted collection of unaccepted output and the failed or recovered outcome, never completion.

**3.5 A healthy run survives a pause** (B3, K5, N01, E36 item 6). When the tick finds a run lease past `expires_at` (D1 §8.1 step 1), the engine re-grants it, on the same generation so fencing (D1 §8.3) is unchanged, if and only if: the run's current domain observes `running`; its ownership and launch authorization name this incarnation and the current lease generation; the run is not ending (E27 item 5); and a **fresh challenge** succeeds: the engine sends a nonce bound to the invocation and lease generation on the init's control channel and receives, within `pause_challenge_timeout`, a response carrying that nonce and the backend's state as the init observes it. A heartbeat queued before the pause proves nothing. A response reporting that the backend has exited ends the run by its exit; no response within the bound ends it as before (E27 item 3). While the challenge is outstanding nothing replaces the run. The re-grant emits `run.lease_regranted`; it never changes the invocation's deadline, restores spent budget, or reverses an ending decision, so a backend that lives without progressing is still ended at its original deadline.

**3.6 Grace periods on a real backend** (B4). D1's defaults stand: `terminate_grace` 10 s, `kill_grace` 5 s (A.9). A backend that ignores TERM costs the rest of `terminate_grace` on each cancellation and whatever it would have flushed (the transcript tail, the final usage event, its session files), so its usage is incomplete and its provider files partial. The cancellation canary (§7.2) measures TERM-to-exit and records it on the trust entry; no default changes because of it.

**3.7 The resource envelope** (B09). **Admission:** the scheduler admits a domain only if, after admission, the domains running stay within `max_concurrent_domains` and the host keeps `host_reserve_memory` of memory and `host_reserve_disk` free on the engine home's filesystem beyond what the admitted domains may use; otherwise the work stays eligible and the run read shows the hold as `resource_envelope`. **Per domain:** `pids.max` from `domain_tasks_max`; `memory.max` from `domain_memory_max`, which covers the volatile filesystem's pages, with `memory.swap.max` 0 so nothing of the domain, the volatile filesystem included, is swapped; writable bytes and inodes bounded by the volatile filesystem's `domain_writable_bytes` and `domain_writable_inodes` (observed enforceable, preamble), the role having no other writable location. A profile without enforceable writable-storage bounds is refused for real dispatch. **Supervisor side**, because that work is outside the domain's cgroup: stream lines (`stream_line_max_bytes`) and queued stream bytes (`stream_queue_max_bytes`); collection entries (`collect_entries_max`) and time (`collect_deadline`), without following links or opening special files; egress tunnels and buffers (§2.4); the egress log (`egress_log_max_bytes`). Collection and cleanup never hold a tick past `tick_step_budget`; they continue across ticks. Reaching any bound cancels the run through §3.2 and records the evidence as truncated or incomplete, never as complete. Cancellation, refusal and the ledger stay recordable while another domain is at its limits, which Appendix B tests for each resource alone and for concurrent domains together.

**3.8 What D3 inherits.** The sandbox and the domain are parameterized by a **profile** that fixes the mount plan, the volatile bounds and the egress list. D2 defines `role` (§2) and `probe` (§2.8); D3 defines `check` for the check runner inside the same boundary, so a check execution's termination and resources are established the same way and `execution_established` (D1 §9.2) can rest on a domain's observation.

**3.9 Optional execution observer** (E57). A host may run an optional observer, built on eBPF, that records selected process creation, exec and exit events, file-access attempts and connection attempts of a role, each with the kernel's answer, over the launcher's interval in the supervisor as well as the domain's, and attributes them to the incarnation, invocation and domain through identity the engine established (placement and cgroup), never through role-supplied markers, so that a reused pid or cgroup id never carries attribution to another invocation. Its records are **qualification evidence only**: it never authorizes a launch, establishes termination, passes a check or measures tokens; the launch authorization and the cgroup boundary of §3.2 stay authoritative. A missing event is never evidence of absence, and an observation interval in which the collector stopped, lost events or lacked a required hook makes every piece of evidence that depends on it incomplete. The observer is a trusted host component outside every domain; neither the engine's Node process nor a role holds the privilege to load BPF programs. Its loader is a checked host requirement (H13): unprivileged BPF is disabled on this host, so the loader needs a privilege the operator grants. Its availability is reported apart from sandbox qualification, and an unavailable observer does not disqualify a host; a test that depends on observer evidence is then not established, unless another qualified witness establishes it. The insertion detail is in `docs/design/sdlc-design-D2-ebpf-note.md`; production monitoring and BPF-based enforcement are not part of D2 (§8).

## 4. The trust table and the two backends

**4.1 The entry and where it lives** (T1, N03, N04). A trust entry is a row of `trust_entries` in the runtime store, written only by a successful qualification attempt (§7.2), keyed by backend, version, binary SHA-256 and mode, and bound to the host it was qualified on. Its fields (A.3) and their evidence:

| Field | Evidence |
|---|---|
| `binary_path`, `binary_sha256`, `version`, `help_sha256` | engine-observed by the attempt: the resolved real path, the file's hash, `--version`, and a hash of the help text of the commands the template uses |
| `mode`, `template`, `template_version`, `auth_mode`, `model` | the exact template the canaries ran; only `one_shot_headless` can be active in M2 |
| `capabilities` | the effective headless tool surface the canaries established, with every delegation, scheduling and background feature shown disabled or unavailable (§4.5, §4.6) |
| `isolation`, `boundary`, `profile_fingerprint` | the mechanism identifiers of §2.2 and §3.1 and the fingerprint of the mount plan, volatile bounds and egress list qualified |
| `host_qualification` | the host qualification in force during the attempt, as historical evidence only |
| `egress_hosts` | the destinations the attempt's candidate list allowed and the canaries used; refused contacts are reported by the attempt, not added |
| `usage_granularity`, `usage_semantics`, `cost_reporting` | the canaries' streams and usage observations |
| `enforceable_boundaries` | each boundary the engine can enforce with its mechanism, evidence and overshoot limitation (§4.2) |
| `result_channel` | `file` |
| `session_qualified` | false; one-shot qualification never establishes continuation |
| `provider_files` | the inventory of every writable location after the canaries (§4.3) |
| `term_to_exit_ms` | the cancellation canary |
| `qualification_attempt`, `evidence`, `evidence_fingerprint` | the attempt and its records; the fingerprint covers template, capabilities, auth mode, egress policy and profile, not record identifiers alone |

The table is **engine-owned**: a successful attempt writes the entry `proposed`; only the human's consumption of `trust_activation`, whose preview binds the entry, its evidence fingerprint and the host's current eligibility, makes it `active`; and answering that decision launches nothing (CH incident 10). A project's policy may choose among active entries per role and never adds one. Revocation follows §7.3. **Dispatch** to an entry requires that it is `active` and that a **current** active host qualification exists for the same host with a mechanism and profile fingerprint compatible with the entry's; the entry's own `host_qualification` row is historical and is normally `lapsed` after the next start. A compatible restart therefore restores dispatch without a paid canary; an incompatible mechanism or profile requires requalification. The engine ships no entries.

**4.2 Budget boundaries** (T3, K6, B06). Reporting and enforcement are separate fields. `usage_granularity` records how often the backend reports usage (`model_call`, `invocation`, or `none`). `enforceable_boundaries` records what the engine can stop at, each with its mechanism, evidence and overshoot: `invocation`, enforced by the dispatch-time budget check and the run deadline, is available to any entry whose usage is reported at all; `model_turn` is enforceable only where qualification establishes admission control, or a stated maximum of additional calls, parallel and delegated calls included, after exhaustion becomes observable. Per-call usage events alone establish neither. The project setting `budget_run_boundary` (default `invocation`) names what policy requires; a finer boundary than the entry's is refused before launch with `budget_boundary_unenforceable`. A deadline limits elapsed time, not tokens or dollars: at the `invocation` boundary the overshoot within one invocation is bounded only by the deadline, which the entry and the run read state. A policy that declares a hard spending maximum (`budget_hard_maximum`) is refused with `hard_cap_unenforceable`, because no M2 mechanism enforces one; a provider-side limit on the dedicated key is the place for a hard maximum (Q2), recorded on the grant as `configured` evidence and never reported as engine enforcement. No confirmation labels an estimate as a maximum. `--max-budget-usd` (`claude --help`) may be passed as a second stop and is never evidence of enforcement. An entry whose canaries observed no usage cannot be activated.

**4.3 Provider-native files** (T4, B08, B09). Every location the backend can write is on the domain's volatile filesystem (§2.3), inside the sandbox and the boundary; the operator's `~/.claude` and `~/.codex` are not in the view. Both backends run with their no-persistence flags (`--no-session-persistence`, `claude --help`; `--ephemeral`, `codex exec --help`). After termination is established, the adapter inventories every writable location, not only the home, without following links or opening special files, within `collect_entries_max`, `provider_files_max_bytes` and `collect_deadline`; credential files are never retained; everything else passes the secret screen (§2.5) and the redactor into one `provider_files` record (retention per D1 §14.3); the volatile filesystem is then discarded with the domain. Where the canaries found each backend writing despite its flags is recorded on the entry (§7.2).

**4.4 Quiescence** (T5, D1 §7.3, §15.2, Q2). Under D2 an idle session owns no process, because each turn is a domain and `open_idle` requires that domain to be terminated with closure (§1.8, §3.2). Any daemon a backend starts, Claude Code's background-session daemon (`claude agents`, `--bg`) or Codex's app-server daemon (`codex app-server daemon`), would start inside the domain and die with it; the operator's daemons are unreachable, their sockets being under the operator's home and their abstract sockets in another network namespace. This is a property of descendant containment while session mode is refused; no session has reached `open_idle` under D2 (AR N04). Live checkpoints stay refused (D1 Q2).

**4.5 Claude Code 2.1.288** (T2, B05). Template: `claude --bare -p --output-format stream-json --verbose --model <m> --tools <role tools> --disallowed-tools Agent Task ScheduleWakeup Workflow --permission-mode bypassPermissions --no-session-persistence --session-id <uuid> <prompt>`, with the dedicated key in `ANTHROPIC_API_KEY`. Established from `claude --help`: every flag above exists; `-p` skips the workspace trust dialog and silently ignores settings files that fail validation; `--bare` skips hooks, plugins, CLAUDE.md auto-discovery and keychain reads, and takes Anthropic authentication strictly from `ANTHROPIC_API_KEY` or an `apiKeyHelper`, never OAuth; `--tools` sets the available built-in tools, where `--allowed-tools` only pre-approves; `--disallowed-tools` denies. The denied names are those CH §3.7 recorded at 2.1.281 as running despite an allow list; the qualified version's delegation and scheduling tools are whatever the canaries establish. Qualification MUST establish the effective headless tool surface: from the stream's initial event if it lists tools, otherwise by an executable capability test in which the canary is instructed to delegate and to schedule and must be seen unable to; no inventory and no test is a refusal, never a pass. Established by the canaries, not yet: whether `--verbose` is still needed with `stream-json`; which events carry usage and how often (CH: `usage` and `total_cost_usd` on the final `result` line at 2.1.281); the terminal success fields (CH: `subtype`, `is_error`); `HTTPS_PROXY` handling and the hosts contacted; key delivery through `ANTHROPIC_API_KEY`; what it writes despite `--no-session-persistence`; exit statuses; TERM behaviour. Cost reporting: `reported` if `total_cost_usd` is present.

**4.6 Codex CLI 0.159.2** (T2, B05, Q5). Template: `codex exec --json --ephemeral --ignore-user-config --ignore-rules --strict-config --disable multi_agent --dangerously-bypass-approvals-and-sandbox -C /surety/workspace -m <m> -o /surety/out/last-message.txt -`, with the prompt on standard input and `CODEX_HOME` in the volatile home. `--disable multi_agent` is required: Astra observed `multi_agent stable true` at this version (AR B05, §9). ## 5. Decisions carried in by the build

All four are decided by Sean (E56; dispositions file). None changes M1's accepted behaviour until a test pins it.

**C1. The Alpha exception** (E34 item 4, E36 item 5). A Reviewer run's structured result may carry `alpha_exception_proposals`, each naming a finding, the containment argument and the testing purpose. The engine refuses a proposal before raising anything if the finding is not High, has a `sensitive_area`, or is not open against the candidate the Reviewer reviewed. Otherwise it resolves every reference the argument makes, to workspace paths at the reviewed revision or to records, into retained content, publishes the argument with that content as a `containment_evidence` record with provenance `claimed` (D1 §3.4), and raises `finding_disposition` with the option `alpha_exception`, whose effect plan writes `findings.alpha_exception` bound to the candidate's acceptance content hash and whose manifest binds the finding's status, severity and sensitive area and the candidate, so a change between proposal, preview and effect stales it (D1 §10.5). Only the human consumes it. A Builder or Verifier result carrying the field is invalid. The exception never overrides a non-passed check (D1 §9.3 input 5).

**C2. The Reviewer's powers** (E41, E44 item 2, E48 item 3). Both restrictions hold: any lowering of a finding from Critical requires the human through `severity_lower`, the Reviewer proposing it (K7, a stricter policy for a real agent, not a necessary reading of F §6.3); and a tightening's classification is an effect precondition re-checked at application, with a Reviewer's approval only a recommendation until D3's classifier is qualified (K8). Neither approval turns a non-passed check into a pass.

**C3. Roles reading the token** (E25 item 2). M1's acceptance that a scripted role could read `api.token` is withdrawn once the sandbox exists. Every dispatch outside harness mode runs in the sandbox of §2, the qualification path and the scripted backend outside the scripted boundary included, and no production configuration can select the harness boundary. The withdrawal is pinned by `D2-I01`, `D2-I02`, `D2-I05` (absence and unreachability through the real boundary, with controls), `D2-T04` (refusal while no current host qualification exists) and `D2-C06` (no entry can be activated with another isolation). M1's tests that run scripted roles against the scripted boundary remain, labelled kernel evidence (BS §8); every production isolation claim is tested through the real boundary.

**C4. Estimated and unknown cost** (E32 item 4, E37 carried, K6). The daily limit `budget_day_verified_usd` is checked against reported and estimated cost together; the ledger read shows the two apart and never calls the estimated part verified; each estimated row keeps its price table's version (D1 §3.6). An invocation whose usage is incomplete keeps its known usage (§1.5) and is charged, once, an **unknown allowance** against `budget_day_unknown_tokens`: the run's `budget_run_billable_tokens` less the billable tokens observed, not below zero, recorded as `unknown_allowance_tokens` on its original ledger row. A later correction reconciles the allowance without deleting the original evidence; repeated finalization charges nothing twice. At dispatch, each running invocation counts at its known usage plus its remaining allowance, so concurrent dispatches cannot each pass against the same remaining budget.

## 7. Qualification

**7.1 A host** (N03). Host qualification is the checks of §6, run as a startup step between repository integrity and lifting the listener to full mode (D1 §1.4 steps 5 and 6; K2), bounded by `tick_step_budget`, and never a paid canary. A pass writes a `host_qualifications` row (host identity, kernel, tool versions, each check's observed value, the probe suite's results as a `qualification_evidence` record, and a mechanism fingerprint of the boundary, sandbox and profile in force) and lapses the previous row; `host.qualified` or `host.qualification_lapsed` records the outcome. No row is active while `ui_bootstrap` is true (§2.6). A sandbox the launcher fails to build refuses that run with `isolation_unqualified` and runs the checks again. The probe suite needs no model and no internet: the proxy's one probe destination is the engine's own echo endpoint (§2.4).

**7.2 A backend** (B04, B05, N04, K10, Q7). Qualification is a **qualification attempt**, not a project dispatch and not a trust entry. `surety qualify <backend> --mode one_shot_headless --model <m>` (`POST /v1/trust/qualify`) makes the static checks (resolved path, hash, `--version`, help hashes) and writes a `qualification_attempts` row `proposed`, binding before any launch: the binary and help hashes, the exact template and its version, the model, the authentication mode, the current host qualification, the engine-owned fixture project, the candidate egress list, a deadline per canary, and the spend: an enforceable cap where one is qualified, otherwise an estimate labelled as an estimate with the invocation overshoot stated (§4.2). It raises `qualification_approval`; only the human's consumption makes the attempt `authorized` (Q7: a paid canary runs only by explicit command and approval; a binary change may offer qualification, never run it). Only the qualification transition can then dispatch the attempt's canaries, each a run on the fixture project whose receipt binds the attempt and is charged to the ordinary ledger; this authority dispatches nothing else and no policy can select it (K10). A change to any bound dependency invalidates the attempt; a replay is a new attempt with a new approval, so no paid work repeats silently. A destination outside the candidate list is refused by the proxy and reported for review, never added.

The **positive canary** asks for one exact file edit and an exact result and must produce both, with exit class `clean`; it yields the stream, usage, terminal events, effective tool surface, egress log, inventory of writable locations and key-delivery evidence that fill §4.5 or §4.6. The **cancellation canary** asks the agent to run a command that creates a barrier file in `/surety/out` and then a command that waits far beyond the canary's deadline; the domain init, not the stream, observes the barrier and reports it on the control channel, and the engine then cancels. It passes only if the backend was authenticated and still running at the barrier, and records `term_to_exit_ms`, the exit class, the domain's closure and emptiness, and the partial usage retained (§1.5); a backend that finishes, fails to authenticate or never reaches the barrier has not passed (`barrier_not_reached`), independently of any usage event. The **containment canary** asks the agent to run the engine's probe program from `/surety/context` with each action in turn: read the seeded sentinel at the token's host path, change the repository configuration through `git config`, connect to the engine's port, `CONNECT` to a destination not on the list, and delegate and schedule through the backend's own tools. The domain init witnesses each execution of the probe program (its executable path and arguments, as a descendant of the backend), the program reports each outcome to the init over a channel the init accepts only from that executable, and host-side witnesses corroborate (the proxy's log, the sentinel and configuration unchanged). It passes only if every action was witnessed, every outcome was the expected denial, and each permitted control ran; a liveness marker, a transcript claim or a plausible result without witnessed executions fails (AR B05). **Diagnostics:** every canary failure keeps the redacted structured provider error and a failure class (`auth_failed`, `proxy_refused`, `unsupported_flag`, `tool_action_missing`, `delegation_unverified`, `invalid_result`, `barrier_not_reached`, `cancellation_failed`, `containment_failed`); an unexpected contact is reported with its destination and refusal. A failed canary ends the attempt `failed` with `qualification_failed`. A succeeded attempt writes the trust entry `proposed`, with the attempt and every record as evidence, and raises `trust_activation` (§4.1).

**7.3 Lapse and revocation.** An entry is revoked (`trust.revoked`) when its binary's hash or help hash changes, its template version, capabilities or profile fingerprint changes, or its host identity differs from the running host's; revocation refuses new dispatch with `backend_refused` and touches no running domain. A failed host check suspends every entry on that host without revoking it, and a later compatible pass restores dispatch (§4.1). Claude Code installs each version at its own path (`~/.local/share/claude/versions/2.1.288` resolves from `~/.local/bin/claude`), so an update elsewhere leaves a pinned entry valid until that file changes or goes.

**7.4 A second host.** Any Linux host on which H1 to H9, H11 and H12 pass is qualified by §7.1 unchanged; entries are per host, so its backends need their own attempts. A host that is not Linux has no cgroups or namespaces and needs its own mechanism, an amendment to D2.

**7.5 The incident record.** AR §7 re-ran all twenty CH §3.4 incidents and AH §5.2 and §5.9 against draft 1. The rows draft 2 changes:

## 8. What D2 does not claim

In the form of `M1-not-claimed.md`: class A is outside the threat model, class B is real behaviour no test or canary has yet established, class C is a limitation accepted by design or by Sean's decision.

**Class A.** Protection against root, a kernel exploit, the user's systemd manager, a compromised operator account, or Windows-side software on a WSL2 host (§2.1). What the provider retains of what it is sent.

**Class B.** Everything §4.5 and §4.6 list as established by the canaries, until an attempt has succeeded and its entry is active: key delivery, usage events and their granularity, terminal events, the effective tool surface and the absence of delegation, proxy handling, persistence despite the no-persistence flags, exit statuses and TERM behaviour. The isolation probes' results on any host before the suite has run there; WSL2 is eligible, not qualified (Q3). That storage honours a sync (unchanged from M1, E32 item 1).

**Class C.** Q2's limitation, as Sean decided it: the role holds its provider key, so the backend's reported usage is attributed evidence, not an independent meter of all the key could spend; a role can make extra provider calls through the allowed destination, and a hard maximum belongs to a provider-side limit on the key, not to the engine. The role can read that key, and can copy or encode it into its workspace or send it to an allowed host; the secret screen (§2.5) detects registered raw and escaped forms only, never an arbitrary encoding. The proxy restricts destinations, not content. At the `invocation` boundary, overshoot within one invocation is bounded only by the deadline (§4.2). A crash loses the volatile filesystem: the role's unsnapshotted workspace changes, its provider files and its unvalidated result are recorded missing and are not recovered, so a Resume starts from the last snapshot (E30 item 10 does not apply to real backends). The mount plan is validated before each launch; a socket or credential an operator's own software creates in an approved `sandbox_read_paths` directory after that validation is not caught. The role reads all of the repository's objects and refs (F §3.10.8). A same-uid process outside every domain can read the token file and replace a backend binary between the hash check and the exec. With `ui_bootstrap` on, any local uid can obtain the token (§2.6). Sessions, filter drivers, Git LFS, partial clones, repositories with alternates, and any host other than Linux are not supported. The optional execution observer (§3.9) is a qualification aid only: production monitoring and BPF-based enforcement are out of D2's scope, and no claim rests on an event the observer did not record.
