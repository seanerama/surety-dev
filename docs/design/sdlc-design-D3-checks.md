## 1. The protected acceptance path at runtime

**1.1 The governed set** (P1). As built, the protected set of a revision is every file under the protected roots; the roots are the `protected_paths` of the governed file `.surety/checks/protected-policy.json`, default `[".surety/checks/"]`, and that file is always protected; the fingerprint is SHA-256 of the sorted `[path, blob id]` pairs (RN R2; BS §6 correction 3; E34 item 1; `src/protected/set.ts`; SEAM §66). That fingerprint omits Git type and mode, so a regular file and a symlink with the same content compare equal; correction L6 replaces it with the manifest of §1.3 (B01). M1 stores the other five governed fields and gives them no meaning. D3 gives each a closed schema (A.4); an absent field, and each absent member of one, takes the default A.4 enumerates with its unit, and no default is derived from the host environment (N04):

- `check_discovery`: `{"definitions": "<dir>"}`, default `.surety/checks/defs/`, a directory under a root. It names where definitions are; it can name no program (§1.4).
- `check_commands`: the programs a definition may run, `{"<name>": {"path": "<absolute path>", "sha256"?: "<hex>"}}`. Every definition's `command[0]` is a name here; the path lies under D2 §2.3's read-only system directories or `runner_config.direct.read_paths`. Pinning `sha256` is optional; every execution records the resolved program's path and hash whether pinned or not (Q6, decided (a); the limitation is §6). Default `{}`: no check runs until a person approves a program.
- `runner_config`: per runner class; only `direct` is defined (§2.8): `read_paths` (toolchain directories bound read-only, each validated against D2 §2.3's forbidden set), `path` (the check's `PATH`), `env` (constant variables for every check), `egress_allow` (hosts a definition may name, through D2 §2.4's proxy), `timeout_max_s`. Keys for `container` and `remote` are refused while those classes are unqualified. The toolchain a check runs is governed here rather than through D2's `sandbox_read_paths`, which is an ungoverned project setting for roles: what a check runs is part of the protected path (F §5.2).
- `result_collection`: `{"output_max_bytes": <n>}`, within the engine's `check_output_max_bytes`. Nothing here can make a verdict depend on output: the verdict is the exit status of the check's own process (E8).
- `required_checks`: an array of check keys; absent, every discovered check is required. A listed key with no definition is a discovery error.

A governed value outside an engine bound (`check_timeout_max`, `check_output_max_bytes`) is the discovery error `invalid_value`; it is never clamped.

**1.2 The layout.** `.surety/checks/protected-policy.json` holds the governed fields; `.surety/checks/defs/<key>.json` holds one check definition each; everything else under a root (the checks' code, expectations, fixtures, data) has a free layout and is protected content a check reads through its inputs. The engine parses only the governed file and the definitions. Appendix B is a definition example the spec template can point to.

**1.3 A check definition** (P1). A JSON object, schema version 1, closed (A.4):

| Field | Meaning |
|---|---|
| `key` | the file's stem, `[a-z0-9][a-z0-9._-]{0,63}`; a check is identified across versions by its key (SEAM §69) |
| `kind`, `origin` | `CheckKind` (D1 A.2); `CheckOrigin` `acceptance` (default) or `developer` (§2.9) |
| `command` | an argument array of 1 to 64 strings; `command[0]` a name in `check_commands`; no shell is ever interposed |
| `cwd` | a workspace-relative directory, default `.`; absolute paths and `..` refused |
| `env` | constant string variables; none may name a variable the engine sets (§2.3) |
| `timeout_s` | 1 to `runner_config.direct.timeout_max_s` |
| `covers` | `{"criteria": ["R<n>.<m>"], "sensitive_areas": [SensitiveArea]}`: an acceptance-origin check of kind `acceptance`, `integration`, `property` or `failure_recovery` names at least one criterion, and the requirements it covers are those of its criteria; `sensitive_areas` appears only on kind `sensitivity_floor`, which names at least one; a developer check covers nothing |
| `gate_kinds`, `tier_floor`, `phase` | as the `checks` row (D1 A.3); `tier_floor` absent on `sensitivity_floor` |
| `runner_class` | `RunnerClass`, default `direct` |
| `requires` | a subset of `environment`, `artifact_digest` (as built, `checks.requires`, SEAM §71); non-empty only on post-deploy kinds (§5 X3) |
| `inputs` | the protected paths the check reads: files, or directories ending `/`, under a root, never the governed file; default every file under the roots but the governed file (Q3, decided (a)). They expand to the check's input manifest (below); the `check` profile presents exactly that (§2.2), so the declaration is enforced |
| `egress` | hosts, a subset of `runner_config.direct.egress_allow`; default none |

**What a check produces** is one exit status of its own process and one output record; schema 1 has no artifact or report field, and nothing else a check writes survives its domain (§2.2).

**The input manifest** (B01; correction L6). At discovery the engine expands a check's `inputs` at the version into a canonical **input manifest**: the entries `[path, type, mode, object id]` of every permitted member, sorted by path. A directory input is a projection of its permitted members, never a bind of the directory: overlapping directory inputs yield each member once, and the governed file is never a member, wherever it lies. In the first runner only regular files (modes `100644` and `100755`) are permitted members: a symlink, a submodule or any other entry type among a check's inputs is the discovery error `input_not_regular`. Type and mode are part of identity: a regular file replaced by a symlink to the same content, or an executable bit changed, is a changed input, never an unchanged blob.

The engine derives each check's **check fingerprint**: SHA-256 over the canonical definition, its input manifest, and the governed entries it uses (its `check_commands` entry, `runner_config.direct`, `result_collection`). The as-built column `checks.definition_hash` holds it; the parsed definition and the manifest are stored on the row (`checks.definition`, `checks.input_manifest`, A.3).

**1.4 Discovery** (P3). Discovery is a function of a tree, never a program. Given a tree (a version's commit, or a proposal's `tree_id`), the engine reads the governed file and lists `check_discovery.definitions` with engine git (`ls-tree`, `cat-file`), which runs no repository code and contacts no remote (E25 item 3, E29 item 1, E37 item 1; `src/git/exec.ts`), and parses each regular-file blob named `<key>.json` against the closed schema. Nothing is executed, expanded as a pattern or followed. A symlink, submodule or other entry in the definitions directory, a definition over 64 KiB, more than 512 definitions, invalid JSON or a JSON object with a repeated member name, a repeated criterion, input or required key, an unknown field or value, an input outside the roots, naming the governed file or not a regular file, a program not in `check_commands`, a criterion or area the approved spec does not have (§3.4), or a `required_checks` key with no definition is a **discovery error** with its path and `DiscoveryError` code; discovery never drops a definition silently, because a dropped check is a loosening nobody approved. Discovery runs on the main thread, as `src/gates/prepare.ts` reads git before a transaction, within the bounds of §2.4, and its output is frozen: for the initial version at project creation, and for a proposal at classification (§3.3), where it is stored on the proposal and written as the new version's `checks` rows by the application's finalizer (D1 §7.9; BS §6 correction 14, finalizer inputs frozen at intent). The fixture that declares checks (SEAM §67) stays, harness-only. A version's errors are recorded on it (`protected_versions.discovery_errors`) and recomputed when the spec revision changes (§3.4); while the effective version has any, every gate of the project carries `ACCEPTANCE_SCOPE_INCOMPLETE` naming the paths (D1 §9.1, "uncertain"). A proposal with errors cannot be approved (L5).

**1.5 Materialization at the effective version** (P2). An execution sees the candidate's source at `source_revision` with the protected roots replaced, never merged, by the input manifest of the check at the protected version it was registered under, which is the effective version at registration (§2.5); the candidate's own copy of the protected paths is never mounted, and the governed file is absent from every projection, the candidate-source projection included, even when it lies outside the configured roots (B01). Protected content not in the check's manifest is absent from every path the domain can see. The candidate's copy is ignored rather than the gate blocked, for two reasons: the gate judges a candidate against the effective version (D1 §9.3 input 2) and a result binds source and protected version separately (D1 §9.2), so a candidate nominated before a tightening is judged by the tightened checks; and a copy that is never mounted cannot influence a result. Blocking would stall every earlier candidate after any protected change and protect nothing more. Whether the protected set on the integration branch is authorized stays the integrity question it is (D1 §7.6, §9.3 input 2; §5 X1); the runner records the candidate's own fingerprint on the execution (`candidate_protected_fingerprint`) so a difference is visible in the read.

**1.6 The Verifier's proposals** (P4). As built and pinned: a Verifier run whose diff is exactly protected changes is captured as a proposal with its snapshot tree (D1 §7.3 step 2; SEAM §68), and a human's governed edit through the policy route becomes a proposal whose tree differs in the governed file only (D1 §11.4; SEAM §66). D3 adds what follows: at the next tick the engine discovers the proposal's tree and the effective version's tree and classifies (§3), replacing the classification fixture (SEAM §67), which stays harness-only. `affected_checks` MUST include every key whose definition, input identity, required membership or applicability changes, each entry with its reasons (`AffectedReason`, A.2); a change of the required set is visible even when the check fingerprint is unchanged (N01). Under default inputs a change to any file under the roots affects every check.

## 2. The check runner

**2.1 What it is.** The engine component that executes one check definition against one candidate in one execution domain of profile `check` (D2 §3.8) and records what it observed as one `check_results` row. Its unit is the **check execution** (`check_executions`, A.3): registered, materialized, launched, observed, collected, recorded. An execution is not a run: no role, no model, no invocation receipt, no capability grant. It reuses D2's launcher, domain init, volatile filesystem, boundary and resource envelope, with the check execution in the place of the invocation on every launch, closure, recovery, resource and projection path, a domain allocated before `started` included (correction L1). Its code lives under `src/checks/`, which joins the places permitted to start a process (E39 item 7) and the lint that enforces them.

**2.2 The `check` profile** (R1, R2; D2 §3.8). The mount plan is resolved and validated before each launch exactly as D2 §2.3 validates a role's:

| Location | Content |
|---|---|
| `/usr`, `/bin`, `/lib`, `/lib64`, the enumerated `/etc` | read-only, as D2 §2.3 |
| `runner_config.direct.read_paths` | read-only at their own paths; any that is, contains or aliases D2 §2.3's forbidden set refuses the launch (`mount_plan_refused`) |
| `/surety/workspace` | an overlay: lower layer the candidate-source projection of the check tree (§2.4), read-only; upper layer on the domain's volatile filesystem, discarded with the domain |
| each entry of the check's input manifest, at its workspace pathname | read-only, in an **immutable input namespace**; protected content not in the manifest is absent |
| `/surety/home`, `/tmp`; `/proc`, minimal `/dev`, private `/dev/shm` | volatile; as D2 §2.3 |

Absent, compared with the `role` profile: a backend installation, the context package, `/surety/out`, any git metadata (the check tree has no `.git`), any provider key or grant secret. The network namespace has only its loopback; D2 §2.4's proxy is bound only when the definition names `egress`, with exactly those hosts. Volatile and resource bounds are D2 §3.7's per domain, and admission is its envelope.

**The writable overlay** (E89 item 2, accepted). R1 asks the source to be read-only except where the check declares it writable. D3 gives the check a writable overlay whose writes are discarded, because toolchains write caches and reports in places no declaration lists correctly, and discarding gives the property the declaration was for: nothing a check writes reaches the candidate, the checkout or another check.

**Inputs are immutable at their pathnames** (B01; correction L6). The `check` profile MUST enforce the identity of each protected input at its workspace pathname for the entire execution: neither check code nor candidate code may rename, remove, exchange or replace the input or any of its ancestors in a way that changes what that pathname resolves to. A read-only bind beneath a writable ancestor is insufficient, since renaming the ancestor frees the pathname for a replacement (AD §9), and directories created as mount targets exist only in the overlay's upper layer. The mount plan MUST provide an immutable namespace for the inputs while keeping the discarded writable source overlay; D3 fixes the property, not the construction. A mount target whose ancestor in the source projection is a symlink, or whose resolution would traverse one, refuses the launch (`mount_plan_refused`). Qualification MUST refuse a profile that cannot enforce these properties (§2.8). The profile's fingerprint joins the mechanism fingerprint of the host qualification (D2 §7.1). **No host requirement is added:** H1 to H12 cover what the profile uses.

**2.3 The environment.** Constructed, never inherited (D1 §17 item 4): `PATH` from `runner_config.direct.path`; `HOME=/surety/home`; `TMPDIR=/tmp`; `LANG=C.UTF-8`; `TZ=UTC`; `CI=true`; `runner_config.direct.env`; the definition's `env`; the identifiers `SURETY_CHECK`, `SURETY_CANDIDATE`, `SURETY_SOURCE_REVISION`, `SURETY_PROTECTED_VERSION`; `HTTPS_PROXY` only with egress; the domain marker (diagnostic, D2 §1.2). No secret reaches a workspace check (§5 X3 reserves secrets for environment-bound checks).

**2.4 Materialization** (R1). Before launch the main thread builds, or reuses, the **check tree** of a (project, source revision, protected version) triple under `$SURETY_HOME/checktrees/`: with engine git, `read-tree` of the revision into a private index and `checkout-index --prefix`, omitting the files under the version's roots and the governed file wherever it lies (probe above), which is the candidate-source projection; and the version's protected files beside it, from which each check's manifest is projected. Files are made read-only; a tree is immutable, shared by every execution of its triple, and removed when none references it. The tree is engine-owned like `workspaces/` and never named by policy. It has no `.git`, so a check cannot read history or the repository's configuration; submodules, LFS and filters stay unsupported (D2 Q4). **Bounds** (T17): preparation is bounded in entries (`checktree_max_entries`), in bytes per tree (`checktree_max_bytes`) and for all trees on the host (`checktrees_max_bytes`, admitted before a build starts), and in time (D2's git deadlines); an unreadable revision, a deadline or a bound is `materialization_failed` (§2.7). A tree is built in a private staging directory and becomes visible to executions only once complete; a failed build removes its partial state; a tree is keyed by project, so no execution reads the same relative path from another project's repository. Discovery and materialization keep the API and cancellation responsive within D2 §3.7.

**2.5 Registration, triggers and scheduling** (R4, R5).

**Registration decides** (B03; correction L7, which corrects D1 §9.2). One engine transition registers an execution and allocates its `execution_seq` from the project's one durable sequence (D1 §3.3, "assigned by the runner registration transaction"). The same sequence numbers the harness fixture's results and supplies the disposition watermark (§2.11), so the three never collide and nothing derives a sequence from the results recorded. Registration, not completion, orders executions: of the matching registrations of a check for a candidate the latest decides whichever finishes first, and until it has a usable recorded result the check is `missing`, the gate is unsatisfied and the gate read names the execution and its condition (queued, materializing, running, quarantined, collecting, interrupted, cancelled). It MUST NOT fall back to an earlier pass or reuse entry. Registration, and every change of whether an execution can decide (recorded, quarantined, interrupted, cancelled), stales the dependent evaluations in the same transition. Registration freezes the check row of the version, the candidate, its revision, the protected version effective at registration, the definition's runner class, the trigger, and, from an environment trigger only, environment and artifact (§5 X3).

**Triggers** (`CheckTrigger`): `nomination`, every check of the union of the required sets of the `stage` gates of the stages the candidate holds and of its `alpha_authorize` gate (§4.2), the fix's candidate that E43 nominates included; `protected_application`, from the application's finalizer, the new version's checks in the required sets of every candidate with no `superseded_by`; `operator_request`, by route (A.7), re-running named or all required checks of a candidate; `recovery` (§2.7); `deployment_verification`, reserved (§5 X3). The trigger identity is `(source, id, generation, check key)`: replaying a trigger registers nothing new; two operator requests are two triggers; a recovery registration is the next generation of its original trigger, whose `infra_retries` count survives a restart (T05). No role's result can register an execution or write a result: role result schemas have no such field, and the fixture route exists only in harness mode (E23 item 4).

**When registration happens** (correction L2, with Astra's variant). In the trigger's own transition: the application's finalizer registers with the invalidation it performs (§3.5); the route registers in its transaction; recovery registers in the transition that ends the interrupted execution. A nomination whose required set needs facts read from the candidate's tree (module presence, §4.1) registers in its finalizer from facts frozen at intent, or records `checks_due` on the candidate there; while a candidate has checks due, every evaluation of it treats each check of the due registration as `missing`, naming it. Either way, Gates can never consume evidence older than a registration the trigger owes.

**Scheduling.** A tick step "Checks" after Gates (correction L2) admits queued executions oldest first within D2 §3.7's envelope, where a hold shows as `resource_envelope`, and the project's `max_concurrent_checks` (default 1, so a candidate's checks run one at a time), and continues supervision and collection. Executions are not runs: the project concurrency of exactly one run (BS §6 correction 20) does not count them, and a check may run while a role's run holds the project, because it reads an immutable revision and writes nothing of the repository. Each execution holds a lease of kind `check` (L1), renewed while supervised and re-granted after a pause exactly as a run's (D2 §3.5), never extending `timeout_s`. **Binding at launch** (T19): dispatch needs the host qualification and the runner qualification current at launch, not at registration; an execution whose class has none then records `runner_unqualified` (§2.7); the execution and its result persist the runner identity, the qualification and the resolved program hash actually used, and a frozen historical result is never relabelled under a later qualification. **Supersession** (T15): a queued execution whose candidate or protected version is superseded before launch is cancelled with no row (`check.cancelled`); one already running is recorded under its version, which §9.2 then makes `stale`; a result of a candidate with `superseded_by` never triggers a repair (§2.10) or resolves a finding (§2.11), and never authorizes a promotion (§7.4 Q9 asks how).

**2.6 Launch, observation, and what is established** (R2, R3). The launcher places itself in the domain and obtains a launch authorization bound to domain, check execution, incarnation and lease generation (D2 §3.2, with L1). The domain init brings up loopback and the forwarder if any, opens the output capture, and execs `check_commands[command[0]].path` with `command[1..]`, the constructed environment and `cwd`: the check's own process, under no shell and no wrapper of the engine's. On its control channel the init reports `started` once the exec has succeeded (a close-on-exec pipe; a failed exec reports its errno instead), then the exit status or terminating signal of that process. **At that process's exit, before it drains output or tears anything down**, the init observes whether any other process remains in the domain and reports it (`orphans`), the init being process 1 to which orphans are reparented; the observation stands even if the descendant ends during cleanup, and it does not depend on the descendant holding output open (correction L4; T08; as built, `src/invoke/domain-init.ts` drains output before reporting an exit, and the check init MUST observe first). The engine then terminates the domain with closure (D2 §3.2), whatever the check did.

**`execution_established` is true if and only if the engine itself recorded** the domain launched under an authorization bound to this execution, the init's `started` report, and the domain terminated with closure. It never derives from the check's output or exit status, or from anything a process in the domain wrote: only the init's reports on a channel that check code cannot reach (D2 §2.3), so check code's standard output, standard error or writes aimed at the control descriptors cannot forge `started` or an exit. The other fields: the exit status the init reports for the check's own process ending of itself is `exit_status`; a signal the engine did not send, an OOM kill included, sets `signaled` with `exit_status` null; a cancellation at `timeout_s` sets `deadline_hit` and `signaled`; an exit the init reports after the engine began terminating the domain for any reason (deadline, cancellation, recovery) is never `exit_status`, so a check the engine stopped is never `passed`, however it handled TERM (T07); established with no exit report (the init died, the channel failed) leaves `exit_status` null. D1 §9.2 makes each of these `failed`, and `orphans` too (correction L4; CH 17: a check that leaves work running did not finish it). Known not started (a launch refused before authorization, an `exec_failed` report) is a row with `execution_established` false and a `not_run_reason` (§2.7), which §9.2 makes `skipped`. **Unknown** (D2 §3.4): while the domain's termination is `unknown` nothing is collected and **no row is recorded**; the execution is `quarantined`, from `materializing` as well as from `running` once a domain is allocated, the check is `missing` in evaluations, and the gate read names the quarantined execution. The row is recorded only when termination with closure is observed, from the reports the init had made. No row rather than a `skipped` row, because `skipped` would claim the runner knows the check did not run.

**Interrupted** (T07). When the engine restarts during an execution, recovery first establishes its domain's closure by D2 §3.3; until then the execution and its domain stay nonterminal, before `running` too. An execution whose exit report the engine had recorded is then collected and recorded as usual. Any other ends `interrupted`, with **no row**: a check that may have started is never recorded as not started, and one the engine stopped is never recorded as failed or passed. A domain that ended with neither a `started` nor an `exec_failed` report is treated the same way. The check is `missing` meanwhile, and recovery registers it again (§2.7); retries wait for closure.

**Output** (R2). The init captures standard output and error, interleaved, onto the volatile filesystem, keeping the first and last halves of `output_max_bytes` and counting what it dropped; output volume never cancels a check. After termination, collection under D2 §1.4's rules (no link followed, bounded entries and time) passes the secret screen and the redactor (D2 §2.5; D1 §14.2) and publishes a `check_output` record named by `check_results.output`. **Every established result names its output record**, an empty one when the check wrote nothing. A screen hit refuses publication and raises D1 §14.2's critical finding; a result whose record is refused, absent or missing is `EVIDENCE_MISSING` on every evaluation that selects it (D1 §9.3 input 8), independently of that finding (T09; as built, `gates.ts` passes over an absent record id, which this corrects). No raw secret is published. Output never changes a field of the result.

**History beside the deciding result** (N03). For each deciding execution the gate read MUST expose the count and identities of earlier executions at the same bindings, failed attempts included, and a link to their ordered history (A.7). A successful rerun MUST NOT erase or relabel an earlier failure, and an operator's request stays distinguishable from a bounded infrastructure retry by its trigger.

**2.7 What cannot run** (R6). An execution the runner attempted and knows did not start records a row with `execution_established` false and one `NotRunReason`: `definition_invalid`, `toolchain_missing` (the program's path absent, or its pinned hash different), `materialization_failed`, `mount_plan_refused`, `isolation_unqualified` (no current host qualification), `runner_unqualified` (§2.8), `environment_unbound` (§5 X3), `exec_failed` (the init reported a failed exec). Each is `skipped` at the gate, which is therefore not satisfied (E41 item 2); the reason is on the gate read beside the check's state (E47); and the host-level reasons (`toolchain_missing`, `mount_plan_refused`, `isolation_unqualified`, `runner_unqualified`) make the project's status line `refused` with cause `check_unrunnable` (D1 §12.3; E53 item 4). An `interrupted` execution (§2.6) and a `materialization_failed` one are registered again automatically, as trigger `recovery`, at most `check_infra_retries_max` times per original trigger, a restart resetting nothing; every other reason waits for what it names (a correction, a host fix) and then the operator's re-run. A registered execution never attempted has no row and the check stays `missing`. A genuine test failure is never retried as an infrastructure error.

**2.8 Runner classes** (R7; E89 item 2). `direct`, a check in a `check`-profile domain on the engine's host, is the only class D3 qualifies, and the class M3 builds. It is qualified on a host when the host qualification is active (D2 §7.1) and the **runner self-test** passed at the same start: scripted check programs in real `check` domains, each beside a control, whose results must be exactly: exit 0, passed; exit 1, failed; output "passed" with exit 1, failed; a foreign signal, failed; past the timeout, failed with `deadline_hit`; TERM handled with exit 0 after an engine cancellation, not passed; a missing program, skipped; a protected input written, renamed, exchanged, replaced, redirected through a symlink or aliased through a hard link, directly or through any ancestor, an ancestor created in the overlay's upper layer included, refused with the input's pathname still reading the protected bytes, while a source write succeeds and does not persist (B01); an orphan, with its standard output closed, failed; an undeclared egress refused while the declared one connects (CH 17, "the test runner is a gate too"; AH §9.9). **Every** mandatory case and its control MUST have run and passed: a `failed` or `not_exercised` case leaves `direct` unqualified, and an optional observer (E57) never substitutes for one (T18). The outcome is recorded on `host_qualifications.check_runner`. A successful self-test qualifies the runner, never a project's checks. Every result records `runner_id`, `direct@<host id>/<profile fingerprint prefix>`, and `runner_qualification`, the host qualification row in force at launch (§2.5), as a trust entry records its evidence (D2 §4.1). `container` and `remote` are not qualified: their definitions are discovered and their executions `runner_unqualified`. Before either can be qualified, `container` needs a rootless mechanism with D2's boundary guarantees (D2 §2.2 rejects the Docker daemon), termination with closure, and the same judgment (E8: one definition executes identically under every runner); `remote` needs a result channel the engine authenticates, binding the remote's observation to the registration, which is a design of its own. A result matches only its own class (D1 §9.2).

**2.9 Developer tests** (R8; F §5.4). A Builder's own runs of its tests are claims in its transcript (E12), never results. A project makes developer tests evidence with a definition of origin `developer`: definition, command and runner are protected like any check; the test files it runs are the Builder's, outside the roots. Its results are ordinary `check_results` rows of a check whose `origin` is `developer`. It may be required, so it can block a gate and must pass; it never covers a criterion and never counts toward the kind inventory, so it never stands for an acceptance check (§4.3). The Builder can change what it runs without the protected route, which is exactly why.

**2.10 A failed check and the repair loop** (R9; the question E38 left open, which the brief files under E37; Q2, decided (a), with T13's conditions). The rule applies to a `fix` item and to a `stage_build` item in `verifying`. The item's **current candidate** is the candidate nominated from its latest integration (for a fix, E43's fix candidate). Its **repair checks** are, for a fix, the check its finding names, and for a `stage_build`, the required checks of its stage's `stage` scope at the current candidate. The engine **reconciles durable state** rather than reacting to a result's arrival: in every transition that records a result, ends an execution or moves the item into `verifying`, and at each tick, if the item is `verifying`, some repair check's state at the current candidate by §9.2 (with L7) is `failed`, and no repair has been taken for this item, candidate and work generation, the engine sends the item back: `verifying → eligible` as an automatic repair (D1 §4.3), `repair_attempts` incremented exactly once for that transition however many repair checks failed, with every failed repair check's output record in the next run's context package (D2 §1.3). The repair records the candidate it was taken for (`work_items.check_repair`), so a restart or a repeated tick takes no second one. Only the latest registration's state counts, so an earlier failure finishing after a newer pass triggers nothing; `skipped`, `missing` (pending, quarantined, interrupted, cancelled, due) and `stale` are not the Builder's doing and never consume a repair; a result of a superseded candidate triggers nothing. The progress key (D1 §4.3) gains `(check, <key>, exit_status, signaled, deadline_hit)` for each failed repair check, so the same failure on an unchanged snapshot tree counts toward `no_progress_max`; either limit parks the item with a `blocker` naming the checks. A `contract_conflict` or `requirement_conflict` finding from the Builder's run wins over the repair and takes §5 X2's route.

**2.11 Resolving a finding** (F2, decided option (c), E90 item 4; correction L8; T20). A finding names the criterion it breaks: a role's finding gains `criterion`, an enum of the registered index's criteria in the run's result schema, as its `check` is an enum of the effective keys (E87 item 11, F1); a finding naming any other criterion is an invalid result, and nothing is stored. A finding dispositioned `fix` is resolved by an evaluation of a candidate it applies to (as built, SEAM §74) if and only if all of these hold:

1. the finding names a criterion and a check;
2. the named check, at the effective version, is of origin `acceptance`, covers that criterion (`covers.criteria`), and is in the required set of the evaluation's scope (§4.2);
3. its state there is `passed` by §9.2 with L7, and its deciding execution was registered after the disposition: its `execution_seq` is above the disposition watermark, which `recordDisposition` takes from the project's sequence of §2.5, registrations included, not from the highest recorded result as built (`src/store/transitions/queue.ts`; T06);
4. its evidence is intact: the execution established by the engine, its output record present (§2.6), its bindings current, and the result not invalidated.

An unrelated green check, a developer check, a check outside the scope's required set and a check that does not cover the finding's criterion never resolve it. **When no such check exists** (the finding names no criterion, or its named check is not a required acceptance-origin check of the effective version covering that criterion), the finding stays unresolved, a subject of `FINDING_UNSATISFIED` or `FINDING_BLOCKING` as now, the gate read names the missing verification, and the engine routes it for correction: in the transaction that records the `fix` disposition, or the one that makes a new version effective, it registers `check_correction` work for the Verifier triggered by the finding, the same work §5 X2's `correct_check` registers (§7.4 Q8 asks Sean to confirm this route). A Verifier who finds that the spec has no criterion for the defect reports a `requirement_conflict`, which takes §5 X2's route to `change_spec`. Whether the check really tests the defect stays the Reviewer's assessment (F §4.1): the engine checks the link, not the test's meaning. When the resolving execution is invalidated, the finding reopens, as built.

## 3. The diff classifier

**3.1 Definitions** (C1). `classify(P0, P1, S)` compares P0, the discovery of the effective version's tree, with P1, the discovery of the proposal's tree, against S, the registered requirement index (§4.5). Each difference, per check key and per governed field, is one **element** with a `ClassificationReason` (A.2):

- **Strict:** a check added with a valid definition; a check's `covers.criteria` or `gate_kinds` gaining values; `tier_floor` lowered or removed; a key added to `required_checks` together with the check it names.
- **Loosening:** a check removed; a check leaving the required set (its key removed from `required_checks`, or a list introduced that omits it); `covers.criteria`, `covers.sensitive_areas` or `gate_kinds` losing values; `tier_floor` raised or added; a root removed from `protected_paths`.
- **Unclassifiable:** any change of `protected_paths` other than a removal: a root added, changed or narrowed (`root_layout_changed`, B02); any change of `check_commands` (a new program is a person's decision even beside the new check that needs it), `check_discovery`, `runner_config` or `result_collection`; any change of an existing check's `kind`, `origin`, `command`, `cwd`, `env`, `timeout_s`, `runner_class`, `requires`, `inputs` or `egress`; any change in an existing check's input manifest, type and mode included; a key added to `required_checks` naming a check that already existed (C2); any discovery error in P1; and **any other semantic difference** in a definition, an input manifest or a governed field that no rule above places (`unhandled_change`), a `phase` change or a `covers.sensitive_areas` gain among them.
- **Neutral:** a changed file under the roots that is in no check's input manifest and is not the governed file, with the root layout unchanged.

Then: `initial` if and only if there is no effective version (project creation); otherwise `unclassifiable` if any element is, or if there is no strict and no loosening element; otherwise `loosening` if any element is; otherwise `tightening`. Classification MUST account for every semantic difference, and adding a strict element MUST NOT hide an unclassifiable one (B02). A tightening is therefore a proposal under which the root layout is unchanged, every check of P0 is kept with an identical check fingerprint or changed only by strict elements, the criteria and areas covered by P1's required checks are a superset of P0's, and something is strictly added. A changed input file is unclassifiable, not judged: E13's "new assertions, narrower accepted ranges" are statements about test code, which the classifier does not read (brief §7). **Why a root addition is never a tightening** (B02): an existing check's execution input is not only its declared inputs; the candidate source it sees depends on `protected_paths`, and hiding source can turn a failing check into a passing one with no protected file changed (AD's counterexample: a protected runner discovering tests under `src/` returns zero once `src/` becomes a root). Agent approval of a root addition waits for a classifier that proves every retained check's visible source and input namespace unchanged. Declared inputs are what make the remaining tightenings provable: a new check whose files lie outside every existing check's inputs leaves their fingerprints unchanged; under default inputs any new protected file changes every default-input check's, and the proposal is unclassifiable (Q3). The governed file is in no check's inputs, so `required_checks` moves a fingerprint only through the inputs it changes. The classifier reads trees, the governed file and the requirement index only, runs nothing, and records its `classifier_version` with each classification.

**3.2 The conservative fallback** (C2). In doubt, `unclassifiable`, which only the human approves (D1 §7.9). No change to `protected_paths`, `required_checks`, `check_commands`, `check_discovery`, `runner_config` or `result_collection` is a tightening by itself: a root removal is a loosening, every other change of the first and any change of the last four are unclassifiable, and `required_checks` contributes a strict element only beside the check it adds. A change to `required_checks` also needs the validation-scope approval, as built (`changes_required_set`, the option blocker `APPROVAL_MISSING`; E13; SEAM §69). A classification is never a judgment of a check's quality: a vacuous new check covering a criterion is a tightening by these rules (§6 class C). The controls for that are the Reviewer's assessment of test adequacy (F §4.1) and the protected delta shown at human gates (E13).

**3.3 Binding, revalidation and authority** (C3; K8). A classification is recorded on the proposal as `{change_kind, elements, affected_checks, effective_version, spec_revision, classifier_version, discovery}` with `protected.classified`, and routes as built (SEAM §69: a tightening stays `classified`; loosening and unclassifiable go `awaiting_human`). The three `check_correction_*` manifests, which already bind the classification, the effective version and the spec revision (SEAM §§77, 101), gain `classifier_version`, `classifier_authority`, the proposal's discovery and, where `required_checks` changes, the validation-scope approval; the spec revision's binding covers the requirement index's criteria and areas (§4.5; as built, `specRevision` in `src/store/transitions/baseline.ts` hashes key, text reference, phase and status only). **At application** the whole binding is an effect precondition (K8; D2 §5 C2; T10): immediately before the application's journal intent (D1 §10.5), and before a Reviewer's application begins, the engine re-reads every bound input and classifies again. If any bound input differs, or the class differs, the intent is invalidated with `EFFECT_PRECONDITION_CHANGED`, the approval withdrawn and the next generation raised, as SEAM §104 does for a moved branch, **even when the class is unchanged**; a replay after a restart is revalidated the same way. A Reviewer's approval carries no decision and no intent; the same check runs before its application begins and withdraws it the same way. Revalidation matters because an application writes the proposal's whole protected set: a check another application added meanwhile would be removed. **Authority** (Q5, decided (a)): the engine setting `classifier_authority` is `recommend` until the operator sets it `authoritative` naming the qualified `classifier_version`. Under `recommend` a Reviewer's approval of a tightening is recorded as a recommendation, provenance `claimed`, on the `check_correction_tightening` decision the human answers, and applies nothing (D2-C03). Under `authoritative`, and only while the running classifier is the version named, it is the authority F §4.1 and E13 give a Reviewer, and applies after revalidation. Losing that match (the setting changed, or a different classifier running) MUST also stop a Reviewer application already pending: its precondition fails, it is withdrawn as above, and the proposal goes to the human as under `recommend`. A classifier version is qualified when the kernel-lane classifier rows of Appendix C pass on it, B02's and T03's included.

**3.4 Reading the spec** (C4). Discovery and the classifier read the requirement index the engine registered from the approved spec (§4.5). A definition naming a criterion or area the index does not have is the discovery error `criterion_unknown` or `area_unknown`; the proposal is unclassifiable and its approval blocked (L5). That is M11's contradiction at the protected path: a check that contradicts the spec goes to a person, who has the Verifier correct the check or changes the spec through F §3.8; it is never a repair. A withdrawn requirement's criteria are unknown. When a spec revision removes a criterion a check of the effective version names, the version's discovery errors are recomputed against the new revision and the project's gates carry `ACCEPTANCE_SCOPE_INCOMPLETE` until a correction lands.

**3.5 Invalidation and reuse** (C5; Q1, decided (a)). An applied change invalidates in its finalizer every result recorded under the superseded version (as built, `invalidateResults` in `src/store/transitions/protected.ts`; SEAM §72), stales every evaluation (D1 §9.5), and in the same finalizer registers the new version's checks (trigger `protected_application`, §2.5), so the checks run without anyone asking and no gate meanwhile reads older evidence. Evidence reuse (D1 §9.1; BS §6 correction 18) is bounded by the classifier's notion of unchanged: a reuse entry counts only if the reused result's check fingerprint equals the fingerprint of the scope's check and, as built, the result's protected version is the effective one, so a result never crosses a protected change (M41; SEAM §103). There is no reuse across versions. D3 creates no reuse entry: checks cost no model, so the runner re-runs every required check for every candidate, and reuse stays a path for a later design (expensive environment checks) and for the fixture.

## 4. Validation scope at run time

**4.1 Scope modules, tier and cadence** (S1; M43). A scope's **modules** are, at `stage`, those its stage lists (`stages.modules`); at a deployment gate, every module with at least one file at the candidate's revision, read with the tree and recorded as a fact of the candidate, as ancestry is (`src/gates/prepare.ts`); at `phase`, those of the phase's stages. A deployment gate takes every present module, not those a diff touched, because it judges the state being deployed: a sensitive module changed in an earlier candidate must not escape the floor of a later one (Q7, decided (a)). A module absent at the revision drops out of the scope, but the disappearance of its files is no evidence that its external effects (stored personal data, say) disappeared; the deployment design accounts for those. An unread module fact is `ACCEPTANCE_SCOPE_INCOMPLETE`. The scope's **tier** is the highest of the project's tier and each scope module's `tier_override` (D1 A.3; F §5.6, "module overrides"); an override never lowers. The tier selects checks (`tier_floor`; as built, `applies` in `src/store/transitions/evidence.ts`), the kind inventory (§4.3) and sign-offs (as built in `buildScope`: T2 a Reviewer's at candidate scope; T3 also one per module and a security review), now from the scope's tier rather than the project's. **The scope tier also sets the verification cadence** of F §5.6 (B04; correction L3): integration of a `stage_build` whose `stage` scope's tier is T2 or T3 nominates by engine cadence even when the project's tier is T1 and no role asks (as built, the integration finalizer in `src/store/transitions/accept.ts` reads the project's tier only). A `fix` item has no stage; its integration takes the highest of the project's tier and the tiers of the modules present at its revision (§7.4 Q10).

**4.2 The required set** (S1). From the effective version's required checks that list the gate kind: (a) checks covering no criterion (release obligations, developer checks), at the scope's tier; (b) checks covering a criterion of an obligation requirement, at the scope's tier, the obligations being as built (at `stage` the delivered requirements its stage implements; at deployment gates the delivered requirements) and at `phase` every requirement assigned to the phase, delivered or not (RN R7); (c) every `sensitivity_floor` check naming a scope sensitivity category, whatever the tiers. `required_check_ids` is that set and `runner_classes` each check's class. `sensitivity_categories`, always `[]` as built, is the union of the scope modules' `sensitive_areas` and the `sensitive_areas` (§4.5) of every requirement the scope touches: at `stage`, every requirement its stage implements, delivered or partially delivered at the candidate; at deployment gates, every delivered or partially delivered requirement; at `phase`, every requirement assigned to the phase (B04). Partial delivery MUST NOT suppress a sensitivity floor; delivery and criterion-completeness claims stay D1 §9.1's. **One rule, every consumer** (B04; T12): check registration (§2.5), scope evaluation, the required sign-offs and the acceptance content hash (D1 §3.4) derive from these same rules through one function; as built, `contentHash` in `src/store/transitions/evidence.ts` hashes `sensitivity: []` with its own copy of the required-set rule, and both are replaced.

**4.3 When a scope is validated** (S1, S3; correction L3). A scope is `validated` if and only if:

- the required set is not empty;
- every criterion of every obligation requirement is named by at least one required check of origin `acceptance` in the set (a requirement registered with no criterion is **uncertain**, which gives M38's "uncertain" a reachable meaning);
- **the kind inventory of F §5.7 is present** (B04): for the scope's tier, the set holds at least one required acceptance-origin check of each kind: T1 `acceptance` and `smoke`; T2 also `integration` and `security_lint`; T3 also `property` and `failure_recovery`. A project's `required_checks`, `gate_kinds` or `tier_floor` cannot waive it, and developer-origin checks never count toward it; required sign-offs and the security review stay separate obligations (§4.1);
- every sensitivity category has at least one `sensitivity_floor` check in the set;
- the effective version has no discovery error; and every fact the scope needs (ancestry, module presence, the index) was read.

Otherwise the evaluation carries `ACCEPTANCE_SCOPE_INCOMPLETE` with each uncovered criterion, missing kind (`kind:<kind>`), area (`area:<name>`), definition path or unread fact among its subjects. The `phase` gate stays refused (`unsupported`; SEAM §70; BS §6 correction 9) until its milestone; its scope is defined here so that F §3.10.6's plan check ("every requirement assigned to the phase has required checks planned") can use the same coverage function.

**4.4 What a sensitive area requires** (S2; F §5.6, O1). For each area of the closed list (`SensitiveArea`, A.2) in a scope's categories: at least one required `sensitivity_floor` check naming it, at every tier and every gate kind evaluated, passing like any required check. D3 ships the requirement; the engine enforces existence, naming and passing; D3 ships no checks, because what a check establishes is the spec's and the Verifier's (brief §7). Appendix B gives the Verifier a one-line minimum per area as a starting point, not as the engine's test.

**4.5 The requirement index** (S3). From the approved spec (`.surety/spec/spec.md`) the engine reads only the requirement index of the template's section 5: one table row per requirement with key `R<n>`, title, phase, sensitive areas (from the closed list, or `none`) and criteria (`R<n>.<m>`, comma-separated). Registration at spec approval writes `requirements` rows with `criteria` and `sensitive_areas` (A.3); a row that does not parse, an unknown area, a criterion that is not of its requirement's key, or a repeated criterion refuses the approval and names the row. Until spec approval is built, the plan fixture supplies the same fields. A check names what it covers by criterion keys (`covers.criteria`, §1.3), and a finding names the criterion it breaks (§2.11); delivery comes from stages (D1 §9.1, unchanged), coverage from checks.

## 6. What D3 does not claim

In the form of `M1-not-claimed.md`: class A is outside the threat model, class B is real behaviour no test has yet established, class C is a limitation accepted by design.

**Class A.** As D2 §8 class A. A check the Verifier wrote to pass whatever the source does.

**Class B.** The runner on any host before its self-test has passed there; `container` and `remote`; the environment-bound check; the phase gate; spec approval's registration of the index (the fixture stands in). That a project's toolchain fails on every condition its checks care about: the definition must make it so (E8). Node 22's `node --test` exits 0 when every test is skipped and when none exists (probe above), so a definition that runs it bare is a vacuous check; the reference project's demonstration of this is a limitation, never evidence of guarded execution.

**Class C.** The verdict is the exit status of the check's own process: a check that runs candidate code in its own process can be made to exit 0 by that code (`process.exit(0)` in an imported module), and no runner can tell; a check should run candidate code as a child and judge what it observably does, which is the Verifier's construction and the Reviewer's assessment, not the classifier's. A protected command can itself hide a child's nonzero status; exit-only judgment cannot prove a wrapper honest. The runner self-test qualifies the runner, never a project's checks. The classifier judges structure, so a vacuous new check covering a criterion classifies as a tightening (§3.2); a root addition is never agent-approved (§3.1). The latest registration decides, so an operator's repeated re-runs of a flaky check can turn a failure into a pass; a pending rerun blocks (§2.5), and every execution is kept and shown beside the deciding one (§2.6). A finding resolves only through a required acceptance check covering its criterion, but whether that check tests the defect is the Reviewer's judgment (§2.11). A check sees no git history and no live repository metadata (it reads `SURETY_SOURCE_REVISION` instead); submodules, LFS and filters are unsupported. Toolchain drift between executions is recorded (each records the program's resolved path and hash) but prevented only where `check_commands` pins a hash, and a pinned program hash alone does not pin its libraries, packages or mutable toolchain directories: optional pinning is not an immutable toolchain, and the stronger reproducibility claim is the deployment design's (Q6). Output is kept head and tail within its bound. A check's writes are discarded, and a check produces no artifact in D3. The engine creates no evidence-reuse entry. A candidate's checks run one at a time by default.

## Appendix B. `.surety/checks/` at runtime: a definition example for the project's Verifier

This is a definition example, not a complete valid project's check inventory (N04): a T1 project also needs a `smoke` check, and each tier the kinds of §4.3.

```
.surety/checks/protected-policy.json
  {"protected_paths": [".surety/checks/"],
   "check_commands": {"node": {"path": "/usr/bin/node"}},
   "runner_config": {"direct": {"read_paths": [], "path": ["/usr/bin", "/bin"], "env": {}, "egress_allow": [], "timeout_max_s": 600}},
   "result_collection": {"output_max_bytes": 1048576}}
.surety/checks/defs/login-refuses-bad-password.json
  {"schema": 1, "key": "login-refuses-bad-password", "kind": "acceptance",
   "command": ["node", ".surety/checks/run/login.mjs"], "timeout_s": 120,
   "covers": {"criteria": ["R2.1"]}, "gate_kinds": ["stage", "alpha_authorize"],
   "inputs": [".surety/checks/run/login.mjs", ".surety/checks/expect/login/"]}
.surety/checks/run/, .surety/checks/expect/     the checks' code and expectations (free layout)
```

What the Verifier writes: one definition per check, its key the file's name; criteria named exactly as the spec's index has them; `inputs` declared, regular files only, so that a later added check is a tightening an agent may approve (§3.1; a new root never is); a command that exits nonzero on every condition the check cares about, a skipped or empty test run and a child's failure included (E8; §6 classes B and C), and that runs the candidate's code as a child process; for each tier the kinds of §4.3; for each sensitive area a requirement or module names, one `sensitivity_floor` check naming the area, with no `tier_floor`. A program change, a toolchain path, an egress host or an output bound is a governed change only the owner approves; every execution records each program's hash, and pinning `sha256` in `check_commands` is recommended when the checks gate a deployment, though it does not pin the program's libraries (Q6). A starting minimum per area (§4.4), not the engine's test: **authentication**, each entry point the spec names refuses an unauthenticated request; **authorization**, a user without the right is refused each protected action, by direct reference too; **payments and financial data**, amounts are exact and a repeated request charges once; **personal data**, personal fields are absent from logs and outputs not meant to hold them; **secrets and credentials**, no secret is in the repository, a log or a response; **data migrations and destructive operations**, the migration runs on representative data and the destructive operation needs the confirmation the spec names; **irreversible external actions**, none happens without its confirmation and a retry does not repeat it.
