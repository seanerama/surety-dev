## 1. The protected acceptance path at runtime

**1.1 The governed set** (P1). As built, the protected set of a revision is every file under the protected roots; the roots are the `protected_paths` of the governed file `.surety/checks/protected-policy.json`, default `[".surety/checks/"]`, and that file is always protected; the fingerprint is SHA-256 of the sorted `[path, blob id]` pairs (RN R2; BS §6 correction 3; E34 item 1; `src/protected/set.ts`; SEAM §66). M1 stores the other five governed fields and gives them no meaning. D3 gives each a closed schema (A.4); an absent field takes its default:

- `check_discovery`: `{"definitions": "<dir>"}`, default `.surety/checks/defs/`, a directory under a root. It names where definitions are; it can name no program (§1.4).
- `check_commands`: the programs a definition may run, `{"<name>": {"path": "<absolute path>", "sha256"?: "<hex>"}}`. Every definition's `command[0]` is a name here; the path lies under D2 §2.3's read-only system directories or `runner_config.direct.read_paths`. Default `{}`: no check runs until a person approves a program.
- `runner_config`: per runner class; only `direct` is defined (§2.8): `read_paths` (toolchain directories bound read-only, each validated against D2 §2.3's forbidden set), `path` (the check's `PATH`), `env` (constant variables for every check), `egress_allow` (hosts a definition may name, through D2 §2.4's proxy), `timeout_max_s`. Keys for `container` and `remote` are refused while those classes are unqualified.
- `result_collection`: `{"output_max_bytes": <n>}`, within the engine's `check_output_max_bytes`. Nothing here can make a verdict depend on output: the verdict is the exit status of the check's own process (E8).
- `required_checks`: an array of check keys; absent, every discovered check is required. A listed key with no definition is a discovery error.

**1.2 The layout.** `.surety/checks/protected-policy.json` holds the governed fields; `.surety/checks/defs/<key>.json` holds one check definition each; everything else under a root (the checks' code, expectations, fixtures, data) has a free layout and is protected content a check reads through its inputs. The engine parses only the governed file and the definitions. Appendix B is the short reference the spec template can point to.

**1.3 A check definition** (P1). A JSON object, schema version 1, closed (A.4):

| Field | Meaning |
|---|---|
| `key` | the file's stem, `[a-z0-9][a-z0-9._-]{0,63}`; a check is identified across versions by its key (SEAM §69) |
| `kind`, `origin` | `CheckKind` (D1 A.2); `CheckOrigin` `acceptance` (default) or `developer` (§2.9) |
| `command` | an argument array of 1 to 64 strings; `command[0]` a name in `check_commands`; no shell is ever interposed |
| `cwd` | a workspace-relative directory, default `.`; absolute paths and `..` refused |
| `env` | constant string variables; none may name a variable the engine sets (§2.3) |
| `timeout_s` | 1 to `runner_config.direct.timeout_max_s` |
| `covers` | `{"criteria": ["R<n>.<m>"], "sensitive_areas": [SensitiveArea]}`: an acceptance-origin check of kind `acceptance`, `integration`, `property` or `failure_recovery` names at least one criterion, and the requirements it covers are those of its criteria; `sensitive_areas` appears only on kind `sensitivity_floor`, which names at least one; a developer check covers nothing |
| `gate_kinds`, `tier_floor`, `phase` | as the `checks` row (D1 A.3); `tier_floor` absent on `sensitivity_floor` |
| `runner_class` | `RunnerClass`, default `direct` |
| `requires` | a subset of `environment`, `artifact_digest` (as built, `checks.requires`, SEAM §71); non-empty only on post-deploy kinds (§5 X3) |
| `inputs` | the protected paths the check reads (files, or directories ending `/`, under a root); default every root. The `check` profile mounts exactly these (§2.2), so the declaration is enforced, and the classifier can prove a check unchanged by a change outside its inputs (§3.1) |
| `egress` | hosts, a subset of `runner_config.direct.egress_allow`; default none |

The engine derives each check's **check fingerprint**: SHA-256 over the canonical definition, the sorted `[path, blob id]` pairs of its inputs, and the governed entries it uses (its `check_commands` entry, `runner_config.direct`, `result_collection`). The as-built column `checks.definition_hash` holds it; the parsed definition is stored on the row (`checks.definition`, A.3).

**1.4 Discovery** (P3). Discovery is a function of a tree, never a program. Given a tree (a version's commit, or a proposal's `tree_id`), the engine reads the governed file and lists `check_discovery.definitions` with engine git (`ls-tree`, `cat-file`), which runs no repository code and contacts no remote (E25 item 3, E29 item 1, E37 item 1; `src/git/exec.ts`), and parses each regular-file blob named `<key>.json` against the closed schema. Nothing is executed, expanded as a pattern or followed. A symlink, submodule or other entry in the definitions directory, a definition over 64 KiB, more than 512 definitions, invalid JSON, an unknown field or value, an input outside the roots, a program not in `check_commands`, a criterion or area the approved spec does not have (§3.4), or a `required_checks` key with no definition is a **discovery error** with its path and `DiscoveryError` code; discovery never drops a definition silently, because a dropped check is a loosening nobody approved. Discovery runs on the main thread, as `src/gates/prepare.ts` reads git before a transaction, and its output is frozen: for the initial version at project creation, and for a proposal at classification (§3.3), where it is stored on the proposal and written as the new version's `checks` rows by the application's finalizer (D1 §7.9; BS §6 correction 14, finalizer inputs frozen at intent). The fixture that declares checks (SEAM §67) stays, harness-only. A version's errors are recorded on it (`protected_versions.discovery_errors`) and recomputed when the spec revision changes (§3.4); while the effective version has any, every gate of the project carries `ACCEPTANCE_SCOPE_INCOMPLETE` naming the paths (D1 §9.1, "uncertain"). A proposal with errors cannot be approved (L5).

**1.5 Materialization at the effective version** (P2). An execution sees the candidate's source at `source_revision` with the protected roots replaced, never merged, by the authorized tree of the protected version it was registered under, which is the effective version at registration (§2.5); the candidate's own copy of the protected paths is never mounted. The copy is ignored rather than the gate blocked, for two reasons: the gate judges a candidate against the effective version (D1 §9.3 input 2) and a result binds source and protected version separately (D1 §9.2), so a candidate nominated before a tightening is judged by the tightened checks; and a copy that is never mounted cannot influence a result. Blocking would stall every earlier candidate after any protected change and protect nothing more. Whether the protected set on the integration branch is authorized stays the integrity question it is (D1 §7.6, §9.3 input 2; §5 X1); the runner records the candidate's own fingerprint on the execution (`candidate_protected_fingerprint`) so a difference is visible in the read.

**1.6 The Verifier's proposals** (P4). As built and pinned: a Verifier run whose diff is exactly protected changes is captured as a proposal with its snapshot tree (D1 §7.3 step 2; SEAM §68), and a human's governed edit through the policy route becomes a proposal whose tree differs in the governed file only (D1 §11.4; SEAM §66). D3 adds what follows: at the next tick the engine discovers the proposal's tree and the effective version's tree and classifies (§3), replacing the classification fixture (SEAM §67), which stays harness-only. `affected_checks` is the set of keys added, removed, or whose check fingerprint differs between the two discoveries; under default inputs a change to any file under the roots affects every check.

## 2. The check runner

**2.1 What it is.** The engine component that executes one check definition against one candidate in one execution domain of profile `check` (D2 §3.8) and records what it observed as one `check_results` row. Its unit is the **check execution** (`check_executions`, A.3): registered, materialized, launched, observed, collected, recorded. An execution is not a run: no role, no model, no invocation receipt, no capability grant. It reuses D2's launcher, domain init, volatile filesystem, boundary and resource envelope, with the check execution in the place of the invocation (correction L1). Its code lives under `src/checks/`, which joins the places permitted to start a process (E39 item 7) and the lint that enforces them.

**2.2 The `check` profile** (R1, R2; D2 §3.8). The mount plan is resolved and validated before each launch exactly as D2 §2.3 validates a role's:

| Location | Content |
|---|---|
| `/usr`, `/bin`, `/lib`, `/lib64`, the enumerated `/etc` | read-only, as D2 §2.3 |
| `runner_config.direct.read_paths` | read-only at their own paths; any that is, contains or aliases D2 §2.3's forbidden set refuses the launch (`mount_plan_refused`) |
| `/surety/workspace` | an overlay: lower layer the check tree (§2.4), read-only; upper layer on the domain's volatile filesystem, discarded with the domain |
| each path in `inputs`, at its workspace location | a read-only bind of the materialized protected tree over the overlay; protected paths not in `inputs` are absent |
| `/surety/home`, `/tmp`; `/proc`, minimal `/dev`, private `/dev/shm` | volatile; as D2 §2.3 |

Absent, compared with the `role` profile: a backend installation, the context package, `/surety/out`, any git metadata (the check tree has no `.git`), any provider key or grant secret. The network namespace has only its loopback; D2 §2.4's proxy is bound only when the definition names `egress`, with exactly those hosts. Volatile and resource bounds are D2 §3.7's per domain, and admission is its envelope. **One deviation from the brief:** R1 asks the source to be read-only except where the check declares it writable. D3 gives the check a writable overlay whose writes are discarded, because toolchains write caches and reports in places no declaration lists correctly, and discarding gives the property the declaration was for: nothing a check writes reaches the candidate, the checkout or another check. The protected inputs are strictly read-only, so neither the check nor candidate code it runs can write, rename or replace an expectation before reading it. The profile's fingerprint joins the mechanism fingerprint of the host qualification (D2 §7.1). **No host requirement is added:** H1 to H12 cover what the profile uses.

**2.3 The environment.** Constructed, never inherited (D1 §17 item 4): `PATH` from `runner_config.direct.path`; `HOME=/surety/home`; `TMPDIR=/tmp`; `LANG=C.UTF-8`; `TZ=UTC`; `CI=true`; `runner_config.direct.env`; the definition's `env`; the identifiers `SURETY_CHECK`, `SURETY_CANDIDATE`, `SURETY_SOURCE_REVISION`, `SURETY_PROTECTED_VERSION`; `HTTPS_PROXY` only with egress; the domain marker (diagnostic, D2 §1.2). No secret reaches a workspace check (§5 X3 reserves secrets for environment-bound checks).

**2.4 Materialization** (R1). Before launch the main thread builds, or reuses, the **check tree** of a (source revision, protected version) pair under `$SURETY_HOME/checktrees/`: with engine git, `read-tree` of the revision into a private index and `checkout-index --prefix`, omitting the files under the version's roots (probe above); and the version's protected files beside it, from which `inputs` are bound. Files are made read-only; a tree is immutable, shared by every execution of its pair, and removed when none references it. The tree is engine-owned like `workspaces/` and never named by policy. It has no `.git`, so a check cannot read history or the repository's configuration; submodules, LFS and filters stay unsupported (D2 Q4). It is bounded by `checktree_max_bytes`; an unreadable revision, a git deadline or the bound is `materialization_failed` (§2.7).

**2.5 Registration, triggers and scheduling** (R4, R5). One engine transition registers an execution and allocates its `execution_seq` from the project's sequence (D1 §3.3, "assigned by the runner registration transaction"), shared with the harness fixture route so the two never collide. **Registration, not completion, orders results:** of two executions with the same bindings the later-registered decides (D1 §9.2 step 3) whichever finishes first, so a slow earlier execution never overrides a newer request. Registration freezes the check row of the version, the candidate, its revision, the protected version effective at registration, the definition's runner class, the trigger, and, from an environment trigger only, environment and artifact (§5 X3). **Triggers** (`CheckTrigger`): `nomination`, every check of the union of the candidate's `stage` and `alpha_authorize` required sets (§4.2), including the fix's candidate that E43 nominates; `protected_application`, from the application's finalizer, the new version's checks in the required sets of every candidate with no `superseded_by`; `operator_request`, by route (A.7), re-running named or all required checks of a candidate; `recovery` (§2.7); `deployment_verification`, reserved (§5 X3). The trigger identity `(source, id, check key)` makes registration idempotent, as for work triggers (D1 §8.2). No role's result can register an execution or write a result: role result schemas have no such field, and the fixture route exists only in harness mode (E23 item 4). **Scheduling:** a tick step after Gates (correction L2) admits queued executions oldest first within D2 §3.7's envelope, where a hold shows as `resource_envelope`, and the project's `max_concurrent_checks` (default 1, so a candidate's checks run one at a time). Executions are not runs: the project concurrency of exactly one run (BS §6 correction 20) does not count them, and a check may run while a role's run holds the project, because it reads an immutable revision and writes nothing of the repository. Each execution holds a lease of kind `check` (L1), renewed while supervised and re-granted after a pause exactly as a run's (D2 §3.5), never extending `timeout_s`. A queued execution whose candidate or protected version is superseded before launch is cancelled with no row (`check.cancelled`); one already running is recorded under its version, which §9.2 then makes `stale`.

**2.6 Launch, observation, and what is established** (R2, R3). The launcher places itself in the domain and obtains a launch authorization bound to domain, check execution, incarnation and lease generation (D2 §3.2, with L1). The domain init brings up loopback and the forwarder if any, opens the output capture, and execs `check_commands[command[0]].path` with `command[1..]`, the constructed environment and `cwd`: the check's own process, under no shell and no wrapper of the engine's. On its control channel the init reports `started` once the exec has succeeded (a close-on-exec pipe; a failed exec reports its errno instead), then the exit status or terminating signal of that process, and whether any other process remained in the domain when it ended (`orphans`), the init being process 1 to which orphans are reparented. The engine then terminates the domain with closure (D2 §3.2), whatever the check did.

**`execution_established` is true if and only if the engine itself recorded** the domain launched under an authorization bound to this execution, the init's `started` report, and the domain terminated with closure. It never derives from the check's output or exit status, or from anything a process in the domain wrote: only the init's reports on a channel that check code cannot reach (D2 §2.3). The other fields: an exit status reported is `exit_status`; a signal the engine did not send, an OOM kill included, sets `signaled` with `exit_status` null; a cancellation at `timeout_s` sets `deadline_hit` and `signaled`; established with no exit report (the init died, the channel failed) leaves `exit_status` null. D1 §9.2 makes each of these `failed`, and `orphans` too (correction L4; CH 17: a check that leaves work running did not finish it). Not started (a failed exec, no `started` report, a refused launch) is a row with `execution_established` false and a `not_run_reason` (§2.7), which §9.2 makes `skipped`. **Unknown** (D2 §3.4): while the domain's termination is `unknown` nothing is collected and **no row is recorded**; the execution is `quarantined`, the check is `missing` in evaluations, and the gate read names the quarantined execution. The row is recorded only when termination with closure is observed, from the reports the init had made. No row rather than a `skipped` row, because `skipped` would claim the runner knows the check did not run.

**Output** (R2). The init captures standard output and error, interleaved, onto the volatile filesystem, keeping the first and last halves of `output_max_bytes` and counting what it dropped; output volume never cancels a check. After termination, collection under D2 §1.4's rules (no link followed, bounded entries and time) passes the secret screen and the redactor (D2 §2.5; D1 §14.2) and publishes a `check_output` record named by `check_results.output`. A screen hit refuses publication, raises D1 §14.2's critical finding, and leaves the result's evidence missing (`EVIDENCE_MISSING`). Output never changes a field of the result.

**2.7 What cannot run** (R6). An execution the runner attempted and could not start records a row with `execution_established` false and one `NotRunReason`: `definition_invalid`, `toolchain_missing` (the program's path absent, or its pinned hash different), `materialization_failed`, `mount_plan_refused`, `isolation_unqualified` (no current host qualification), `runner_unqualified` (§2.8), `environment_unbound` (§5 X3), `exec_failed`, `interrupted` (the engine restarted during the execution; recorded after D2 §3.3's recovery). Each is `skipped` at the gate, which is therefore not satisfied (E41 item 2); the reason is on the gate read beside the check's state (E47); and the host-level reasons (`toolchain_missing`, `mount_plan_refused`, `isolation_unqualified`, `runner_unqualified`) make the project's status line `refused` with cause `check_unrunnable` (D1 §12.3; E53 item 4). `interrupted` and `materialization_failed` are registered again automatically, as trigger `recovery`, at most `check_infra_retries_max` times per original trigger; every other reason waits for what it names (a correction, a host fix) and then the operator's re-run. A registered execution never attempted has no row and the check stays `missing`.

**2.8 Runner classes** (R7). `direct`, a check in a `check`-profile domain on the engine's host, is the only class D3 qualifies, and the class M3 needs. It is qualified on a host when the host qualification is active (D2 §7.1) and the **runner self-test** passed at the same start: scripted check programs in real `check` domains, each beside a control, whose results must be exactly: exit 0, passed; exit 1, failed; output "passed" with exit 1, failed; a foreign signal, failed; past the timeout, failed with `deadline_hit`; a missing program, skipped; a protected input written, renamed or replaced from inside, refused while a source write succeeds; an orphan, failed; an undeclared egress refused while the declared one connects (CH 17, "the test runner is a gate too"; AH §9.9). The outcome is recorded on `host_qualifications.check_runner`. Every result records `runner_id`, `direct@<host id>/<profile fingerprint prefix>`, and `runner_qualification`, the host qualification row in force, as a trust entry records its evidence (D2 §4.1). `container` and `remote` are not qualified: their definitions are discovered and their executions `runner_unqualified`. Before it can be, `container` needs a rootless mechanism with D2's boundary guarantees (D2 §2.2 rejects the Docker daemon), termination with closure, and the same judgment (E8: one definition executes identically under every runner); `remote` needs a result channel the engine authenticates, binding the remote's observation to the registration, which is a design of its own. A result matches only its own class (D1 §9.2).

**2.9 Developer tests** (R8; F §5.4). A Builder's own runs of its tests are claims in its transcript (E12), never results. A project makes developer tests evidence with a definition of origin `developer`: definition, command and runner are protected like any check; the test files it runs are the Builder's, outside the roots. Its results are ordinary `check_results` rows of a check whose `origin` is `developer`. It may be required, so it can block a gate and must pass; it never covers a criterion, so it never stands for an acceptance check (§4.3). The Builder can change what it runs without the protected route, which is exactly why.

**2.10 A failed check and the fix loop** (R9; E38). When a result of the check a `fix` item's finding names is recorded for the fix's candidate (E43) after the item reached `verifying`, and that check's state is `failed` (not `skipped`, `missing` or `stale`, which are not the Builder's doing), the engine sends the fix back: `verifying → eligible` as an automatic repair (D1 §4.3), `repair_attempts` incremented once per such result, with that result's output record in the next run's context package (D2 §1.3). The progress key (D1 §4.3) gains `(check, <key>, exit_status, signaled, deadline_hit)` for the failed check, so the same failure on an unchanged snapshot tree counts toward `no_progress_max`; either limit parks the item with a `blocker` naming the check. A `contract_conflict` or `requirement_conflict` finding from the Builder's run stops the repair and takes §5 X2's route. Whether the same rule applies to a `stage_build` item is Q2.

## 3. The diff classifier

**3.1 Definitions** (C1). `classify(P0, P1, S)` compares P0, the discovery of the effective version's tree, with P1, the discovery of the proposal's tree, against S, the registered requirement index (§4.5). Each difference, per check key and per governed field, is one **element** with a `ClassificationReason` (A.2):

- **Strict:** a check added with a valid definition; a check's `covers.criteria` or `gate_kinds` gaining values; `tier_floor` lowered or removed; a root added to `protected_paths` with none removed; a key added to `required_checks` together with the check it names.
- **Loosening:** a check removed; a key removed from `required_checks`; `covers.criteria`, `covers.sensitive_areas` or `gate_kinds` losing values; `tier_floor` raised or added; a root removed or narrowed.
- **Unclassifiable:** any change of `check_commands`, `check_discovery`, `runner_config` or `result_collection`; any change of an existing check's `kind`, `origin`, `command`, `cwd`, `env`, `timeout_s`, `runner_class`, `requires`, `inputs` or `egress`; any change of a file in an existing check's inputs; a key added to `required_checks` naming a check that already existed (C2); any discovery error in P1.
- **Neutral:** a changed file under the roots that is in no check's inputs and is not the governed file.

Then: `initial` if and only if there is no effective version (project creation); otherwise `unclassifiable` if any element is, or if there is no strict and no loosening element; otherwise `loosening` if any element is; otherwise `tightening`. A tightening is therefore a proposal under which every check of P0 is kept with an identical check fingerprint or changed only by strict elements, the criteria and areas covered by P1's required checks are a superset of P0's, and something is strictly added. A changed input file is unclassifiable, not judged: E13's "new assertions, narrower accepted ranges" are statements about test code, which the classifier does not read (brief §7). Declared inputs are what make a tightening provable: a new check whose files lie outside every existing check's inputs leaves their fingerprints unchanged; under default inputs any new protected file changes every check's, and the proposal is unclassifiable (Q3). The classifier reads trees, the governed file and the requirement index only, runs nothing, and records its `classifier_version` with each classification.

**3.2 The conservative fallback** (C2). In doubt, `unclassifiable`, which only the human approves (D1 §7.9). No change to `required_checks`, `check_commands`, `check_discovery`, `runner_config` or `result_collection` is a tightening by itself: the last four are always unclassifiable, and `required_checks` contributes a strict element only beside the check it adds. A change to `required_checks` also needs the validation-scope approval, as built (`changes_required_set`, the option blocker `APPROVAL_MISSING`; E13; SEAM §69). A classification is never a judgment of a check's quality: a vacuous new check covering a criterion is a tightening by these rules (§6 class C). The controls for that are the Reviewer's assessment of test adequacy (F §4.1) and the protected delta shown at human gates (E13).

**3.3 Binding, re-classification and authority** (C3; K8). A classification is recorded on the proposal as `{change_kind, elements, affected_checks, effective_version, spec_revision, classifier_version, discovery}` with `protected.classified`, and routes as built (SEAM §69: a tightening stays `classified`; loosening and unclassifiable go `awaiting_human`). The three `check_correction_*` manifests, which already bind the classification, the effective version and the spec revision (SEAM §§77, 101), gain `classifier_version`. **At application** the classification is an effect precondition (K8; D2 §5 C2): immediately before the application's journal intent (D1 §10.5) the engine classifies again against the effective version, the spec revision and the classifier version current then. If the class differs from the approved one, the intent is invalidated with `EFFECT_PRECONDITION_CHANGED`, the approval withdrawn and the next generation raised, as SEAM §104 does for a moved branch. A Reviewer's approval carries no decision and no intent; the same check runs before its application begins and withdraws it the same way. Re-classification matters because an application writes the proposal's whole protected set: a check another application added meanwhile would be removed, which the new comparison sees as a loosening. **Authority:** the engine setting `classifier_authority` is `recommend` until the operator sets it `authoritative` naming the qualified `classifier_version` (Q5). Under `recommend` a Reviewer's approval of a tightening is recorded as a recommendation, provenance `claimed`, on the `check_correction_tightening` decision the human answers, and applies nothing (D2-C03). Under `authoritative`, and only while the running classifier is the version named, it is the authority F §4.1 and E13 give a Reviewer, and applies after revalidation. A classifier version is qualified when the kernel-lane classifier rows of Appendix C pass on it.

**3.4 Reading the spec** (C4). Discovery and the classifier read the requirement index the engine registered from the approved spec (§4.5). A definition naming a criterion or area the index does not have is the discovery error `criterion_unknown` or `area_unknown`; the proposal is unclassifiable and its approval blocked (L5). That is M11's contradiction at the protected path: a check that contradicts the spec goes to a person, who has the Verifier correct the check or changes the spec through F §3.8; it is never a repair. A withdrawn requirement's criteria are unknown. When a spec revision removes a criterion a check of the effective version names, the version's discovery errors are recomputed against the new revision and the project's gates carry `ACCEPTANCE_SCOPE_INCOMPLETE` until a correction lands.

**3.5 Invalidation and reuse** (C5). An applied change invalidates in its finalizer every result recorded under the superseded version (as built, `invalidateResults` in `src/store/transitions/protected.ts`; SEAM §72), stales every evaluation (D1 §9.5), and now also registers the new version's checks (trigger `protected_application`, §2.5), so the checks run without anyone asking. Evidence reuse (D1 §9.1; BS §6 correction 18) is bounded by the classifier's notion of unchanged: a reuse entry counts only if the reused result's check fingerprint equals the fingerprint of the scope's check and, as built, the result's protected version is the effective one, so a result never crosses a protected change (M41; SEAM §103). Q1 asks whether to allow reuse across versions for checks whose fingerprint did not change. D3 creates no reuse entry: checks cost no model, so the runner re-runs every required check for every candidate, and reuse stays a path for a later design (expensive environment checks) and for the fixture.

## 4. Validation scope at run time

**4.1 Scope modules and tier** (S1; M43). A scope's **modules** are, at `stage`, those its stage lists (`stages.modules`); at a deployment gate, every module with at least one file at the candidate's revision, read with the tree and recorded as a fact of the candidate, as ancestry is (`src/gates/prepare.ts`); at `phase`, those of the phase's stages. A deployment gate takes every present module, not those a diff touched, because it judges the state being deployed: a sensitive module changed in an earlier candidate must not escape the floor of a later one (Q7). An unread module fact is `ACCEPTANCE_SCOPE_INCOMPLETE`. The scope's **tier** is the highest of the project's tier and each scope module's `tier_override` (D1 A.3; F §5.6, "module overrides"); an override never lowers. The tier selects checks (`tier_floor`; as built, `applies` in `src/store/transitions/evidence.ts`) and sign-offs (as built in `buildScope`: T2 a Reviewer's at candidate scope; T3 also one per module and a security review), now from the scope's tier rather than the project's.

**4.2 The required set** (S1). From the effective version's required checks that list the gate kind: (a) release obligations, checks covering no criterion, at the scope's tier; (b) checks covering a criterion of an obligation requirement, at the scope's tier, the obligations being as built (at `stage` the delivered requirements its stage implements; at deployment gates the delivered requirements) and at `phase` every requirement assigned to the phase, delivered or not (RN R7); (c) every `sensitivity_floor` check naming a scope sensitivity category, whatever the tiers; (d) required `developer` checks at the scope's tier. `required_check_ids` is that set and `runner_classes` each check's class. `sensitivity_categories`, always `[]` as built, is the union of the obligation requirements' `sensitive_areas` (§4.5) and the scope modules' `sensitive_areas`.

**4.3 When a scope is validated** (S1, S3; correction L3). A scope is `validated` if and only if the required set is not empty; every criterion of every obligation requirement is named by at least one required check of origin `acceptance` in the set (a requirement registered with no criterion is **uncertain**, which gives M38's "uncertain" a reachable meaning); every sensitivity category has at least one `sensitivity_floor` check in the set; the effective version has no discovery error; and every fact the scope needs (ancestry, module presence, the index) was read. Otherwise the evaluation carries `ACCEPTANCE_SCOPE_INCOMPLETE` with each uncovered criterion, area (`area:<name>`), definition path or unread fact among its subjects. The `phase` gate stays refused (`unsupported`; SEAM §70; BS §6 correction 9) until its milestone; its scope is defined here so that F §3.10.6's plan check ("every requirement assigned to the phase has required checks planned") can use the same coverage function.

**4.4 What a sensitive area requires** (S2; F §5.6, O1). For each area of the closed list (`SensitiveArea`, A.2) in a scope's categories: at least one required `sensitivity_floor` check naming it, at every tier and every gate kind evaluated, passing like any required check. D3 ships the requirement; the engine enforces existence, naming and passing; D3 ships no checks, because what a check establishes is the spec's and the Verifier's (brief §7). Appendix B gives the Verifier a one-line minimum per area as a starting point, not as the engine's test.

**4.5 The requirement index** (S3). From the approved spec (`.surety/spec/spec.md`) the engine reads only the requirement index of the template's section 5: one table row per requirement with key `R<n>`, title, phase, sensitive areas (from the closed list, or `none`) and criteria (`R<n>.<m>`, comma-separated). Registration at spec approval writes `requirements` rows with `criteria` and `sensitive_areas` (A.3); a row that does not parse, an unknown area, a criterion that is not of its requirement's key, or a repeated criterion refuses the approval and names the row. Until spec approval is built, the plan fixture supplies the same fields. A check names what it covers by criterion keys (`covers.criteria`, §1.3); delivery comes from stages (D1 §9.1, unchanged), coverage from checks.

## 6. What D3 does not claim

In the form of `M1-not-claimed.md`: class A is outside the threat model, class B is real behaviour no test has yet established, class C is a limitation accepted by design.

**Class A.** As D2 §8 class A. A check the Verifier wrote to pass whatever the source does.

**Class B.** The runner on any host before its self-test has passed there; `container` and `remote`; the phase gate; spec approval's registration of the index (the fixture stands in). That a project's toolchain fails on every condition its checks care about: the definition must make it so (E8). Node 22's `node --test` exits 0 when every test is skipped and when none exists (probe above), so a definition that runs it bare is a vacuous check.

**Class C.** The verdict is the exit status of the check's own process: a check that runs candidate code in its own process can be made to exit 0 by that code (`process.exit(0)` in an imported module), and no runner can tell; a check should run candidate code as a child and judge what it observably does, which is the Verifier's construction and the Reviewer's assessment, not the classifier's. The classifier judges structure, so a vacuous new check covering a criterion classifies as a tightening (§3.2). The latest registration decides, so an operator's repeated re-runs of a flaky check can turn a failure into a pass; every execution is kept and listed with its sequence. A check sees no git history; submodules, LFS and filters are unsupported. Toolchain drift between executions is recorded (each records the program's resolved path and hash) but prevented only where `check_commands` pins a hash. Output is kept head and tail within its bound. A check's writes are discarded, and a check produces no artifact in D3. The engine creates no evidence-reuse entry. A candidate's checks run one at a time by default.
