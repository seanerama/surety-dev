# Surety M5 build specification

**Status:** draft 1, written for Sean by the owner's assistant (no Builder, Verifier or Reviewer role), 2026-10-12, against **D6 draft 2** (decided, E139 and E140; **not yet approved to build**: Astra's cross-review is pending, E139 item 11), with the M5 acceptance plan (`docs/acceptance/sdlc-M5-acceptance-plan.md`). Every change Sean dispositions from her review into D6 draft 3 is applied to this document and the plan by the owner before adoption; a statement D6 draft 3 adds, removes or renumbers changes a row. **Not adopted.** **Owner:** Sean. **Changes:** by the owner only.
**Readers:** the sessions that verify, build and review M5, the driver, and Sean.

M1 built the kernel on a scripted stand-in for a coding agent (`docs/spec/M1-build-spec.md`; accepted, E45). M2 made the engine run one real coding agent inside isolation the host qualifies and the engine observes (`docs/spec/M2-build-spec.md`; accepted, E88). M3 made the engine run a project's protected checks itself and judge them (`docs/spec/M3-build-spec.md`; accepted, E109). M4 made the engine deploy a sealed candidate to a real Alpha environment on this host and verify it by observation (`docs/spec/M4-build-spec.md`; accepted, E138). In all four every project started from a hand-entered fixture: an approved plan with its index and texts installed by `installFixturePlan`, one stage, and a human `continue` after every role run (D1-34). M5, this document, makes the engine **take a project from an idea the owner types, or from an existing repository the owner adopts, to `alpha_deployed`**: three conversational roles as engine-metered sessions, the specification as a governed artifact with its change workflow, the architecture, the roadmap and the one-phase-at-a-time plan checked mechanically and registered atomically, checks authored before any stage, stages ordered by their dependencies and run as many at once as the host admits, the phase gate and the Architect's re-entry, the deploy request under policy, the pace recorded from rows, and the retrofit journey with its evidence rules, as D6 draft 2 designs (E136, E139). Everything the M1 to M4 specs fix about roles, constraints and procedure stays in force; this document says only what M5 adds or changes.

Read sections 1 to 5 before doing anything. Sections 6 to 12 are reference for the slice you are working on. Section 10 states the pace instruments M5 records and the benchmark that follows M5; section 11 holds the items E139 and E140 carry; section 16 the questions this draft raises.

## 1. What M5 is

M5 is **idea to Alpha** (E136): the two journeys of D6 §1 and §8 on this WSL2 host, on a scripted backend in every lane but one and once for real on each journey. Sessions (D6 §2; K6): a run of kind `session` whose every turn is a one-shot invocation carrying the engine-held transcript in its context package, no provider-side continuation, save and close through the journal, idle timeout, resume from durable records, one open session per project, the continuation canary on the qualification attempt. The three interactive roles and their products (D6 §3): Vision's idea record with its identity block, the Spec Writer's specification in TPL's shape parsed at every save, the Architect's architecture, module map, ADRs, roadmap and phase plan parsed from closed schemas (Appendix B), each approved by the owner through the decision its close raises. The specification as a governed artifact (D6 §4; K8): the change request, the Spec Writer's proposed diff on a side ref, the exact impact, the owner's approval, invalidation that flows to checks, stages and gates. Planning (D6 §5; K4, K5): the roadmap, the next phase's plan only, the mechanical check of fourteen reasons, routing, atomic registration in the committing finalizer, the Architect's one-shot replan from durable records, early replanning, the `phase` gate and `phase_verification`. The build's execution (D6 §6; K1, K2, K3, K7, K9): `check_authoring` per phase before any stage, order by `depends_on`, pipelining and parallel builds under the admission envelope alone with per-profile memory maxima, the autonomy profile `step | stage | phase`, the event-driven tick, `alpha_deploy: manual | on_phase_complete`. Pace (D6 §7.6): `GET /v1/projects/:p/pace`, every figure from rows, `unknown` where a row is missing, `memory.peak` per domain. Retrofit (D6 §8; K10, K11): adoption with its signals and `adoption_mode`, retrofit mode for the sessions, the index's `Origin` column and the claims table, `requirement_confirm` consolidated with the spec approval, the conformance stage with no Builder, the conformance-phase `fix` rule, the evidence rules that make nothing of an adopted repository acceptance evidence by default. M5 has no Beta or Live, no rollback, no reattachment, no build execution, no remote target, no second machine, no adoption of a public repository, no Codex or API-key sessions, no provider-native continuation, no automated architecture approval, no evidence reuse across a spec change, no UI, and runs no benchmark.

M5 is accepted when:

- `npm test` exits zero on `main` for the kernel, sandbox and project lanes, which requires every M5 acceptance row (M401 to M446) to have executable tests and none skipped, and the M1 to M4 rows to keep passing, with the accepted rows of D6 Appendix C.2 migrated by a Verifier and recorded in COVERAGE;
- the exhaustion-lane file of row M438 has passed on the designated host (E69; question 2);
- the two real-lane rows, M443 (idea to Alpha) and M444 (retrofit), have passed under Sean's command (D6-J02, D6-J04; E139 items 7 and 8), each after its rehearsal, with their records and their pace reads retained;
- the M5 acceptance report is written (section 13), and Sean has run the hands-on script (M446) if he chooses it.

Nothing less is acceptance.

Accepting M5 supports one claim: **on this host, with the recorded versions and limits, on a scripted backend and once for real on each journey, the engine took a project from an idea the owner typed, and another from a repository the owner adopted, to `alpha_deployed`: it metered every conversational turn as a run of its own and carried the conversation only in records it held; parsed every product with a closed schema and let no role approve its own; checked each phase plan mechanically before registering it, atomically with its commit, and registered no stage work any other way; authored the phase's checks before any stage built; dispatched as many runs at once as the plan's dependencies allowed and the host's envelope admitted, each domain counted at its configured maximum, and never more; ran a phase unattended within F §9.1's floor and stopped exactly where the foundations route a decision; computed a specification change's impact exactly from records and invalidated what it named; evaluated the `phase` gate over the phase's whole requirement set and replanned from durable records, never from a session's transcript; requested Alpha under policy only through D4's gate; recorded the pace of all of it from rows, with `unknown` where a row was missing; and made nothing of an adopted repository acceptance evidence except through the Verifier's protected proposal and the owner's or Reviewer's approval.** It does not support the claims that a specification is truthful or a plan sensible (D6 §11 class C), that a real-size stage takes any particular time or any number of tokens (D6 §7, §11: the benchmark's measurements, after M5), that a role runs within `role_memory_max` (D6-X08 measures it), that several machines can run one project, or anything D5 owns.

## 4. Roles, lanes and who runs what

The M1 to M4 specs' section 4 stands: the same three roles with the same paths (`CLAUDE.md`), Sean the owner, the lean procedure of E31 and E40 as E123 amended it (one full run per slice, the driver's, from a clean scratch copy; the Builder runs its own slice's files, every earlier file its change touches and the unit tests; the next slice's Verifier and Builder overlap the run), objections as before. **The role paths stay as in M4.** M5 adds:

- **Five lanes** (D6 Appendix C; plan §2.1). `kernel`: real git and SQLite, the scripted backend playing every role turn by turn (its replies, products and packages scripted and recorded by the test), the scripted check boundary of M3 and the scripted deployment adapter of M4, no domain. `sandbox`: real `role` domains on D2's launcher and init running the scripted backend's fixture binary, real `check` domains, and where a row deploys, the real `local_service` adapter in transient user units; no model. `project`: the two reference projects through their whole journeys on real domains and a real unit, no model; it runs with `npm test` like the sandbox lane (E92 item 2 (1)). `exhaust`: a role domain past `role_memory_max` (row M438's exhaust file), on `mini-hp01` only (question 2). `real`: Sean's command only, two files (section 12).
- **Who may run what.** `npm test` and `--slice N`: every role and the driver, under the safety rules below. `--lane exhaust`: only on `mini-hp01` with `SURETY_EXHAUSTION_HOST`, by Sean or by the driver at his request (E69). The real lane: only by Sean's command, on a subscription token he makes (section 12). A Builder never runs a real backend. No session with a real model is opened outside the real lane.
- **The Reviewer's rule** (E31) stands: anything called serious is reproduced by running the engine; in the sandbox and project lanes that includes opening a session on the scripted backend in a disposable home and, where a row deploys, deploying to a real unit, under every rule below. Never a model.
- **Host steps are Sean's.** M5 adds none: the user service manager is H3's (D4 §9.4); the sessions' domains are D2's. The reference projects' runtime is the engine's own `node`.

### 4.1 Safety rules for M5 (absolute; in substance in every Verifier, Builder and Reviewer brief)

BS4 §4.1's rules 1 to 13 are carried whole and renumbered here unchanged in substance; rules 14 to 19 are added for M5.

1. **Units only from a disposable home's derived name.** A test, an experiment, the hands-on script and the real lane create only units named `surety-<h>-<env>-g<n>.service` where `<h>` derives from their own disposable `SURETY_HOME`, refuse a name that already exists, and stop or reset only those exact names. Never a pattern, a glob, `--all` or a prefix with an action. A decoy unit a test seeds is created by that test under a name outside every Surety prefix, and is stopped only by its exact name.
2. **Never the user's manager itself.** Nothing stops, restarts, reloads, `daemon-reexec`s or `daemon-reload`s the user's service manager.
3. **Never Docker, never the system manager**, and nothing on `mini-hp01` outside the exhaustion lane's own directories and the units its disposable homes derive.
4. **The unreadable-manager case** points the adapter at a bus address that does not exist, never at a stopped manager (M4's M331 (d) stands; M5 adds no such case).
5. **The adapter's own guard** (BS4 §4.1 rule 5) stands; M5 touches `src/deploy/` only where K9 raises the `deploy` trigger, which adds no host call.
6. **The audit list.** Each slice's Builder lists every `systemctl`, `systemd-run`, kill, signal, `cgroup.kill`, `cgroup.procs` write, removal and mount site that its change adds or moves, with what establishes the target is the engine's own; the Reviewer checks the list; the driver reads every new acting instrument's guard in a Verifier branch before merging it. M5's expected answer for most slices is "none": sessions reuse D2's launcher and init.
7. **Before and after every sandbox-lane or project-lane run** the runner's read-only check (E121; `scripts/run-tests.mjs`) stands: `is-system-running` `running` before; afterwards no `surety-*` unit left, leftovers of `/dev/shm/surety*` and `/tmp/surety-*` reported by exact name; nobody cleans up a unit they did not create.
8. **E64's two-part fail-closed rule.** A destructive instrument (a fixture role or service that allocates, forks or writes to its limits; a step that stops, restarts or kills a unit or writes `cgroup.kill`) refuses to act unless it establishes from inside that it is contained (its pid namespace is not the host's, pid 1 is the domain init, at most 16 processes visible; any failed read is a refusal), and the test releases it only after reading from the host side that the domain or unit carries its own home's prefix and that the instrument's pid is in that domain's cgroup. The test's own changes refuse any unit or cgroup outside its home's prefix.
9. **Order:** within a slice, a destructive file runs last, after containment is observed in a non-destructive one.
10. **No exhaustion here:** memory, task and storage exhaustion of any domain, a `role` domain at `role_memory_max` included, run only in the exhaustion lane on `mini-hp01` with E69's caps; every bound a sandbox row tests is set low through a harness override, never by filling memory or a disk. The read-back of a role domain's `memory.max` is not exhaustion and runs here (M438 sandbox).
11. **Nothing paid without Sean.** The real lane runs only by his command; no fixture approves spend; the token is never written to a file the repository or a record holds (E74, E87); **no session on a real model is opened by any role or by the driver outside the real lane.**
12. **Keep the machine quiet** during sandbox and project runs: at E140's defaults a role domain is admitted at 4 GiB, a check domain at 2 GiB, the reserve is 2 GiB, and a running Alpha service holds its memory and one check's capacity (E126); the project lane's journeys run two role domains at once where the envelope admits (D6-X05), so about 12 GiB available is needed for the journey files to take the pipelined path rather than the serial one (either passes; the pace read records which).
13. **The first sandbox run that opens a session in a real `role` domain** (slice 33) and **the first project-lane run that builds two stages at once** (slice 31) are started by the driver, who shows Sean the before-and-after unit lists and the pace read's peak concurrent domains; every later run proceeds under these rules without asking (E124's form).
14. **Nothing a session writes is run.** A plan is registered, never executed; the machine files are parsed with closed schemas and unknown fields refused (D6 §9); the owner's typed text reaches a prompt as the owner's own and nothing else; no fixture passes owner-typed or role-written text to a shell. The engine performs every commit (E2).
15. **Disposable homes and run directories are short.** Every `SURETY_HOME` a test, the hands-on or the real lane uses is at most 56 bytes (E134 item 6; objection 055): the engine refuses a longer one at start, and the test fails, never skips, if it did. Run directories are chosen under `$HOME` with short names (`~/surety-m5-real-<date>`).
16. **On `mini-hp01`** (E134 item 3): `TMPDIR` on disk (its `/tmp` is tmpfs, which the engine refuses correctly), `XDG_RUNTIME_DIR=/run/user/1000`, the pinned Node 22.22.0; the exhaust file fails fast and names the engine's stderr if a domain's setup fails (objection 056's harness rule), and the driver stops nothing but an engine incarnation scope of its own disposable home, by exact name, after reading its `SURETY_HOME`.
17. **The clock** (E132 item 8, E134 item 1): every deadline or due-time crossing a sandbox or project test waits for carries the 10 s margin (`STEP_MARGIN`, SEAM §334); durations are measured on a monotonic clock (SEAM §333); the idle timeout, the tick's interval and the pace read's wait figures are pinned in the kernel lane under the scripted clock, where they are exact. Before the real runs Sean restarts the VM (`wsl --shutdown`) at a pause if the clock is stepping.
18. **The real lane's rehearsal fakes play from the package** (E135; section 12): a rehearsal whose fake carries a hard-coded product the package does not state is not a rehearsal; row M442 (b) pins it.
19. **A session's domain is a `role` domain** with D2's mount plan, the proxy as its only egress and no control-plane reach; a save is admitted only with zero live processes (D1 §7.3; D6-S01). No fixture or test opens a channel from a turn's domain to the engine but the result file.

## 5. Fixed technical constraints

The M1 to M4 specs' section 5 stand, with these added or sharpened:

- **Dependencies:** unchanged; `better-sqlite3` is the engine's only runtime dependency. The reference projects, the adopted fixture repository and every fixture role use Node's own modules only. The YAML identity block of IBT (Appendix B.1) is parsed by an engine parser over the closed key set, not a library.
- **Process starts:** unchanged. A session's turn starts a process only through D2's launcher as a one-shot run does (`src/invoke/`); no new site. `check_authoring`, `replan`, `spec_change` and `phase_verification` runs are dispatched through the same path as `stage_build`.
- **No shell:** unchanged. Owner-typed text (a turn, a change request, an idea brief) is written to records and context files, never interpolated into a command.
- **No transaction across a host call** (D1 §6.1): the plan check, the impact analysis and the pace read are pure functions over the store and git blobs read before the transaction; the registration finalizer writes in one transaction after the commit is confirmed (D6 §5.5).
- **Closed schemas** (D6 Appendix B; D3 §1.4): every machine file the engine reads refuses unknown fields and reports the row or field by name; a file that does not parse is a finding returned to the session, never a default.
- **One tick at a time** (D1 §1.5; K1): the requested tick sets the existing flag; `tick_budget` and `tick_interval` are unchanged; a requested tick never pre-empts a running one and never skips D1 §8.1 steps 1 to 4.
- **The envelope is as built** (`src/store/transitions/envelope.ts`; K2): a domain is counted at its configured maximum (`role_memory_max` or `check_memory_max`, each at most `domain_memory_max`), never at its use; the service's reservation and the shared check capacity of E126 count; `max_concurrent_domains` caps.
- **Every transcript entry passes the redactor** before disk (D1 §14.2); the role's reply can set neither `speaker` nor `turn` (D6 §2.3: the engine writes both).
- **Unix socket paths** are checked against `sun_path` before bind and dial (E134); the engine refuses a home longer than 56 bytes at start.
