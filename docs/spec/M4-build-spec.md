# Surety M4 build specification

**Status:** draft 1, written by the architect; **adopted by Sean, 2026-10-09 (E121)**, with CD1 to CD4, the proposed numeric defaults and the recommendations to questions 1 to 9 of BS4 §16 as recommended. 2026-10-09, with the M4 acceptance plan (`docs/acceptance/sdlc-M4-acceptance-plan.md`). **Owner:** Sean. **Changes:** by the owner only.
**Readers:** the sessions that verify, build and review M4, the driver, and Sean.

M1 built the kernel on a scripted stand-in for a coding agent (`docs/spec/M1-build-spec.md`; accepted, E45). M2 made the engine run one real coding agent inside isolation the host qualifies and the engine observes (`docs/spec/M2-build-spec.md`; accepted, E88). M3 made the engine run a project's protected checks itself and judge them (`docs/spec/M3-build-spec.md`; accepted, E109). In all three nothing was ever deployed: `alpha_complete` is unbuilt, the environment record's only writer is a fixture, and the M3 report says Surety cannot deploy anything (M3 report §1). M4, this document, makes the engine **deploy a sealed candidate to a real Alpha environment on this host, identify what runs there from the target's own state, verify it by observation, survive a crash honestly, and tear it down**, as D4 draft 2 designs. Everything the M1, M2 and M3 specs fix about roles, constraints and procedure stays in force; this document says only what M4 adds or changes.

Read sections 1 to 5 before doing anything. Sections 6 to 12 are reference for the slice you are working on. Section 11 holds the items D4 left to this spec (E120 item 2); section 16 the questions this draft raises.

---

## 1. What M4 is

M4 is **Alpha deployment on one target, `local_service`**, of D4 draft 2 (E95, E110 to E118, approved E120), on this WSL2 host: environment configuration in owner-written immutable versions with a keyed identity; the artifact projected and sealed by the engine from the candidate's revision, its bytes and its source mappings kept apart; the authorization derived by the engine and gated on the completion's obligations (J3, J4); the deploy operation with its frozen operation intent, per-attempt intents, generations, capabilities, the journal's `deploy_apply` and `teardown_apply` kinds and reconcile from the target's state (J1); the `service` sandbox profile in a transient user unit with a single-use launch and no reattachment (J2, E110); the identity read that binds the original application instance and hashes the tree it runs from (§3.4); verification rounds bracketing environment-bound checks run by D3's runner through the service link (J7, J8); completion and `alpha_deployed` (J5); the environment record, the observation job and out-of-band handling (J6); the environment lease, the orchestration deadline and environment-wide generation guards (J9, E114, E115); deployment secrets and their rotation, withheld output after a restart (E116); preempting teardown; adapter qualification by command; the operator relay. M4 has no Beta or Live, no rollback, no build step, no remote or container target, no reattachment, no automatic deployment, no sessions and no user interface.

M4 is accepted when:

- `npm test` exits zero on `main` for the kernel, sandbox and project lanes, which requires every M4 acceptance row (M301 to M344) to have executable tests and none skipped, and the M1, M2 and M3 rows to keep passing, with the accepted rows of D4 Appendix C.2 migrated by a Verifier and recorded in COVERAGE;
- `surety qualify-adapter local_service` has passed on this host by Sean's command, so an `adapter_qualifications` row is `current` with every case and its control `passed`, recorded with its evidence (row M338);
- the exhaustion-lane file of row M341 has passed on the designated host (E69);
- the real-lane row M342 has passed under Sean's command (E95 Q10), with its records retained;
- the M4 acceptance report is written (section 13), and Sean has run the hands-on script (M344) if he chooses it.

Nothing less is acceptance.

Accepting M4 supports one claim: **on this host, with the recorded versions and limits, the engine deployed a candidate it had sealed from the object store only under an authorization it derived itself and a gate that could be met; created, stopped and removed only units and resources it had positively recorded for the environment; treated every adapter receipt as a claim and decided every effect by a complete read of the target; identified the running application by its original instance and the tree it was started from, never by the application's account of itself; verified a deployment only by two bracketing identity reads and the passing of required post-deploy checks it ran itself, all bound to one round of the current generation; advanced the candidate to `alpha_deployed` only through a satisfied `alpha_complete`; and after a crash kept a surviving service running with its supervision `unknown`, verified nothing on it and published none of its output.** It does not support the claims that a post-deploy check tests the behaviour it covers (D4 §5.4, §11 class C), that the engine can reattach to a service after a restart, roll back, build or install dependencies, deploy anywhere but this host, or deploy to Beta or Live.

## 3. Scope

**In M4:**

- **Configuration** (D4 §3.2, §3.3): `environment_configs` versions written only by the owner through `PUT /v1/projects/:p/environments/:e/config` (`surety env config`), immutable; `config_identity` with HMAC digests of secret values under `$SURETY_HOME/secret-digest.key`; the deployment secret namespace beside `KEY_REFERENCES`; `secrets_changed` at start; one target; the refusals of X2 (persistent state, egress, a target count other than one).
- **The artifact** (D4 §3.1; E117): the projection from the object store (tracked files minus `.surety/` and `artifact.exclude`), the canonical manifest with mode classes `100644` and `100755`, sealing under `$SURETY_HOME/artifacts/`, the rehash at every deploy, `artifacts` and `artifact_mappings` apart, bounded preparation with the values of section 11.3.
- **The authorization** (J3, J4): `POST /v1/projects/:p/deployments` (`surety deploy`) seals, proposes with engine-derived bindings, evaluates `alpha_authorize` with the completion's obligations, issues and creates the `deploy` work item; repeated requests coalesce; caller-supplied bindings only through `src/testing/`.
- **The deploy operation** (D4 §4; J1; E111 to E113, E115): the Release Operator as engine code (`src/deploy/release-operator.ts`), the environment lease, the operation's frozen intent in `finalizer_inputs`, `attempt_intents`, the precondition manifest with the issuing gate's eligibility revalidated, generations, the capability and `adapterCall`'s check, receipts as claims, reconcile after a complete inventory and quiescence, the finalizer and its one durable round, retries (`deploy_auto_retries_max`, `rollout_partial` with its bounded preview), abandonment, the orchestration deadline and stage, every lease release of §4.7, verification capacity reserved at admission.
- **The first target** (D4 §9; J2; E110): the `local_service` adapter with `systemd-run --user` and `systemctl --user` only, names `surety-<h>-<env>-g<n>.service`; the `service` profile on D2's launcher and init with the launch socket under `$SURETY_HOME/run/`; the single-use launch; the init retaining the original application instance and its exit; legal endings; supervision `attached` or `unknown`; recovery that closes launch authority first, observes service domains and never kills them, accounts for their reservations and blocks on unknown ownership.
- **Identity** (D4 §3.4): `tree_digest` by the four-step chain, the stable snapshot, the read's `instance` and `generation`.
- **Verification** (D4 §5; J5, J7, J8, J9; E114): environment-bound checks of kinds `post_deploy_identity` and `post_deploy_behavior` as release-required obligations, registered only from `deployment_verification`, their check trees holding protected inputs only; the service link; rounds registered before any read, the newest deciding; `deployment_verifications` with both reads; `last_verified` from the environment's current generation and the deciding round only; `alpha_complete` and `candidate.advanced` to `alpha_deployed`; no `releases` row.
- **The environment** (D4 §6; J6): the record's three facts, `running` and `rotation_pending_replacement`; stored reads only; the observation job with `identity_observation_every`; out-of-band observations with `teardown` and `acknowledge`; the log collection command.
- **Secrets** (D4 §7; E116): `--secret-file` for deployment references, delivery on the launch reply only, `check_secrets` and the definition field `secrets`, the redactor and the screen, the init's volatile capture, `redaction_unavailable` after a restart.
- **Teardown** (D4 §4.6): positive ownership, the cleanup record apart from the observed condition, preempting teardown.
- **Qualification** (D4 §2.6): `surety qualify-adapter local_service` and `POST /v1/adapters/:a/qualify`, its nine cases with controls, its lapse.
- **The operator relay** (D4 §5.2, Q7): `surety env open` and `close`, closed by default.
- **The role packages**, following E87 item 10's principle that each role's package says what its gate reads: the Verifier's check-writing package (`src/checks/guide.ts`) gains the environment-bound kinds, `requires`, `gate_kinds` `alpha_complete`, `SURETY_TARGET_<NAME>` and the `secrets` field, and states that `alpha_complete` reads at least one required `post_deploy_behavior` check; the Builder's package for a project with an environment states what the configuration fixes (runtime, start command, port variable, excludes) and, if Sean confirms CD4, that the service must not change its process title or arguments.
- **The reference project of the project lane**: a dependency-free Node HTTP service (Node's own `http`, nothing from npm) with requirements and criteria, workspace acceptance checks, a `post_deploy_behavior` check exercising a specified user operation, and the Switchboard mutant (section 11.2).
- **The C.2 migrations** of accepted rows (M08, M01, M44, M140), by a Verifier, in COVERAGE.
- The M4 acceptance report, the real-lane run and the hands-on run (sections 12, 13).

**Not in M4** (each refused by the engine, with a test that it is, where the engine can refuse it):

- Beta and Live (Q1): `publish`, `rollback` and export operation kinds, `beta_*` and `live_*` gates (`unsupported`, as built), `releases`, `export_records`, `promotion_records` (D4 X3).
- Rollback to the last verified deployment (Q8); teardown and a new authorized deployment are not a tested recovery plan.
- The build execution (Q4): a configuration declaring a build step is refused (`config_invalid`); a project that must be compiled or have dependencies installed is not supported.
- Any adapter but `local_service`, any remote or container target (`config_invalid` for another `adapter`); persistent state, egress and target counts other than one (D4 X2; row M312).
- Reattachment after an engine restart and recovery of old secret versions (E110, E116).
- Automatic deployment (Q3): no policy setting starts one.
- A Release Operator agent: no run of role `release_operator` is dispatched (D4 §8.1).
- Sessions and the interactive roles (E119), a second backend, the API-key mode for the real lane, the UI, the Mechanic, production telemetry, the eBPF observer.

## 4. Roles, lanes and who runs what

The M1 to M3 specs' section 4 stands: the same three roles with the same paths (`CLAUDE.md`), Sean the owner, the lean procedure of E31 and E40, objections as before. **The role paths stay as in M3.** M4 adds:

- **Five lanes** (D4 Appendix C; plan §2.1). `kernel`: real git and SQLite, the scripted check boundary of M3, and a **scripted deployment adapter** (harness mode only, through `src/testing/`) whose target states, receipts and read failures the test scripts. `sandbox`: the real `local_service` adapter and real service domains in transient user units on this host, test-built fixture artifacts and test-owned check programs, no model. `project`: the reference project deployed through the whole journey, no model; it runs with `npm test` like the sandbox lane (E92 item 2 (1)). `exhaust`: service limits, on `mini-hp01` only. `real`: Sean's command only.
- **Who may run what.** `npm test` and `--slice N`: every role and the driver, under the safety rules below. `--lane exhaust`: only on `mini-hp01` with `SURETY_EXHAUSTION_HOST`, by Sean or by the driver at his request (E69). The real lane: only by Sean's command, on a subscription token he makes (section 12). A Builder never runs a real backend. The first `surety qualify-adapter` outside a test's disposable home (the real lane's or the hands-on's) is Sean's command.
- **The Reviewer's rule** (E31) stands: anything called serious is reproduced by running the engine; in the sandbox and project lanes that includes deploying to a real unit in a disposable home, under every rule below. Never a model.
- **Host steps are Sean's.** M4 adds none: the user service manager is already H3's (D4 §9.4). The reference project's runtime is the engine's own `node`, pinned by path and hash in the configuration.

### 4.1 Safety rules for M4 (absolute; in substance in every Verifier, Builder and Reviewer brief)

Carried from M2 and M3 (E64; BS3 §4; SEAM §§127, 128), and added for service units (D4 §9.5; the orchestrator prompt's rules):

1. **Units only from a disposable home's derived name.** A test, an experiment, the hands-on script and the real lane create only units named `surety-<h>-<env>-g<n>.service` where `<h>` derives from their own disposable `SURETY_HOME`, refuse a name that already exists, and stop or reset only those exact names. Never a pattern, a glob, `--all` or a prefix with an action. A decoy unit a test seeds (D4-T02) is created by that test under a name outside every Surety prefix, and is stopped only by its exact name.
2. **Never the user's manager itself.** Nothing stops, restarts, reloads, `daemon-reexec`s or `daemon-reload`s the user's service manager.
3. **Never Docker, never the system manager**, and nothing on `mini-hp01` outside the exhaustion lane's own directories and the units its disposable homes derive.
4. **The unreadable-manager case** points the adapter at a bus address that does not exist (D4 §2.6 `unreadable`, D4-N04), never at a stopped manager.
5. **The adapter's own guard.** `adapterCall` refuses any unit name not derived from its home's hash and recorded in its store's attempt intents, and any stop, kill or cgroup write outside a domain cgroup it recorded; `cgroup.kill` is written only to a recorded domain cgroup. The Reviewer of every slice that touches `src/deploy/` checks this by reading and by running.
6. **The audit list.** Each slice's Builder lists every `systemctl`, `systemd-run`, kill, signal, `cgroup.kill`, `cgroup.procs` write, removal and mount site that its change adds or moves, with what establishes the target is the engine's own; the Reviewer checks the list; the driver reads every new acting instrument's guard in a Verifier branch before merging it.
7. **Before and after every sandbox-lane or project-lane run** (any run that may create a unit, the Reviewer's included): before it, `systemctl --user is-system-running` prints `running`; after it, `systemctl --user list-units --all 'surety-*' --no-legend` is empty, and so are the process table's leftovers of the run, `/dev/shm/surety*` and `/tmp/surety-*`. Anything left is reported with its exact name; nobody cleans up a unit they did not create. (Question 4 asks whether the runner makes this check itself.)
8. **E64's two-part fail-closed rule.** A destructive instrument (a fixture service that detaches descendants, holds ports, floods output, rewrites its arguments or exhausts its limits; a check program that attacks the link; any test step that stops, restarts or kills a unit or writes `cgroup.kill`) refuses to act unless it establishes from inside that it is contained (its pid namespace is not the host's, pid 1 is the domain init, at most 16 processes visible; any failed read is a refusal), and the test releases it only after reading from the host side that the unit carries its own home's prefix and that the instrument's pid is in that unit's domain cgroup (`/proc/<pid>/cgroup`, the cgroup's `cgroup.procs`). The test's own changes refuse any unit or cgroup outside its home's prefix.
9. **Order:** within a slice, a destructive file runs last, after containment is observed in a non-destructive one.
10. **No exhaustion here:** memory, task and storage exhaustion of a service run only in the exhaustion lane on `mini-hp01` with E69's caps; every bound a sandbox row tests (artifact limits, writable bytes and inodes, log bounds) is set low through a harness override, never by filling a disk.
11. **Nothing paid without Sean.** The real lane runs only by his command; no fixture approves spend; the token is never written to a file the repository or a record holds (E74, E87).
12. **Keep the machine quiet** during sandbox and project runs: a running service domain holds `service_memory_max` and one check's capacity (D4 §4.7), and H12 needs about 10 GiB available at D2's role defaults (E87 item 7).
13. **The first sandbox run that creates a real unit** (slice 24) is started by the driver only after Sean's go-ahead, as the probe was (question 3).

## 5. Fixed technical constraints

The M1 to M3 specs' section 5 stand, with these added or sharpened:

- **Dependencies:** unchanged; `better-sqlite3` is the engine's only runtime dependency. The reference project and every fixture service use Node's own modules only.
- **Process starts:** `src/deploy/adapters/` joins the places permitted to start a process (E39 item 7), and only for `systemd-run` and `systemctl`, both with `--user`, resolved to absolute paths and recorded with their versions on the qualification; the spawn lint (row M74's) lists it and enforces both (D4-A08).
- **No shell:** every host call is an argument array; nothing in `src/deploy/` interposes a shell.
- **No transaction across a host call** (D1 §6.1): an adapter call runs on the main thread with asynchronous spawns, a deadline and an output bound.
- **The artifact is built from the object store** with engine git (`ls-tree`, `cat-file`), never through a work tree (E93 S2); attributes, filters and hooks never touch its bytes.
- **Sealed artifacts** live under `$SURETY_HOME/artifacts/`, engine-owned, keyed by project and digest, never named by policy; the HMAC key `$SURETY_HOME/secret-digest.key` (0600) is absent from every mount plan.
- **The launch socket** lives under `$SURETY_HOME/run/`. A service launcher, started by the service manager rather than by the engine, reaches the engine only through it (the as-built launcher talks on its standard streams, `src/invoke/launcher.ts`; the `service` profile changes the channel, never the authorization rule).
- **The bus address** comes from the engine's own environment; only the qualification's `unreadable` case and its test override it.

## 8. The test seam

The M1 to M3 seams stand. M4 adds, each confined to harness mode by SEAM §7's rule and M74's lint, reachable only through `src/testing/`, never through a harness branch in a production route (J3, D4-R02):

- **The scripted deployment adapter** (kernel lane): the test scripts each call's result, each target state, inventory entry, pending job, instance and identity read, and each read failure class, so the engine's operation, reconcile, verification and observation rules run without a unit.
- **Caller-supplied authorization bindings** for kernel fixtures that need them (J3), and **labelled qualification facts** (J4) so the accepted rows' Alpha authorizations meet the same gate rule.
- **An adapter qualification stand-in** (E92 item 2's pattern): a harness route that records an `adapter_qualifications` row labelled `test_fixture`, for the sandbox lane before slice 29 builds the qualification; row M336 pins that no such route exists outside harness mode, and M307 (f) and M339 pass without it.
- **Fixture services** a test builds as artifacts: a dependency-free Node HTTP server and variants that exit, detach a descendant holding the port with output closed, re-exec into another program or other arguments, set `process.title`, print a held secret, flood output, refuse setup, or allocate and fork to their limits (the last only in the exhaustion lane), each under the two-half rule.
- **Test-owned post-deploy check programs** reaching `SURETY_TARGET_<NAME>`, and ones that attack the link (another generation, another address, a held tunnel, a reverse connection).
- **Barriers and faults** at the request, the intent, the attempt row, before and after the adapter's host call, the receipt, the confirmation, the finalizer, the round's registration, each identity read, the launch authorization (D2's), the init's `started`; faults: a lost receipt, a false receipt, each `AdapterReadFailure`, a missing bus address, a delayed manager job, a held launcher, a dropped control channel, a scripted clock past the orchestration deadline.
- **Host-side reads** the tests use, read only: `systemctl --user show` of an exact unit name, the unit's cgroup files, `/proc/<pid>/{stat,status,exe,cmdline,mountinfo,cgroup}`, the walk of `/proc/<pid>/root/surety/app`.
- **Limits of the instruments** the M4 report must state: the sandbox and project lanes prove the mechanisms on this host, kernel and systemd; the adapter qualification qualifies the adapter, never a project's service or checks; a project-lane check proves the reference project's construction only; the probe and the qualification are kept apart (AR N03).
