# Surety M6 build specification

**Status:** draft 1, 2026-10-16, written for Sean by the owner's assistant (no Builder, Verifier or Reviewer role), against **D7 draft 3** (`docs/design/sdlc-design-D7-designer.md`; every question decided by Sean, its closing section and E153 item 2; reconciled with D8 in its §17, E155 item 2), with the M6 acceptance plan draft 1 (`docs/acceptance/sdlc-M6-acceptance-plan.md`). **Not adopted; adopted when Sean answers section 16 and adopts this spec and the plan** (section 9.1). **Owner:** Sean. **Changes:** by the owner only.
**Readers:** the sessions that verify, build and review M6, the driver, and Sean.

M1 built the kernel on a scripted stand-in (`docs/spec/M1-build-spec.md`; accepted, E45). M2 made the engine run one real coding agent inside isolation it observes (accepted, E88). M3 made it run and judge a project's protected checks (accepted, E109). M4 made it deploy a sealed candidate to a real Alpha environment and verify it by observation (accepted, E138). M5 made it take a project from an idea the owner types, or a repository he adopts, to `alpha_deployed` through sessions, the governed specification, phased planning and the build's execution (`docs/spec/M5-build-spec.md`; accepted, E154). In all five a project with a user interface was built from its specification's prose: the real runs of 2026-10-15 and 16 met their requirements and looked, in Sean's words, "so basic", and a design requirement (V1's R8.5) could only stay `owed` (E152; D7, "Evidence"). M6, this document, adds **the Designer** (D7): a fourth interactive role whose product, the design, is governed like the specification; an interface inventory the engine derives from the approved architecture; design criteria that enter the specification only through the floor's approval; a hold on UI stages and on nothing else; branding assets with placeholders that never block; a preview the owner clicks through; and a design review at Alpha or on his command. Everything the M1 to M5 specs fix about roles, constraints and procedure stays in force; this document says only what M6 adds or changes.

Read sections 1 to 5 before doing anything. Sections 6 to 13 are reference for the slice you are working on. Section 11 holds the items D7's decisions and M5's acceptance carry; section 16 the questions for Sean.

## 1. What M6 is

M6 is **the Designer** (D7; E153 item 2; E155 item 3): D7 §1's journey on this WSL2 host, on a scripted backend in every lane but one and twice for real. **The policy** (D7 §2): `design: off | before_build | at_alpha | both`, default `off`, target-blind; turning it on is a tightening for undispatched UI stages, turning it off releases the holds with recorded waivers. **The three axes** (§4.1; G1, G3; Q7): targets (`web`, `android`, `ios`, `macos`, `windows`, `linux`) in the approved specification's header, UI technologies the Architect chooses beneath them under an admissibility table, and the preview capability the engine computes; interface shapes and errors in a closed shape language. **The interface inventory** (§4): a pure function of the approved bundle, its state obligations per target, its deterministic fixtures and its placeholders committed by the engine before any Designer session. **The Designer session** (§3; G9, G12): a D6 §2 session of role `designer` writing `.surety/design/` less `inventory/` and nothing else, nobody else writing there, admitting one-shot runs beside it on its project (the one exception to D6-S08). **The design product and its check** (§5): closed schemas for the manifest, platform-neutral tokens, flows, per-target screens, navigation, criteria and the asset manifest; mockups of five closed kinds; `checkDesign` over eight clauses with AA contrast computed from declared pairs and nothing executed; a selection the owner may narrow to a floor. **The preview** (§5.7; G4): the design tree served by an engine-authored static server on a `local_service` unit of the reserved environment `design-preview`, web mockups natively, every other target inside an engine-authored frame labelled a simulation, never a candidate or evidence. **Assets** (§6; G10, G11, G14, G15): a versioned manifest whose `slot@version` names one set of files forever, header checks with no decoding, engine placeholders for every default slot, the effective asset set as the only asset source of packages, checks and projections, Builders' asset bindings validated at integration, `asset_updated` fix work and `asset_version_changed` obligations on every change of an effective version, the release hook `assets_required_for` inert until D5. **Approval and readiness** (§7; G5, G6; Q1): `design_approval` batched with one `spec_change` carrying the design's criteria and one human-test requirement per target, bound to the specification version that change creates so it never stales itself; criteria from a closed catalogue scoped by target and technology; native conventions recorded `not_checkable_yet`; `design_ready` set only when the covering protected version is applied. **Planning and execution** (§8): UI stages held `design_pending` or `design_stale` by a third milestone, backend stages untouched, plan-check clause 5 and the design coverage clause, the UI Builder's package. **Staleness** (§9; G8): the impact analysis's design class. **The review** (§10; G7, G13; Q4): at Alpha with the engine's observations of the served web files, or on the owner's command against a native build he names with evidence he supplies, kept apart by provenance; verdicts proposed by the role and confirmed only by the owner's act; a first design at Alpha when none was approved. **No silent stalls** (§11): no design hold without an open `design_due` naming it. **Retrofit** (§12), **pace** (§13). M6 builds design artifacts for every target and execution for none but web's mockups: no emulator, simulator, device runner, native build, packaging check, headless browser, rendered screenshot, pixel comparison or image generation (§15 class B; Q2, Q3); D8 is not M6 (E155 item 1).

M6 is accepted when:

- `npm test` exits zero on `main` for the kernel, sandbox and project lanes, which requires every M6 acceptance row (M501 to M546, section 9; fewer if section 16 drops a conditional row) to have executable tests and none skipped, and the M1 to M5 rows to keep passing, with the accepted rows D7's corrections touch migrated by a Verifier and recorded in COVERAGE (section 9.3);
- the exhaustion lane's existing files (M5's five) have passed once on `mini-hp01` at the final revision (E69; question 8): M6 adds no exhaustion file;
- the two real-lane rows, M519 and M535, have passed (section 12), each after its rehearsal, with their records and pace reads retained;
- the M6 acceptance report is written (row M540, section 13), and Sean has run the hands-on (M541) if he keeps it.

Nothing less is acceptance.

Accepting M6 supports one claim: **on this host, with the recorded versions and limits, on a scripted backend and twice for real, the engine derived an interface inventory from the approved architecture alone and held a Designer session to it; let the Designer write the design and nothing else, and nobody else write the design; checked every save mechanically, per target, without executing anything the role wrote; served web mockups natively and every other target's only inside a frame it labelled a simulation, and counted neither as evidence; let a design's criteria reach the specification only through the floor's approval, batched so the approval never staled itself; held UI stages, and only UI stages, until the protected version covering the design's criteria was applied, and never held anything on an asset's status; gave Builders and checks only the effective asset set, never a held or unanswered proposal, carried every approved replacement into the built application through recorded bindings, and let no parity result stand for a version it did not read; staled exactly the screens a change touched; recorded a review's verdicts as the owner's only on his own act, kept engine-observed evidence apart from what he supplied, and let no verdict on a simulation count as native; and left no design hold without an open question naming it.** It does not support the claims that a design is usable or good, that a simulation is faithful to its native technology, that a UI Builder implements a design, that the static checks catch what a person would call off-design, that an owner build or a screenshot is what he says it is, or that the app shows a bound asset where it is bound (D7 §15 classes B and C), or anything D5 or D8 owns.

## 4. Roles, lanes and who runs what

The M1 to M5 specs' section 4 stands: the same three roles with the same paths (`CLAUDE.md`), Sean the owner, the lean procedure of E31 and E40 as E123 amended it, objections as before. **The role paths stay as in M5.** M6 carries M5's procedure as it ended:

- **One full run per slice** (E123): the driver's, from a clean scratch copy; the Builder runs its own slice's files, every earlier file its change touches and the unit tests; the next slice's Verifier and Builder overlap the run.
- **The split gate on `mini-hp01`** (E143 item 4; E149 item 6; E150 item 6): a slice's full run is the split gate there (three workers, one queue, longest first, `TMPDIR=/var/tmp`, the same selection rules as `run-tests.mjs --slice`); **a failure is rerun alone before it is called real**, three times, and one that passes alone is recorded as load-only, never as a pass of the gate and never as a gate-rule change. The workstation stays with the agents.
- **Every agent tests under a private short `TMPDIR`** (E150 item 6), and nobody cleans up by pattern.
- **Five lanes**, as M5 (plan §2.1): `kernel`, `sandbox` (real domains and, for the preview, a real transient user unit), `project` (the two design journeys on real domains and real units, with `npm test`), `exhaust` (M5's files only; M6 adds none), `real` (two files, section 12).
- **Who may run what.** `npm test` and `--slice N`: every role and the driver, under section 4.1. `--lane exhaust`: only on `mini-hp01` with `SURETY_EXHAUSTION_HOST` (E69). The real lane: by Sean's command, which E144 item 2 made standing (the driver starts a paid run when the plan calls for it, on Sean's subscription token only, and reports its usage after it). A Builder never runs a real backend; no session on a real model is opened outside the real lane.
- **The Reviewer's rule** (E31) stands: anything called serious is reproduced by running the engine, in the sandbox and project lanes including a Designer session on the scripted backend and a preview on a real unit in a disposable home. Never a model, never a browser.
- **Host steps are Sean's.** M6 adds none: the preview is a `local_service` unit under H3's user manager (D4 §9.4).

### 4.1 Safety rules for M6 (absolute; in substance in every Verifier, Builder and Reviewer brief)

BS5 §4.1's rules 1 to 20 are carried whole, unchanged in substance, among them: units only from a disposable home's derived name, acted on only by exact name (rule 1; the preview's unit is `surety-<h>-design-preview-g<n>.service`); never the user's manager itself (rule 2); E64's two-part fail-closed rule (rule 8); no exhaustion here (rule 10); nothing paid without Sean's standing command and no session on a real model outside the real lane (rule 11); nothing a session writes is run (rule 14); every `SURETY_HOME` at most 56 bytes, the engine refusing a longer one (rule 15); `TMPDIR` on disk on `mini-hp01` (rule 16); the clock's 10 s margin and monotonic durations (rule 17); the rehearsal plays from the package (rule 18); production paths only in the journeys (rule 20). Rules 21 to 26 are added for M6.

21. **Nothing the Designer or the owner wrote is executed** by the engine, the design check, a test or a fixture role: the check reads JSON, SVG as text and raster files by their headers (D7 §5.6, §14); mockups and evidence are served or stored as data; no test opens a mockup in a browser, runs a mockup's script, decodes an image beyond its header or plays a recording. A test reads served bytes over HTTP through the relay or the service link only.
22. **No browser, emulator, simulator or device** is installed or launched by any test, real step or agent for M6, on the workstation or `mini-hp01` (D7 §15 class B; Q3). Owner-supplied review evidence and asset files in tests are bytes the test generates with valid headers (a flat PNG, an SVG text, a WebM or MP4 header); no fixture carries a real image of a person, a device screen or a third party's mark.
23. **The preview is a unit of the disposable home** (D7 §5.7): started only under its derived name, read before and after every run by section 4.1 rule 7's check, stopped only by exact name. **The first run that deploys a preview on a real unit** (slice 40's project-lane journey) is started by the driver, who shows Sean the before-and-after unit lists (rule 13's form, E124); later runs proceed under these rules without asking.
24. **The relay is opened only by a command in the test's own home**, bound to `127.0.0.1`, and closed by the case that opened it (D4 Q7). The review's fetch of served files is the engine's, through the service link (D4 §5.2); no test or fixture lets a role's domain reach a service (D2 §2).
25. **No silent stall in a journey or a real step** (E152's lesson; D7 §11): a project-lane journey or a real-lane step that finds its project with no runnable work, no work in flight and no open owner question, short of its expected end, fails at once naming that state, never waiting out its timeout; a real step whose project ends with a question the step raised still open fails, naming it (M444's open blocker, E154 item 6 (3)).
26. **The owner acts only through recorded acts** (D7 §10.3; M5 report §17): every human act goes through the owner's production routes and is recorded with its actor; the real-lane runner prints each act and waits; the driver acting on Sean's instruction records the instruction's words and the act (`acted_by: driver, on_instruction: "<words>"`), and the report says so; no harness default answers `design_due`, `design_approval` or `design_verdicts` outside the scripted human acts of the seam (D7 §11, last item), and no role's file, transcript or close stands for an owner verdict.

## 5. Fixed technical constraints

The M1 to M5 specs' section 5 stand, with these added or sharpened:

- **Dependencies:** unchanged; `better-sqlite3` is the engine's only runtime dependency. The shape language, the closed schemas, the WCAG contrast arithmetic, the magic-byte and header reads (PNG, WebP, ICO, JPEG, MP4, WebM), the SVG activity scan, the placeholder SVGs and the flat PNG encoder (node's `zlib` and its own CRC) are the engine's own code. The preview's static file server and its frame are an engine-authored file in the engine's install, its hash recorded on every preview deployment.
- **Process starts:** unchanged in kind. A Designer turn starts a process only through D2's launcher as any session turn; the preview's process starts only as a `local_service` application domain through D4's operation (D4 §9.2); the design check, inventory derivation, placeholder generation and evidence checks start none.
- **No shell:** unchanged. Owner-typed text (a turn, a build identifier, a verdict edit, a note on `revise`) and file names of evidence or assets are written to records and context files, never interpolated into a command.
- **No transaction across a host call** (D1 §6.1): the inventory, the design check, the impact's design class, the effective set and the binding validation are pure functions over the store and git blobs read before their transactions; the review's served-file fetch is an observation recorded after it returns.
- **Closed schemas** (D7 Appendix B; D6 §9): every machine file the engine reads refuses unknown fields and names the field; a field not applicable to a screen's target is refused (B.12); a review file carrying a verdict `status` is refused (B.14).
- **The effective asset set is the only asset source** (D7 §6.4): packages, check inputs and projections read `design_effective_assets` and nothing else; a manifest's latest files are never read for them.
- **Generations and bindings are compare-and-swap values** (D7 §7.4; D1 §4.6): `design_approval`, `design_due` and `design_verdicts` are bound and stale as any decision; an effective version moves only in an approval's transaction; a role's product moves none.
- **Idempotent triggers** (E153 item 1 (a); D6 §5.5's form): inventory derivation, the placeholder commit, `design_due`, `asset_updated` work, `asset_version_changed` obligations, the stage-to-screen binding, the preview's teardown and the post-final-phase replan are each keyed so that repeated ticks, replays and recovery after a restart create no second row.
- **The latest by insertion** (E148 item 6; E149 item 2): every "latest design revision, save, review or effective version" orders by `rowid` or event `seq`, never by a wall-clock column.
- **Unix socket paths and homes** as M5 (E134): the engine refuses a home longer than 56 bytes at start.
