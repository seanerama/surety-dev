# Surety M4 acceptance plan

**Status:** draft 1, written by the architect; **adopted by Sean, 2026-10-09 (E121)**, with CD1 to CD4, the proposed numeric defaults and the recommendations to questions 1 to 9 of BS4 §16 as recommended. 2026-10-09, in the form of the M3 plan (`docs/acceptance/sdlc-M3-acceptance-plan.md`), with the M4 build spec (`docs/spec/M4-build-spec.md`, BS4). It is the inventory the M4 build's tests will be written from: each slice's Verifier splits its rows into named cases and fixes the details of section 2.6 in the seam. No test is written by this pass and no engine code is touched. This file does not claim that any row has a test or has passed.

**Basis:** D4 draft 2 (`docs/design/sdlc-design-D4-deployment.md`, approved to build, E120), its Appendix C of 63 statements and its C.2 migrations; Astra's review (`docs/reviews/D4/sdlc-review-D4-Astra.md`, cited AR) as decided in E110 to E118; the errata E95 and E109 to E120; the feasibility probe (`docs/reviews/D4/feasibility-probe-2026-10-07/`); the accepted engine's seam (`packages/engine/test/acceptance/harness/SEAM.md`, to §243); the M3 report and its not-claimed list.

**Rows:** `M301` to `M344`, so no row collides with M1's `M01` to `M74`, M2's `M101` to `M142` or M3's `M201` to `M241`. Forty-four rows: twelve kernel, eleven sandbox, fourteen kernel and sandbox, one sandbox and project, two project, one exhaust, one real, one report and one hands-on. Every Appendix C statement is a row or a named case of one (section 4.1), and so is every item E120 item 2 sends to M4 (section 4.2). The M1 to M3 rows are accepted and are not re-planned; where a D4 correction changes what one of their fixtures must supply, section 4.3 says which.

## 1. Sources, authority and scope

References throughout this plan:

- **D4:** draft 2. `§n` is its section; `J1` to `J9` its §12.1 corrections; `Q1` to `Q10` its decided questions (§12.2); `D4-Xnn` a statement of its Appendix C; `RV1` to `RV6` its earlier review findings; `B01` to `B08` and `N01` to `N04` Astra's amendments and suggestions as E110 to E118 decided them.
- **D1, D2, D3, BS, RN:** as the M3 plan; D2's `K1` to `K10` and D3's `L1` to `L8` stand.
- **BS4:** the M4 build spec; `CD1` to `CD4` its carried decisions (BS4 §11.1).
- **E:** the errata, E1 to E120. **SEAM:** the accepted seam, §n.

D4 extends D1 to D3 and changes them only by J1 to J9. Where D4 leaves a detail to the tests, the Verifier fixes it in the seam (section 2.6). The tests are the contract; a Builder never edits an acceptance test to obtain a pass and files an objection instead; Sean keeps integration and approval authority. Design review of D4 stopped at E120: a finding after this plan is a decision for Sean or a failing acceptance test (E20).

**What M4 adds, and what these rows cover.** D4 §§2 to 10 as BS4 §3 lists them: configuration and its identity, the artifact, the engine-derived authorization, the deploy operation and its attempts, reconcile, the `service` profile and `local_service`, identity reads, verification rounds and the service link, completion, the environment record and its observation, out-of-band changes, deployment secrets, teardown, adapter qualification, the operator relay; and two journeys, one on the scripted adapter and one on a real unit, then the reference project's and the real one.

**What M4 does not cover.** BS4 §3's "Not in M4": Beta and Live, rollback, the build execution, other adapters and targets, reattachment, automatic deployment, a Release Operator agent, sessions and the interactive roles, a second backend, the UI. Their refusals are rows where the engine can refuse (M312, M336).

### 2.2 Safety and containment

Every sandbox, project, exhaust and real row follows BS4 §4.1's rules 1 to 13. In particular: units only from the test's own disposable home's derived name, refused if the name exists, acted on only by exact name; never the user's manager itself; never Docker or the system manager; the unreadable case by a missing bus address; the adapter's own guard; the Builder's audit list of every `systemctl`, `systemd-run`, kill, signal, `cgroup.kill`, removal and mount site, which the Reviewer checks; the before-and-after reads around every run; E64's two halves for every destructive instrument (fixture services that detach, hold ports, flood, rewrite their arguments or exhaust limits; check programs that attack the link; any step that stops, restarts or kills a unit), each released only after the host-side read shows the unit carries the test home's prefix and the instrument's pid is in that unit's domain cgroup; the destructive file last in its slice; no exhaustion here. Rows M310, M311, M314, M316, M321, M322, M324, M326, M327, M331, M334 and M341 carry such instruments.

### 2.3 Harness additions this plan assumes

These reach production code as ordinary parameters or seam hooks under SEAM §7's confinement rule and M74's lint, only through `src/testing/`; none is selectable outside harness mode (D4-R02). The Verifier names them exactly in the seam; the Builder may object.

- **The scripted deployment adapter** (kernel): the six calls of D4 Appendix B with every result, outcome, inventory entry, pending job, instance and failure class scriptable, and every call counted.
- **Caller-supplied authorization bindings** and **labelled qualification facts** for kernel fixtures (J3, J4), so M01's and M44's shared fixtures meet the same gate rule.
- **The adapter qualification stand-in** for slices 24 to 28, labelled `test_fixture` (E92 item 2's pattern); M307 (f) and M339 pass without it, and M336 (b) pins that its route exists only in harness mode.
- **Fixture artifacts and services** the test builds: a dependency-free Node HTTP server answering a health route and a specified operation; variants that exit naturally, detach a descendant holding the port with output closed, re-exec into another program or with other arguments, re-exec with identical arguments, set `process.title`, print a held secret on request and into their output, flood output, refuse setup, fail `exec`, write to their volatile filesystem, and (exhaust only) allocate or fork to their limits.
- **Test-owned post-deploy check programs:** exit n; call `SURETY_TARGET_<NAME>`; try another environment's or generation's address, a host address and other loopback ports; hold a tunnel open across a teardown and reconnect; accept a connection back.
- **Barriers:** `deploy.requested`, `deploy.intended`, `deploy.attempt_recorded`, `adapter.before_host_call`, `adapter.after_host_call`, `deploy.receipt_recorded`, `deploy.confirmed`, `deploy.before_finalizer`, `deploy.round_registered`, `verify.after_first_read`, `verify.before_second_read`, the identity read's snapshot halves, D2's launcher barriers for a service launch, `init.app_started`, `init.app_exited`.
- **Faults:** a lost receipt; a false receipt; each `AdapterReadFailure`; a missing bus address; a held launcher (a pending manager job); a dropped control channel; an init report altered to disagree with the host; a scripted clock past the orchestration deadline and past a round's deadline; a delayed verification callback; a restored store (from a backup) missing an attempt intent.
- **Harness overrides, in small units:** the artifact bounds, `host_reserve_disk` as admission sees it, the writable bounds, `service_log_max_bytes`, the `service_link_*` limits, `identity_observation_every`, `deploy_auto_retries_max`, and (exhaust only) `service_memory_max` and `service_tasks_max`.
- **Decoys:** a unit the test creates under a name outside every Surety prefix, and a unit of a second test home's prefix, each stopped afterwards by exact name.
- **The reference project** (`harness/project/`): requirements with criteria, workspace acceptance and smoke checks under M3's protective wrapper, a `post_deploy_behavior` check over a specified user operation, one disposable secret, and the Switchboard mutant of M340.

### 2.4 How results are observed

From outside the engine, as in M3: the API (the environment read, the deployment request's answer, the operation, its attempts and rounds, the gate reads, decisions, events), the store (D4 A.3's tables and columns), git, the filesystem (the sealed artifacts, the engine home, the run directory), the scripted adapter's call counts, and on the host, read only: `systemctl --user show` of an exact unit name, `systemctl --user list-units --all` filtered by the test's own prefix, the unit's cgroup files, `/proc/<pid>/{stat,status,exe,cmdline,environ,mountinfo,cgroup}`, the walk of `/proc/<pid>/root/surety/app`, and `journalctl --user -u <exact unit>`. A fixture service's or check program's report of what it saw is test instrumentation; whatever the claim is about is corroborated host-side. Deterministic barriers, the controlled clock and crash-and-reopen as M1 to M3.

### 2.5 Honest `not_exercised`

Only M341 off the designated host, and the real row if Sean does not run it. Nothing else in M4 depends on host features M3 did not already require beyond the user manager's transient services, which H3 already needs. A sandbox or project row on a host without a running user manager fails.

### 2.6 Details D4 leaves to the tests, which the Verifier fixes in the seam

The scripted adapter's interface and how a test scripts an inventory; the form of `<h>` and how a test computes its own prefix; the reason codes of M312's refusals at the request; the boundary values of the artifact bounds and the harness overrides; how a test reads the init's and the application's instances host-side and drives a disagreement; the form of `service_link_log` and `deployment_logs`; the precondition manifest's fields; the `missing` entries' ids; the round's `deadline_at` field under CD1; the `detail` naming `supervision_unknown` under CD2; the argument-mismatch detail under CD4; how the observation records each fact's source timestamp (M330); how a test drives an engine restart with a surviving service; how a test restores a store from a backup (SEAM's existing backup harness); the hands-on script's steps; the real lane's step names and confirmation phrase (BS4 §12).
