**Post-fix: 4/4.** In (b) the later observation of generation 2 is current: no `ended_by`, `fresh`, its condition as recorded, on both the read and the list.

## M631: a refused policy Alpha request reconsidered (finding 1)

**Readings this file makes (for Sean's review of the row):**
1. "`alpha_deploy: automatic`" is read as `on_phase_complete`. That is the only value under which the engine requests by itself; the configuration has `manual` and `on_phase_complete`. The fixture is a rapid prototype, whose policy is `on_phase_complete`.
2. **The row's premise "refuses CHECK_NOT_PASSED on K and records the request `not_issued`" does not arise on this engine.** When K is registered and running, the policy's evaluation refuses CHECK_NOT_PASSED on K but records no outcome under the key. A reason whose result is still to come "settles" (deploy.ts `requestDeployment`, `settling`), and the policy requests again once K ends. (L) pins this literal path: with the clock stepped back between K's registration and the evaluation, no row while K runs, and one policy request issued after K passes. It **passes on the base**, so it reproduces nothing. The review's smallest case (its step 3, "recorded not_issued") does not hold as written.
3. The stall of finding 1 needs two things: a key already `not_issued` from an earlier refusal, and a newer settling evaluation as the candidate's latest. This is the state real visual run 2 met ("the key kept the not_issued of the gap's refusal"). Cases (a) to (e) put that row in place with a labelled store write: one `deployment_requests` row (`requested_by` policy, `outcome` not_issued, `reason` null) under the engine's own key (D4 A.3 canonical `{project, completion_binding, candidate, environment_configuration}`). No event or other row is written. Everything else is genuine: K's registration, the clock step, the policy's own settling evaluation, K's result and the ticks.
4. "Exactly one new policy `deployment_requests` row" is read as the key's one policy row taken on and issued: an issued authorization, the outcome no longer `not_issued`, exactly one issued authorization and one deploy work item. The store keeps one row per key and requester (`UNIQUE (project, request_key, requested_by)`, migration 0024; `recordRequest` updates that row), and the Builder keeps it so ("the key's one policy row is still taken on (no second row)").
5. Fixture detail: the Builder's tree writes a `package.json` start script, so the deployment read can tell a Node service. Without it `deploy_readiness` reads `unknown` (output kind unknown) and never reaches the checks.

**Base (1/5).**

**Post-fix: 5/5.**
