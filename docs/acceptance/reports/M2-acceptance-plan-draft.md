# Surety M2 acceptance plan — draft

**Status:** draft row inventory for M2, written by the Verifier on 2026-10-03 on branch `verify/m2-plan`, in the form of Astra's M1 plan (`docs/acceptance/sdlc-M1-acceptance-plan-Astra.md`). Sessions, Codex and deployment are not M2 (Codex's template is designed and may be qualified if cheap; M2's end does not need it).

**Rows:** `M101` to `M142`, so no row collides with M1's `M01` to `M74`. Forty-two rows: forty in the three lanes (nine kernel, twenty-six sandbox, five real), one report row and one hands-on row; every one of D2 Appendix B's 73 statements is a row or a named case of a row (section 4.1 accounts for each). The M1 kernel and the two merged M2 slices are accepted and are not re-planned here; their seam sections stand and the rows below add to them.

### 2.3 Harness additions this plan assumes

These reach production code as ordinary parameters or seam hooks under SEAM §7's confinement rule; none selects the harness boundary for production (D2-C06, M109). The Verifier names them exactly in the seam when the rows are written; the Builder may object.

- **Host checks switch.** A harness flag that leaves the host checks and the probe suite unrun (`not_exercised`, no `host_qualifications` row) for kernel-lane engines, so the hundreds of engine starts in the M1 rows do not each run twenty probes; sandbox-lane engines run them. Outside harness mode there is no switch: every start runs the checks (D2 §7.1).
- **Harness overrides for host checks and probes.** A way to make a named check fail or be unexercised (H6 "missing tool", H11 "no tmpfs"), and to make a named probe's target absent, its control fail, or its negative unattempted (M110, M124).
- **A fixture trust entry.** A harness route that installs a `trust_entries` row (`proposed` or `active`, labelled `test_fixture`) for the scripted backend or for a real backend name bound to a **stand-in binary**: a test-owned executable whose path and SHA-256 the entry records, which records the argv and environment it was given and runs the scripted child. Only the sandbox and kernel lanes use it; it can never name a real backend's real binary. This is the M2 analogue of M1's baseline-approval fixtures (Plan §1; E19): test setup, not a public route.
- **A harness resolver.** A name-to-addresses map the egress proxy consults in harness mode instead of the system resolver, with a query counter and an optional delay, so P8's answers (private, mixed, IPv6, mapped, rebinding) are constructed and counted (M127, M128).
- **The echo endpoint.** The engine's own, under the `probe` profile (D2 §2.4, §7.1); the tests read what it received.
- **Sentinels.** Every probe target is seeded and verified from the host before the probe runs: a sentinel file at the real `api.token` path (its real content), in `store.db`'s directory, `engine.log`, `records/`, another domain's area, a second workspace, a developer checkout, each credential location D2 §2.3 enumerates, a host abstract socket and a host pathname socket both listening, a host sentinel process, a `/dev/shm` sentinel. A probe whose target the host cannot read before the probe fails the case (AR §8.1).
- **Barriers,** `pause` and `kill` as SEAM §18, at: `launcher.before_placement`, `launcher.placed`, `launcher.before_authorization`, `launcher.authorized`, `init.before_backend`, `boundary.before_terminated` (the engine has read `populated 0` and is about to record it), `collect.before_read`, `qualification.before_dispatch`, `scope.before_create`.
- **Faults,** one-shot or standing as SEAM §61: `manager_unreachable` (the engine's client of the user manager fails), `init_report_lost` (the backend's exit report never reaches the engine), `challenge_response_dropped`, `launcher_wait` (the launcher's exit cannot be established), `token_read` (M107's "before any token read"), plus `before_event` on the new event types.
- **The probe program.** Engine-shipped, at `/surety/context/probe` in every profile that needs it; the probe suite runs it from the scripted role, and the containment canary asks the real agent to run it (D2 §7.2). In the sandbox lane the scripted role and the probe program are the Verifier's instruments and their reports are test instrumentation; every claim about the host is corroborated host-side (the sentinel unchanged, the socket unreached, the echo endpoint's log, the egress log, the process table). In the real lane nothing the agent prints is evidence (AR B05).
- **Scripted role additions:** a child that ignores TERM; one that `setsid`s, clears its environment and double-forks; one that starts a daemon and exits; one that forks to a limit, allocates to a limit, writes and creates to a limit; one that writes a held secret everywhere it can; one that makes links, FIFOs and oversize files at `/surety/out/result.json`; one that runs the probe program's actions and reports; one that runs git commands and reports.

### 2.4 How results are observed

Every required result is observable from outside the engine: the API (`GET /v1/engine` with the host qualification, attempts, entries and the bootstrap exception; the run, work, ledger, records, decisions and candidate reads; events), the store (new tables and columns of D2 A.3), git (the integration branch, the registry, the repository's real `config` and hooks), the filesystem (the engine home, the host sentinels, the absence of any volatile content on durable disk), the process table (`/proc/<pid>/cgroup`, `environ`, `status`, `cmdline`, `fd`; which the same uid may read for the engine's own helpers), the cgroup files of the delegated subtree, and the proxy's log, published as the domain's `egress_log` record. The tests never read a domain's volatile filesystem from the host; where a row needs the role's own observation (its mount table, its environment, its view of `/proc`), the role reports it in its result file, which the engine collects after termination, and the host-side witness corroborates whatever the claim is about.

Deterministic barriers are used at every store boundary a case depends on, as in M1; grace periods and timeouts are lowered through `config.json`; leases and deadlines use the controlled clock (SEAM §18). A crash case reopens SQLite, reads the cgroup files and the process table, then resumes through the public API. A test about termination asserts the cgroup's `populated 0` and the directory's removal, never a pid's absence (D2 §3.2). Cases that end runs compare the durable facts of SEAM §24's `projectFacts` with a reference where the row says so.

### 2.5 Honest `not_exercised` on this host

Some cases cannot run everywhere and say so rather than pass vacuously (D2 §2.8; AR P10, P11, P12): P11 and the WSL-specific absence claims off WSL2 (W); the Docker socket of P10 when none exists; a host submount under a permitted path (M119 (d)) when the host has none under `/usr`, `/bin`, `/lib`, `/lib64`; a member the kill cannot end (M115 (f): a process in uninterruptible sleep cannot be made on demand); a real stop of the user manager (M115 (h), question 6); every OBS case without H13. The engine reports each as `not_exercised`; the report lists them (M141).

### 2.6 Details D2 leaves to the tests, which the Verifier fixes in the seam

Listed so the Builder knows they are coming: the fewest fields of the `qualification_approval` and `trust_activation` manifests beyond A.7's list, and what "current host eligibility" binds (the active `host_qualifications` row and its mechanism fingerprint); the fewest keys of `exit_evidence`; the shape of the `egress_log` and `provider_files` records and of the probe results inside `qualification_evidence`; the UUID derivation of `--session-id` from the invocation id; `host_id` (a stable installation identity, never the boot id, or every reboot would revoke every entry); the name of the startup step that runs the host checks and where `GET /v1/engine` shows them; the form of the `host_qualifications` row written while `ui_bootstrap` is true (written and never active, with `bootstrap_exception` true); the harness switches and barriers of section 2.3; the small caps used for P20 (D2's preamble observed `size=1m,nr_inodes=64` enforceable); the proxy limits' test values; which per-tunnel proxy limits only refuse the tunnel and which bounds cancel the run (M128); the outcome of a run whose materialization the secret screen refused (M132); how a refused Alpha-exception proposal is shown on the run read (M105); whether `reject` on `trust_activation` or `qualification_approval` leaves `proposed` (M102, M135; the re-ask question of E50 stays Sean's); what a pause re-grant's event carries so a test can tell a fresh challenge from a buffered heartbeat (M118).
